# AB实验样本量计算与显著性核查（ab-test-sample-size）

AB 实验被做砸，最常见的原因**不是统计方法用错，而是样本量从来就没算过**：
定个 5% 的提升目标就跑，跑到「显著」为止——这不是实验，这是拿数据凑结论。

这个技能做三件事：**先算够不够** → **再算跑多久** → **最后验分流**。

> 顺序不能换。没算样本量就上线，后面所有显著性判断都不可信。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给定基线率/MDE/α/power 算出每组所需样本量 | ❌ 代替实验平台的统计引擎给出「已显著」结论 |
| 反解现有流量下实验至少要跑几天 | ❌ 保证按公式跑够天数就一定能显著（业务波动会吃掉效应） |
| 做 SRM 抽样比例失衡检验并给处置方向 | ❌ 判定实验的业务成败（那是产品判断不是统计判断） |
| 检查分流单位、去重与剔除规则是否写全 | ❌ 事后改口径重算历史实验数据 |
| 给出停止规则与多重比较校正建议 | ❌ 支持「跑到显著就停」的提前停止 |

**以下情况必须先做别的：**
- 指标是**比率型但方差极大**（如退款率 0.1%）→ 先考虑改用「转化绝对量」或提高基线，再算样本量
- 实验**分层/聚类抽样**（按门店、按城市分流）→ 有效样本量要乘以设计效应，不能用下面的公式
- 一个实验里同时看 5 个以上指标 → 先定主指标再做校正，不要算完再看
- 分流单元与观测单元不一致（按会话分流、按用户统计）→ 先定分流单元，见规则文件

## 二、完整工作流

```
第 1 步  读规则文件 rules/ab_sample_size.md（公式、取值表、分流与剔除口径）
第 2 步  确定四件事（缺一件就不要开跑）：
         主指标 + 基线率 p1 + 期望提升 + 实验流量
第 3 步  算样本量
         python scripts/ab_sample_size.py --p1 0.10 --mde 10 --mde-rel \
             --alpha 0.05 --power 0.8 --arms 2 --daily 100000 --traffic 0.5
         → 得到每组所需 n、所需总样本、所需天数与最少整周数
第 4 步  流量不够就三条路选一（不要硬跑）：
         ① 放宽 MDE ② 提高实验流量 ③ 合并同类实验（同变体不能同时做两件事）
第 5 步  上线后先跑 SRM，再看指标
         python scripts/ab_sample_size.py --mode srm --observed 4902,5011
         p < 0.001 → 分流失效，实验作废重跑，不要去分析指标
第 6 步  达到预定样本量且 p < α 才读结论；未达到就是「数据不足」，不是「无效果」
第 7 步  记录：实际跑天数、实际样本量、预设停止点、结论与效应量 CI
```

## 三、样本量公式（比例型指标，双侧）

两组各 `n` 个用户，基线率 `p1`，实验组 `p2`，显著性水平 `α`，统计功效 `1-β`：

```
                (z_{1-α/2} + z_{1-β})² × [ p1(1-p1) + p2(1-p2) ]
n (每组)  =    ─────────────────────────────────────────────────────
                                  (p2 - p1)²
```

连续型指标（金额、时长、次数，标准差 σ）：

```
                2 × (z_{1-α/2} + z_{1-β})² × σ²
n (每组)  =    ─────────────────────────────────────
                             δ²
```

**三条必须记住的推论：**

1. `n ∝ 方差项 / δ²`。比例型指标里方差项在 p=0.5 时最大、p→0 或 p→1 时变小，但**绝对提升 δ 通常随 p 同比例变化**，两者相抵后总体呈现「基线率越低、样本量越大」：1% 基线每组要 16 万人，10% 基线每组 1.5 万人。
2. `n ∝ 1/δ²`。想多检测 1 个百分点的提升，样本量变 4 倍；把提升阈值砍半则变 100 倍。**提升目标定得越乐观，实验越跑不出结果。**
3. `n ∝ σ²`。金额类指标方差极大时，先考虑截尾（winsorize）或分桶取中位数，而不是硬堆样本量。

脚本会额外给出**达到该样本量时的实际统计功效**，用于验证公式与 power 一致。

## 四、常用取值表（α / power / z 值）

| α（单侧/双侧） | 场景 | z_{1-α/2} | power=0.8 → z_{1-β} | power=0.9 → z_{1-β} |
|---|---|---|---|---|
| 0.10 双侧 | 早期探索、容错高 | 1.645 | 0.842 | 1.282 |
| **0.05 双侧** | **互联网 A/B 常规默认** | **1.960** | **0.842** | **1.282** |
| 0.01 双侧 | 涉及资金/合规 | 2.576 | 0.842 | 1.282 |

**默认组合就是 α=0.05 双侧 + power=0.8**，理由：power=0.8 意味着「真有效却没测出来」的概率为 20%，这在长期高频实验里是可接受的成本；power=0.95 会让样本量翻近一倍（系数从 7.85 涨到 13.0）。

## 五、按基线率的样本量速查（相对提升 10%、α=0.05 双侧、power=0.8，每组）

| 基线率 p1 | 目标 p2 | 每组样本量 | 总样本量（两组） |
|---|---|---|---|
| 1% | 1.1% | 163,092 | 326,184 |
| 2% | 2.2% | 80,679 | 161,358 |
| 5% | 5.5% | 31,231 | 62,462 |
| **10%** | **11%** | **14,748** | **29,496** |
| 20% | 22% | 6,507 | 13,014 |
| 30% | 33% | 3,760 | 7,520 |
| **50%** | **55%** | **1,562** | **3,124** |
| 80% | 88% | 326 | 652 |

> 数字由 `scripts/ab_sample_size.py` 用默认参数（α=0.05 双侧、power=0.8）算出，可自行复算验证。
>
> 三条直观结论：① 基线率 1% 的实验每组要 16 万人，5% 的要 3 万——**低转化率实验样本量按 `1/p` 膨胀**；② 10% 那行比 5% 那行还高，因为相对提升同为 10% 时绝对差从 0.5pp 变成 1pp；③ 80% 那行最小，但那是「+8pp」的巨大相对提升，对高基线业务几乎无意义。**必须先把相对提升换算成绝对差再进公式。**

## 六、分流与剔除口径（不做对，白跑）

| 要素 | 口径要求 | 写错的后果 |
|---|---|---|
| 分流单位 | 明确到「用户 / 设备 / 会话 / 门店」；默认用**用户**，同一用户的全部流量必须落在同一组 | 同一用户横跨两组，指标被自己污染，效应被稀释到接近 0 |
| 分流比例 | 与目标样本量成比例；对照组不是「剩下的」而是**固定比例**（如各 50%） | 一边倒的分流，后期无法补齐 |
| 去重 | 实验期内只按分流标识首次分组；跨端用户按唯一用户 ID 归并，未登录按设备 ID 归并 | 同一用户被算两次，样本量虚高、方差低估 |
| 剔除规则 | **上线前写死**：机器人/内部账号、脏数据、作弊流量、超时未完成、无有效曝光 | 事后剔除 = 可操纵结论，等于作弊 |
| 曝光口径 | 「分到组」还是「看到新版本」必须选一个，两组用同一个 | 把没看到新版本的人算进实验组，效应被稀释 |
| 护栏指标 | 崩溃率、客诉率、核心功能可用性，**预设阈值 + 触发即停** | 只看正向指标，副作用无人拦 |

## 七、SRM 检验（人数对不上，先别看指标）

抽样比例失衡检验：比较各组**实际人数**与**期望人数**（按设定分流比例），做卡方拟合优度检验。

| 结论 | 判定 | 处置 |
|---|---|---|
| 正常 | p ≥ 0.05 | 继续 |
| 可疑 | 0.001 ≤ p < 0.05 | 暂停结论，排查分流与埋点 |
| **SRM** | **p < 0.001** | **实验作废重跑**：查分流哈希、重定向、去重逻辑、埋点丢失 |

`p < 0.001` 是通行阈值（不是 0.05）。因为分流错误在正常实验里不该发生，正常实验出现 p<0.05 的假阳性并不稀奇；把阈值提到 0.001 可以显著降低误杀。

**SRM 一旦成立，前面所有指标结论全部作废**——不是「数据有点脏」，是两组根本不可比。

## 八、跑多久与什么时候停

**天数算法：**

```
实验所需天数 = ⌈ 每组所需样本量 × 实验组数 ÷ (日流量 × 实验流量比例) ⌉
最少运行天数 = max(该天数, 7)     # 至少覆盖一个完整自然周，含工作日/周末差异
```

**为什么至少 7 天：** 大多数业务都有周内周期（周末流量与转化结构不同）。只跑 3 天，结论里混着的是「周几」而不是「有没有效果」。

**停止规则（必须开跑前定）：**

| 规则 | 做法 |
|---|---|
| 固定样本量 | ✅ 跑到预定样本量（或预定天数）才读结论，这是唯一安全的做法 |
| 逐日看显著就停 | ❌ 这会让假阳性率从 5% 膨胀到 20%–30% |
| 固定天数 + 看 CI 宽度 | ✅ 更好的替代：预定跑 14 天，若第 14 天 CI 仍宽到能同时容纳 -2pp 和 +2pp，则判「数据不足」并说明需要多少样本 |
| 护栏触发 | 崩溃率/客诉超阈值 → **立即停**，不看正向指标 |

「数据不足」必须如实报告成数据不足，不能改写成「有正向趋势」。

## 九、脚本用法

```bash
# 算样本量（相对提升 10%）
python scripts/ab_sample_size.py --p1 0.10 --mde 10 --mde-rel \
    --alpha 0.05 --power 0.8 --arms 2 --daily 100000 --traffic 0.5

# 算样本量（绝对提升 1 个百分点）
python scripts/ab_sample_size.py --p1 0.10 --mde 1 --mde-rel 0.0

# 反解：现在每组 14749 人，能测出多小的提升？
python scripts/ab_sample_size.py --mode mde --p1 0.10 --n-per-arm 14749

# 反解（相对值）
python scripts/ab_sample_size.py --mode mde --p1 0.10 --n-per-arm 14749 --rel

# SRM 检验：两组实际人数 4902 / 5011
python scripts/ab_sample_size.py --mode srm --observed 4902,5011 --ratio 1

# 三组实验 5:5:10
python scripts/ab_sample_size.py --mode srm --observed 4902,5011,9904 --ratio 5,5,10

# 从 JSON 读参数
python scripts/ab_sample_size.py --file plan.json
```

| 参数 | 说明 |
|---|---|
| `--p1` | 基线率（0-1 之间的小数，如 0.10） |
| `--mde` | 最小可检测提升的绝对值或相对百分数 |
| `--mde-rel` | 传 `--mde-rel`（无值）时把 `--mde` 当相对百分数，如 `--mde 10` 表示 10% |
| `--alpha` | 显著性水平，默认 0.05 |
| `--power` | 统计功效，默认 0.8 |
| `--two-sided` / `--one-sided` | 双侧（默认）/ 单侧 |
| `--arms` | 实验组数（含对照组），默认 2 |
| `--ratio` | SRM 模式下的期望分流比例，如 `5,5,10` |
| `--daily` / `--traffic` | 日流量与实验流量占比，用于算天数 |
| `--min-days` | 最少运行天数，默认 7（保证覆盖整周） |
| `--file` | JSON 参数文件 |
| `--out` | 结果输出文件路径 |
| `--selftest` | 跑内置自检（结果写 `scripts/_selftest_result.txt`） |

脚本做的事：① 双样本量公式；② 反解 MDE（二分法）；③ 校验「算出的 n 对应的实际功效」是否真的达到目标 power；④ 算所需天数并向上取整到整周；⑤ SRM 卡方检验；⑥ 对不合理参数（基线率越界、MDE 为 0、流量比例过低）给错误级提示。

## 十、人工确认清单（这步不能省）

- [ ] 主指标是否唯一？辅助指标是否已标注「仅观察，不做决策」
- [ ] 基线率 p1 是**实验前**同口径历史数据吗？口径有没有变过？
- [ ] 分流单位是什么，写进实验文档了吗？同一用户/设备会不会跨组？
- [ ] 剔除规则是**上线前**写死的吗？事后剔除的名单能否追溯？
- [ ] 实验流量比例 × 天数能否真的凑够样本量？不够的话 MDE 是否已提前放宽并告知业务方？
- [ ] 至少覆盖 7 个完整自然日了吗？
- [ ] SRM 检查做了吗？p 值多少？
- [ ] 停止规则是不是「固定样本量」而不是「看到显著就停」？
- [ ] 同时看几个指标？是否需要 Bonferroni 校正（看 k 个指标则 α 需除以 k）？
- [ ] 结论里有没有同时给出**效应量与置信区间**，而不只是 p 值？

## 十一、最常见的坑

**坑一：先上线，样本量以后再说。**
「先跑跑看，有效果就继续」——这不是实验，是拿线上流量做不可控的探索。样本量是**设计输入**，不是**观测结果**。必须开跑前算清。

**坑二：把相对提升当绝对提升塞进公式。**
基线 10% 想提升 10%，是 10% → 11%（绝对 1pp），不是 → 12%（绝对 2pp）。差一倍样本量。

**坑三：按会话分流，按用户看指标。**
同一用户上午在对照组、下午在实验组，两个组的用户高度重叠，指标差被自己的行为抹平，实验永远「不显著」。**分流单元必须和统计单元一致。**

**坑四：跑到显著就停。**
每天 peek 一次，5% 的假阳性率会膨胀到 20%–30%。正确做法是预先定死样本量，跑到才读；或者只看 CI 宽度决定要不要续跑。

**坑五：SRM 不看，直接看指标。**
两组 4902 / 5011 人看着「差不多」，但期望是 1:1，方卡 p 值低于 0.001 就是分流坏了。分组不可比时，任何指标差异都可能是分流偏差造成的。**SRM 不过，指标不看。**

**坑六：事后剔除「异常用户」。**
实验跑了 3 天，看到实验组差就去掉那 2% 异常用户 —— 这是 p-hacking。剔除规则必须上线前写死、且两组用同一条。

**坑七：把「没跑够样本所以不显著」写成「无效果」。**
这两句话结论完全不同。前者是数据不足，需要延长或放宽 MDE；后者是效果已被排除。混淆它们会让团队错误地放弃一个真有效的改动。

**坑八：只看 p 值，不看效应量和置信区间。**
p<0.05 只说明「不太可能纯属偶然」，可能效应量只有 +0.1%，业务上毫无意义。**必须同时报效应量、95% CI 与业务最小有意义提升（MME）。**

**坑九：多个指标不做校正。**
同时看 5 个指标还都用 α=0.05，至少一个「显著」纯属偶然的概率约 23%。主指标之外，其余指标要么预设校正（Bonferroni：α 除以 k），要么只作描述性参考。

**坑十：分流比例不是固定比例。**
「实验组 10%、其余全给对照组」，跑完发现实验组只有 3000 人却已经「显著」——这不是设计，是运气。分流比例必须和样本量规划对齐。

## 十二、边界与免责

- 公式基于**大样本近似的双侧检验**，小样本（每组 n < 30）或极端比例（p < 0.01 或 p > 0.99）建议改用精确检验或贝叶斯方法
- 存在**聚类效应**时（按门店/城市/班级分流，同一簇内用户相关），有效样本量小于名义样本量，需乘以设计效应；本技能不覆盖设计效应估计
- 存在**多重比较**时（一次实验多个变体、多指标），显著性水平需校正，否则假阳性率远超名义 α
- 方差随时间漂移（节假日、大促）时，固定天数估算会偏差，护栏与分时段看数更稳
- 实验平台给出的显著性结论以平台自身实现为准；本技能用于**开跑前的样本量设计与上线后的合理性核查**，不替代平台统计引擎
- 涉及用户数据的部分，实验分组与用户标识处理应遵守本单位的数据合规要求，**以现行规定和主管部门要求为准**
