# 金字塔结构与 SCQA 规则库

> 排结构前先读本文件。**没有顶句的汇报，本质是信息堆。**

---

## 一、金字塔结构图

```
                    ┌─────────────┐
                    │  顶句（结论）│  ← 全文唯一核心观点
                    └──────┬──────┘
            ┌──────────────┼──────────────┐
        ┌───┴───┐      ┌───┴───┐      ┌───┴───┐
        │ 分支1 │      │ 分支2 │      │ 分支3 │  ← 同一层级、同一维度
        └───┬───┘      └───┬───┘      └───┬───┘
          支撑           支撑             支撑    ← 论据与数据
```

---

## 二、四条原则与自检

| # | 原则 | 说明 | 自检方法 |
|---|---|---|---|
| 1 | 结论先行 | 开头就给结论，不从背景讲起 | 遮住第一段，能否看出结论 |
| 2 | 以上统下 | 每一层的意思能概括下一层 | 试着用一个问句概括三个分支 |
| 3 | 归类分组 | 同一层分支必须同维度 | 三个分支能用同一个问句回答吗 |
| 4 | 逻辑递进 | 分支按时间/程度/因果排序 | 打乱顺序后读者会困惑吗 |

---

## 三、顶句的三条标准

```
1. 是一句完整判断，不是话题
2. 能被下层论证（分支支撑不住顶句，说明顶句写错）
3. 包含对方关心的信息（不是自我表达）
```

| ✗ 不是顶句 | ✓ 是顶句 |
|---|---|
| 「关于用户流失的分析」 | 「流失集中在首月未完成引导的用户，建议把引导前置到注册当次」 |
| 「本次汇报三个部分」 | 「建议暂停渠道 B 投放，把预算转到渠道 C」 |
| 「现状与问题」 | 「问题不在需求，在交付节奏」 |

## 四、SCQA 引入模板

```
S 情境（Situation）：大家都认可的事实，一两句带过
C 冲突（Complication）：出现了什么变化，打破了原有判断
Q 问题（Question）：因此需要回答的核心问题
A 答案（Answer）：你的结论，直接接金字塔顶句
```

### 示例

```
S：这个项目的交付节奏一直是每月一个版本，上线后没出过问题。
C：这个月客户临时加了三个需求，我们发现交付周期被压到了原来的一倍。
Q：接不接这批需求？接的话怎么排期才不拖累后续版本？
A：建议接，但把三个需求拆到下两个版本，本版本只做其中最紧急的一个。
   理由有三条……（进入金字塔）
```

**S 不能超过两句。** 情景铺垫长了，读者抓不到冲突。

## 五、分支数量控制

| 数量 | 判定 |
|---|---|
| 1-2 个 | 分支太少，可能是单点论证，确认是否遗漏 |
| 3-5 个 | 合适 |
| 6-7 个 | 偏多，考虑合并或下沉 |
| ≥8 个 | 必须收敛，读者会放弃记忆 |

---

## 六、论点收敛三步法

```
第 1 步  筛：只留与顶句直接相关的，其余下沉为附录
第 2 步  合：同维度的分支合并，控制在 3-5 个
第 3 步  排：按重要性排，不按时间顺序排
```

**常见误区**：把 5 个论点并成 3 个，但合并后的分类标准不统一。**合并前先确认能用同一个问句回答。**

---

## 七、层级一致性检查

| 层级 | 常见错误 |
|---|---|
| 顶层 | 写成了话题（「关于 X 的分析」） |
| 分支层 | 粒度不齐（大类与小项并列） |
| 支撑层 | 跳过了中间层，顶层与底层差两级 |

**处理**：分支粒度不齐时把小的合并进大的；层级跳跃时补中间层。

---

## 八、结构自检清单

- [ ] 顶句是完整判断
- [ ] 结论在第一段
- [ ] 分支能概括成一个问句
- [ ] 分支数 3-5 个
- [ ] 同层粒度一致
- [ ] 每个分支都支撑顶句
- [ ] 顺序有逻辑
- [ ] 论据能支撑论点大小
- [ ] 其余论点已下沉为附录
