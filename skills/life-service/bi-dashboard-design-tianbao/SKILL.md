# BI看板设计与指标口径核查（bi-dashboard-design）

看板不是「大屏装饰」，是**决策链路**。一个看板只有一个问题要回答，
所以指标数量必须有硬上限。

这个技能做三件事：**分层** → **定配额** → **选图型**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出三层指标分层与每层数量上限 | ❌ 代替业务方定义「什么算一次成功转化」 |
| 按数据类型给出图型选型建议 | ❌ 直接决定业务指标定义（须先与指标字典对齐） |
| 检查指标是否缺维度、缺同环比、缺口径版本 | ❌ 保证看板上线后一定被使用 |
| 指出配色/坐标轴/图例的可读性问题 | ❌ 做 BI 工具选型与权限体系设计 |
| 给出看板评审的检查清单 | ❌ 替代数据仓库建模与血缘治理 |

**以下情况必须先做别的：**
- 指标口径本身还没定 → 先做指标字典，再做看板（见「指标字典编写与口径对齐」）
- 底层表还在频繁变更 → 先冻结数据源版本，再设计看板
- 看板受众没定（高管 / 一线运营 / 数据分析师）→ 先定受众，三类受众的层级完全不同

## 二、完整工作流

```
第 1 步  读规则文件 rules/dashboard_layers.md（三层分层、配额、图型选型、配色）
第 2 步  写清一句话：这块看板回答什么问题？给谁看？
         写不出一句话 → 看板必然做散，先拆成多块
第 3 步  把现有指标逐个归入 结果层 / 过程层 / 健康度层
         归不进去的 → 说明它不属于这块看板，挪走
第 4 步  跑配额与完备性校验
         python scripts/dashboard_audit.py --file metrics.csv
         → 输出 超配额/缺维度/图型不匹配/配色不合规 四类分级问题
第 5 步  按「结果层在上、过程层在中、健康度层在下」排版
第 6 步  每个数字必须同时给出：口径链接 + 时间窗 + 数据更新时间 + 同环比
第 7 步  找 2-3 个真实用户做走查：让他们说出「这个看板能回答什么问题」
         答不上来 → 继续砍指标
```

## 三、三层指标分层（看板设计的骨架）

| 层 | 回答的问题 | 典型指标 | 数量上限 | 位置 |
|---|---|---|---|---|
| **结果指标**（Outcome） | 我们做成了吗？ | 收入、订单量、活跃用户、留存率、NPS、GMV | **4–6 个** | 最上方，独立大数字卡 |
| **过程指标**（Driver） | 哪些环节在推动结果？ | 曝光→点击率、加购率、支付成功率、客单价、履约时效 | **6–8 个** | 中部，按业务链路排列 |
| **健康度指标**（Guardrail） | 有没有付出代价？ | 崩溃率、错误率、客诉量、退款率、毛利率、库存周转、消息触达失败率 | **3–5 个** | 最下方，红黄绿状态灯 |

**单屏总数硬上限 12 个**（含所有层）。超过就要拆看板。

**为什么必须有上限**：人眼一次能并行比较的数值块约 5–7 个，超过 9 个后读者会退回逐个扫描，看板就从「一眼看全局」退化成「一张需要解释的图」。宁可拆成两块看板。

## 四、图型选型对照表（数据形态 → 图型）

| 数据形态 | 首选图型 | 不要用 | 理由 |
|---|---|---|---|
| 时间序列（日/周/月趋势） | **折线图** | 柱状图 | 柱状图基线为 0，会放大或掩盖小幅波动 |
| 分类对比（≤8 个类目） | 横向条形图，按值排序 | 饼图 | 条形图长度比角度好比较 |
| 分类对比（>8 个类目） | 排序条形图 + 只显示 Top 10 | 全部铺开 | 超过 8 类无法一眼比较 |
| 占比构成（≤5 个部分） | 堆叠条形图 / 100% 堆叠条 | 饼图（超过 3 块就别用） | 面积与弧度难比较 |
| 占比构成（时间序列上的构成） | 堆叠面积图 | 多条饼图轮播 | 面积可读性优于扇形 |
| 相关关系（两个连续量） | 散点图 | 折线图 | 相关性是二维分布 |
| 漏斗转化 | **漏斗图或横向条形递减** | 折线图 | 需同时看绝对量与递减幅度 |
| 分布（单变量） | 直方图 / 箱线图 | 柱状图 | 柱状图用于离散类目，不是连续分布 |
| 地理分布 | 分级设色地图 + 排序表 | 3D 地球 | 3D 严重扭曲面积感知 |
| 单值 + 目标对比 | 指标数字卡（含进度条/同比） | 仪表盘 | 仪表盘占用面积大、精确度差 |
| 时间 × 分类双维 | 热力图 | 分组柱状图 | 交叉对比更清晰 |

**三条硬规则：**
1. 折线图的纵轴**不强制从 0 开始**（但必须标注断轴），柱状图**必须从 0 开始**。
2. 排序类目图**必须按值排序**，不按字母或编码顺序排。
3. 一张图**只表达一个结论**，需要双轴时先问自己是不是该拆成两张。

## 五、指标维度完备性七要素（缺的数一律不许上板）

任何指标上板前，必须能回答完这七项：

| # | 要素 | 缺了会怎样 |
|---|---|---|
| 1 | **时间窗** | 「日活」是自然日还是滚动 24 小时？跨时区吗？ |
| 2 | **分母口径** | 「转化率」的分母是曝光、访问还是下单？ |
| 3 | **对比基准** | 同比（去年同期）/ 环比（上一周期）/ 无——**必须显式标注** |
| 4 | **维度** | 至少拆到渠道、地区、终端、新老用户中的一个 |
| 5 | **口径版本** | 是否与上期同口径？口径变过的数据不能直接同比 |
| 6 | **数据延迟** | T+1 还是准实时？延迟多少小时？当前是否已跑完？ |
| 7 | **负责人** | 这个数不对时找谁 |

> **维度不是可选项。** 只有一个「总计」的指标没有诊断价值——它告诉你「今天降了」，但不告诉你「哪降了」。至少配一个「趋势 + 一个维度拆分」。

## 六、八大看板常见错误（带识别口径）

| # | 错误 | 识别口径 | 正确做法 |
|---|---|---|---|
| 1 | **把过程指标当结果指标** | 指标是「点击数」「曝光量」这类中间量，却被放在顶部大字区汇报 | 顶部只放结果指标；过程量放链路中部 |
| 2 | **指标无维度** | 只有总计值，没有按任何维度拆分 | 每个指标至少配一个维度拆分视图 |
| 3 | **口径不一致** | 看板数与财务/业务自有报表对不上，且无人能解释差在哪 | 建立指标字典，看板全部引用字典口径 |
| 4 | **同比对象错位** | 用周环比当同比，或用「上周同日」与「上周」混比 | 同比=去年同期同口径；环比=上一个等长周期 |
| 5 | **图表类型与数据形态错配** | 用饼图表示 6 个类目的占比 | 见第四节选型对照表 |
| 6 | **同屏指标过载** | 单屏超过 12 个数字块 | 拆看板，或做「总览页 + 下钻页」两级 |
| 7 | **无数据更新时间** | 看板上没有「数据截至 xx:xx」，用户把半天的数当全天 | 顶部固定显示数据更新时间和延迟口径 |
| 8 | **配色无语义** | 红绿既表示涨跌又表示正常/异常；彩虹色用于无序类目 | 涨跌用红绿且配箭头；异常用固定状态色；无序类目用单色深浅渐变 |

---

## 七、配色与可读性规范

| 用途 | 规范 | 说明 |
|---|---|---|
| 主色 | 单一品牌主色 + 中性灰 | 强调色每屏不超过 2 种 |
| 同比/环比 | 涨绿跌红（国内习惯）或涨红跌绿（海外习惯），**全看板统一并注明** | 必须同时带箭头符号，不能只靠颜色（色觉障碍） |
| 健康度状态 | 绿=正常 / 黄=预警 / 红=异常，固定不变 | 状态色不得挪作他用 |
| 无序类目 | 单色深浅渐变（按值排序后取色阶） | 不用彩虹色（色相间距不均匀，读不出顺序） |
| 有序时间 | 单色由浅到深 | — |
| 对比双组 | 仅两色（对比色 + 中性灰），不用红绿 | 红绿是对立语义，不是分类语义 |
| 背景 | 浅色背景，文字对比度足够 | 深色大屏需降低饱和度防眩光 |
| 图例 | 放在图内靠近数据，或直接在线上标注 | 图例与数据距离过远会强迫来回扫视 |

**禁止**：3D 图表、渐变填充面积、装饰性阴影、超过 7 色的分类配色、把仪表盘当指标卡用。

## 八、脚本用法

```bash
# 校验指标清单（CSV，每行一个指标）
python scripts/dashboard_audit.py --file metrics.csv

# 指定三类文件的阈值
python scripts/dashboard_audit.py --file metrics.csv \
    --max-result 6 --max-driver 8 --max-guard 4 --max-total 12

# 同时校验图型选型
python scripts/dashboard_audit.py --file metrics.csv --check-chart

# 从标准输入读
python scripts/dashboard_audit.py --file - 
```

**CSV 列（表头必填，其余可选）：**

| 列名 | 含义 | 必填 |
|---|---|---|
| `metric` | 指标名 | ✅ |
| `layer` | `outcome` / `driver` / `guardrail` | ✅ |
| `chart` | 计划使用的图型（`line`/`bar`/`hbar`/`pie`/`table`/`number` 等） | 选 `--check-chart` 时必填 |
| `period` | 时间窗描述 | ✅ |
| `denominator` | 分母口径 | ✅ |
| `baseline` | 同比 / 环比 / 无 | ✅ |
| `dimension` | 已拆维度（逗号分隔或多词） | ✅ |
| `version` | 口径版本 | 建议 |
| `latency` | 数据延迟 | 建议 |
| `owner` | 负责人 | 建议 |
| `updated_at` | 数据更新时间标注 | 建议 |
| `color` | 配色语义（`trend`/`status`/`single`/`pair`/`rainbow`） | 选 `--check-color` 时必填 |

脚本输出四类分级问题：
- **错误（ERROR）**：图例缺失、口径为空、同环比未标、跨层混用
- **警示（WARN）**：超配额、指标缺维度、图型不匹配、配色无语义
- **提示（INFO）**：建议补版本号/负责人/更新时间
- **结论**：是否达到可上板标准

## 九、人工确认清单（这步不能省）

- [ ] 这块看板回答的**那一个问题**写下来了吗？受众是谁？
- [ ] 每个指标能回答完七要素吗？特别是分母和对比基准
- [ ] 结果层是不是真的只有结果量（没有点击数、曝光量混进来）？
- [ ] 每个数字都有维度拆分吗？至少拆了一个维度
- [ ] 同环比的对比基准写清了吗？口径版本变过的数据被排除同比了吗？
- [ ] 有没有数据显示「当前是半天的数」？用户知道吗？
- [ ] 口径和财务/业务报表核对过吗？差异能解释到字段级吗？
- [ ] 拿给 2-3 个真实用户走查，他们能说出「这块看板能回答什么问题」吗？
- [ ] 图表的纵轴从 0 开始了吗（柱状图）？断轴标注了吗（折线图）？
- [ ] 涨跌和状态的红绿语义全看板一致，且不只靠颜色传递信息？

## 十、最常见的坑

**坑一：把所有指标都做成顶部大数字。**
点开看板第一屏 12 个 equally 大的数字，没有主次。读者必须逐个扫，等于没有摘要。**结果层 4–6 个，其余下沉分层**。

**坑二：把「曝光量」「点击数」这类过程量当成绩汇报。**
曝光涨了 30%，收入涨了 2% ——这可能是因为流量质量下降。过程指标上升而结果不动，往往是坏消息。只放结果指标会让这类问题被系统性掩盖。

**坑三：指标没有任何维度拆分。**
「日活 100 万，环比 -8%」——哪个渠道跌的？新用户还是老用户？不知道。**只有一个总计的指标没有诊断价值**，看板上必须配一个维度拆分。

**坑四：同比用错对象。**
「本周较上周 +5%」是环比，不是同比；同比是与去年同期同口径比较。**季度同比尤其要对齐到同一季度**（第 2 周 vs 第 6 周也要注意日历周错位）。很多看板的同比是「上个季度」，业务方却当成去年看。

**坑五：口径变过还在同比。**
2025 年把「活跃用户」定义从「登录过」改成「有核心行为」，然后拿 2025 年的新定义去比 2024 年的旧定义，得到一个纯属口径变化的「大涨」。**口径变过的数据必须标注断点，断点两侧不可直接同比。**

**坑六：用饼图表示 6 个类目的占比。**
人眼判断弧度与面积的精度远低于判断长度。类目超过 3 个就该换横向条形图。饼图只能告诉你「哪块最大」，条形图才能告诉你「差多少」。

**坑七：折线图的纵轴强行从 0 开始。**
转化率从 3.0% 到 3.1% 的变化，从 0 起点的图看起来是平的，用户会判定「没变化」而忽略真实波动。**折线可以不从 0 起，但必须标注断轴符号；柱状图则必须从 0 起。** 两者规则相反，别搞混。

**坑八：忘记标数据更新时间。**
用户早上 10 点看昨天的 T+1 报表，当成今天的实时数；或者报表在跑批过程中被查，看到半天的数。**顶部必须固定显示「数据截至 xx:xx，延迟 T+1」。**

**坑九：同一个数在三个页面对不上。**
看板里 GMV 是 1,200 万，业务报表里是 1,150 万，多出来的是含税还是不含税、含退款还是不含。**指标字典是唯一口径来源**，看板不允许自定义口径。

**坑十：配色无语义，红绿混用。**
红色既表示「跌」又表示「异常」，用户看到红色的指标不知道该担心什么。**涨跌用一组色、状态用另一组色、全看板固定并注明含义**，且不能只靠颜色（要配箭头或文字），因为约 8% 的男性有色觉障碍。

## 十一、边界与免责

- 本技能给出的是**通用设计规范与量化阈值**，不同行业（电商、SaaS、游戏、金融）的正常水位不同，具体阈值应结合业务实际校准
- 3 个及以上变量的复杂归因分析不适合放在看板上，应下沉到分析工具或专项报告
- 大屏展示与内部看板不是一回事：大屏是给路过的人看的，必须无交互、零学习成本，通常只放 3–5 个结果指标
- 权限敏感数据（用户级明细、个人信息）在看板上的展示须遵守本单位数据合规要求，**以现行规定和主管部门要求为准**
- 指标口径的最终裁定权在指标字典与业务方，本技能只做设计与核查
