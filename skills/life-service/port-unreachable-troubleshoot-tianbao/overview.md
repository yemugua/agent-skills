# 端口不通与连接失败排查 · 能力概览

## 你会得到什么

一个把「端口不通」拆成两种完全不同故障类型的排查路径——**分错这两者会让整个排查走反方向**。

**第一步的分岔口。** `Connection refused` 是**立即失败**并收到 RST，说明包**已经到达目标机器**，问题在目标侧没有监听该端口（或被主动拒绝）；`Connection timed out` 是**等待后超时**且无任何应答，说明包**没到达目标**或到达后被静默丢弃，问题在防火墙、安全组、ACL。把 refused 当防火墙问题查会白查很久，把 timeout 当服务没启动重启同样白查。这一条是整个技能的地基。

**四层定位**：L1 目标监听（`ss -lntp` 看有没有监听、**绑在哪个地址**）→ L2 本机路由与 DNS → L3 云安全组/网络 ACL → L4 目标机器系统防火墙。refused 直接跳 L1，timeout 从 L3 开始，**不交叉**。

**最高频的坑**：服务只监听 `127.0.0.1`。本机 `curl localhost:8080` 完全正常，一换外部就 refused，而报错信息完全看不出原因——MySQL、PostgreSQL、Redis、MongoDB、Elasticsearch 默认或常见配置都是这样。

**两层过滤的区别**：云安全组在流量到达机器**之前**拦截，表现通常是 timeout；系统防火墙 `DROP` 也是 timeout，`REJECT` 则是 refused。所以**仅从失败现象无法确定是哪一层在拦**，两侧都要查。「只改了系统防火墙忘了安全组」是最常见的原因。

**三类易误判的场景**：连接数超限（偶发 refused 但根因是应用 `max_connections` 打满，或本地端口耗尽报 `cannot assign requested address`）、端口被占（`Address already in use`，注意区分「被别的进程占用」和「同进程多实例属正常」）、隐蔽干扰因素（代理环境变量、DNS 解析到 IPv6、容器未做端口映射）。

## 典型用法

1. 连不上某端口：先 `nc -zv -w 3` 分清 refused 还是 timeout，再按对应层推进。
2. 本机正常外访问不了：查 `ss -lntp` 的监听地址是不是 `127.0.0.1`。
3. nginx 502：优先查**后端端口是否在监听**，不是查网络链路。
4. 云主机端口不通：安全组与系统防火墙两侧都查。
5. 偶发 refused：查 `ss -s` 与应用连接上限，可能是连接数打满而非端口问题。
6. curl 行为异常：先 `env | grep -i proxy`，加 `--noproxy '*'` 复测。

## 边界

- 只做**定位路径规划与现象判读**，不代替现场网络策略变更与端口开放审批
- **在防火墙或安全组新增放行规则属于安全变更**，必须经审批，并先确认服务是否真的需要对外暴露
- 生产环境数据库、中间件、管理后台的端口开放需评估暴露面，**以现行规定和本单位安全要求为准**
- 临时开放端口必须设**明确回收时间与责任人**
- `ping` 不通**不能推出端口不通**——云环境与安全设备常默认禁 ICMP，必须用 `nc`/`telnet` 直接测端口
- 脚本**不发起任何网络连接**，只归拢观测结果；探测他人系统须取得授权，不得对未授权目标扫描
