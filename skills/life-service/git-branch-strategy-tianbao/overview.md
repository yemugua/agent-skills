# Git 分支管理与合并冲突处理 · 能力概览

## 你会得到什么

一个能把「分支策略选型」和「冲突处理」串起来的完整动作清单，而不是几条零散命令。

**策略层面**：按四个硬指标定位——并行维护几个线上版本、多久发一次、有几级发布环境、失败时怎么回滚。四项填完，落到 Trunk-Based / GitHub Flow / GitLab Flow / GitFlow 中的哪一个是确定的，同时列出为什么是这个、以及哪些组合会踩坑（比如小团队日更却用 GitFlow，每次发版要合三处）。

**执行层面**：分支命名硬规则（前缀、字符集、60 字符上限、必须带工单号）、各类型分支的存活上限（feature 3 天、hotfix 1 天、release 14 天）、六类冲突的判定与命令（content / add-add / modify-delete / binary / submodule / merge commit 冲突），以及最容易出错的一组区分：`git checkout --ours` 覆盖整个文件，而 `git merge -X ours` 只在冲突行生效。

**脚本**：`scripts/git_branch_check.py` 读取 `git for-each-ref` 导出的分支清单，推荐策略、逐分支核命名、按领先/落后数算冲突风险等级，输出可直接贴进周报的体检报告，支持 Markdown 与 JSON。

## 典型用法

1. 新团队或新项目定流程：填四个指标，拿到策略与分支构成。
2. 季度清理：导出分支清单跑一遍，一次性拿到「命名不合规 / 已超期 / 高冲突风险」三类清单。
3. 合并炸了：按 `git diff --name-only --diff-filter=U` 拿到清单，判断是一方内容冲突还是树结构冲突，再决定是自己改还是二选一。
4. 长期痛点的根治：`rerere`、`.gitattributes` 统一换行符、生成物不入库、lock 文件设 `merge=binary`。

## 边界

- 只做策略建议与命令指引，**不会替你在仓库里执行 merge / rebase / force push**
- 语义冲突（两边各自改了同一个函数、语法上都能合、跑起来才错）只能人工判断，脚本不参与
- 涉及已推送历史的改写，必须先备份分支再操作
- 数据库迁移、支付与鉴权相关冲突，需模块 owner 评审，不以本技能结论为准
- Git 版本、托管平台的保护分支能力各异，具体开关以现场配置为准
