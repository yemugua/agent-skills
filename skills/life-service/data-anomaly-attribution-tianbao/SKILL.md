# 数据异常归因排查（data-anomaly-attribution）

大盘跌 15%，团队讨论到底是「用户流失了」还是「数据丢了」——
**先查数据，再查业务**。顺序反了会浪费一整天在分析一个本来就错的数据上。

这个技能做三件事：**判真假** → **定形态** → **定顺序拆解**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 用 z-score 与环比同比双阈值判定是否异常 | ❌ 代替业务判断「这个异常重不重要」 |
| 给出波动形态分类与判据 | ❌ 保证定位到的维度就是根因（相关不等于因果） |
| 按固定顺序拆解并给出时间盒 | ❌ 自动给出修复方案 |
| 识别辛普森悖论的三个信号 | ❌ 替代数据质量监控与告警建设 |
| 给出真假异常的甄别清单 | ❌ 处理需要改历史数据或回补的操作（须人工决策） |

**以下情况必须先做别的：**
- 指标本身口径刚变更过 → 先确认口径，再谈异常
- 处在大促/节假日/版本灰度期 → 波动可能是预期内的，要先看活动日历
- 样本量过小（当日量 < 100）→ 统计波动本身就是主要来源

## 二、完整工作流（固定顺序，别跳步）

```
第 1 步  读规则文件 rules/anomaly_rules.md（波动分类、阈值、辛普森信号）
第 2 步  判真假异常（10 分钟内必须完成）
         ① 查数据延迟：今天的数出了吗？出完了吗？
         ② 查埋点：端上上报量 vs 入库量
         ③ 查口径：最近有定义变更或任务修改吗？
         ④ 查回溯：是否在补历史数据 / 重跑任务？
         → 任一项命中 = 假异常，先解决它，再谈业务
第 3 步  判形态（决定要不要查）
         python scripts/anomaly_detect.py --file series.csv --metric dau
         → 输出 z-score、环比、同比、形态判定
第 4 步  按六维顺序拆解（每个维度限时 20 分钟）
         时间 → 渠道 → 地区 → 机型/端 → 版本 → 用户群
         ★ 时间维度永远第一个：如果全时段均匀下跌，是全局问题；
           如果某个时段集中下跌，是任务/时区问题
第 5 步  算贡献度，找到「贡献最大的那一格」
         下降量分解：Δ总量 = Σ(各维度子项变化量)
第 6 步  怀疑辛普森悖论（看第三条，见第七节）
第 7 步  输出结论：真异常 or 假异常 + 定位结果 + 处置建议
```

## 三、波动四分类与判据

| 形态 | 特征 | 量化判据 | 是否要查 |
|---|---|---|---|
| **突增突降** | 单日跳变后回落 | 单日环比 \|变化\| > 历史日环比标准差的 3 倍 | ✅ 立即查 |
| **周期性** | 按固定周期重复 | 周内规律（周末高/低）、月度规律 | ⚠️ 先对齐日历，不算异常 |
| **趋势性** | 连续多期同向 | 连续 ≥5 期同向变化 | ✅ 查趋势性原因（策略/季节） |
| **毛刺** | 单点跳变后立即恢复 | 单点偏离后下一期回归均值 | ⚠️ 多数是数据问题 |

**判定优先用 z-score（对历史窗口的偏离）：**

```
z = (当期值 − 窗口均值) / 窗口标准差
```

| \|z\| | 判定 | 动作 |
|---|---|---|
| < 2 | 正常波动 | 不查 |
| 2 ~ 3 | 值得关注 | 记录但不打断工作 |
| **≥ 3** | **异常** | **触发排查** |

> 注意：日环比的标准误约 `1/√N`（N 为当日量）。当日量 100 时，标准误约 10%——**小流量日的 ±10% 波动完全是正常的**。这是最常见的「假异常」。

## 四、环比 vs 同比（各有用处，不能只用一个）

| 对比 | 公式 | 抗干扰性 | 适用 |
|---|---|---|---|
| **环比（MoM/DoD）** | vs 上一期（昨天/上月） | 差，易受周期影响 | 发现最新变化，响应快 |
| **同比（YoY）** | vs 去年同期 | 好，能抵消周内与季节性 | 判断是否真异常 |

**规则：先看环比发现变化，再用同比判断真假。**

- 环比 -15%、同比 -3% → **大概率是周内效应**（比如昨天是周日）
- 环比 -15%、同比 -15% → **真异常，需要排查**
- 环比 +20%、同比 +2% → 可能是活动或节假日，不一定是好事

**周内对照表（先确认不是周几的问题）：**

| 对比昨天 | 该用 | 说明 |
|---|---|---|
| 周一 vs 周日 | ❌ 错误 | 周末与工作日结构性不同 |
| 周二 vs 周一 | ⚠️ 勉强 | 需考虑周一效应 |
| 周三 vs 周二 | ✅ 较好 | 相对稳定 |
| 任意 vs 上周同一天 | ✅ 同比 | 最适合跨周比较 |

## 五、真假异常甄别清单（排查第一步，限时 10 分钟）

| # | 检查项 | 怎么查 | 假异常特征 |
|---|---|---|---|
| 1 | **数据延迟** | 看任务产出状态与数据截至时间 | 今天的数还没出全 |
| 2 | **埋点丢失** | 端上上报量 vs 入库量对比 | 上报涨、入库跌 = 入库侧问题 |
| 3 | **口径变更** | 查指标字典变更记录与任务修改时间 | 变更有生效时间正好在今天 |
| 4 | **回溯补数** | 查是否在重跑任务、补历史 | 数值出现无法解释的整数或突变 |
| 5 | **小流量日** | 当日量是否 < 100 或远低于平时 | 量小时 ±10% 属正常波动 |
| 6 | **节假日/活动** | 对齐活动日历与大促日程 | 波动方向与活动预期一致 |
| 7 | **外部依赖** | 上游接口/第三方数据是否异常 | 上游中断导致数据缺失 |

**命中任一项 → 先标记为「疑似假异常」，解决后再重新判定。**

> **不要跳过这一步。** 「数据丢了」被当成「用户流失」分析一整天，是数据排查最常见的时间浪费。

## 六、六维拆解顺序（固定，别乱序）

```
第 1 维  时间      全部时段？某时段？某天？
           → 均匀下降 = 全局问题；集中在深夜 = 任务/时区问题
第 2 维  渠道      app/小程序/H5/线下/API
           → 单一渠道跌 = 该渠道技术或策略问题
第 3 维  地区      大区/省市/国家
第 4 维  机型/端   iOS/Android/具体机型/浏览器
           → 单一端跌 = 版本兼容或审核问题
第 5 维  版本      App 版本/接口版本/配置版本
           → 新版本灰度用户跌 = 新版本引入问题
第 6 维  用户群    新老用户/会员等级/生命周期阶段
```

**每维限时 20 分钟**，超时就记为「本维无结论」继续往下，不要在某一维死磕。

**时间维度必须第一个做**，这是最容易漏的。举例：DAU 跌 10%，按渠道拆发现各渠道都跌 10%——这看起来是全局问题，但按时间拆发现「昨天 23:00-24:00 数据是 0」——其实是凌晨任务跑挂了，昨天日数据不完整。**不先看时间就拆渠道，会得出完全错误的结论。**

## 七、贡献度分解与辛普森悖论

### 贡献度分解

```
总量变化 = Σ(各子项变化量)

子项贡献占比 = |该子项变化量| / Σ|所有子项变化量|
```

**按贡献占比排序，优先查贡献最大的那一格。**

| 贡献占比 | 判定 |
|---|---|
| ≥ 50% | 单一原因，重点排查这一格 |
| 20%–50% | 主因之一，需与其他格合看 |
| < 20% | 分散型，无单一主因，查全局因素 |

### 辛普森悖论的三个识别信号

> 每个分组内部都在改善，但总体却在恶化（或反之）。

| # | 信号 | 表现 |
|---|---|---|
| 1 | **方向相反** | 总体下降，但主要细分分组全部上升 |
| 2 | **占比漂移** | 某组数值没变，但该组占比大幅变化 |
| 3 | **加权与简单平均冲突** | 「各组平均值」与「总体数值」方向相反 |

**识别方法：**

```
步骤 1：按一个关键维度拆分，看各子项的绝对值变化
步骤 2：再看各子项的占比变化
步骤 3：绝对值全涨但总体跌 → 一定是占比漂移导致的辛普森悖论
```

**典型例子：**

| 分组 | 上期占比 | 上期数值 | 本期占比 | 本期数值 |
|---|---|---|---|---|
| 高转化渠道 | 20% | 1000 | 10% | 1200（**涨了**） |
| 低转化渠道 | 80% | 1000 | 90% | 800（**跌了**） |
| 总体 | 100% | **2000** | 100% | **2000**（持平） |

**说清楚：每个渠道的用户数都在变化，变化方向还不一样。这种情况下讨论「总体涨了还是跌了」几乎没有意义，必须分开看。**

## 八、毛刺与假异常的区别

| 类型 | 特征 | 常见原因 | 处置 |
|---|---|---|---|
| **数据毛刺** | 单点跳变，下一期立刻回归 | 任务失败重跑、补数、口径临时改动 | 查任务日志，通常可解释 |
| **业务毛刺** | 单点跳变，下一期回归但方向与预期相反 | 突发的活动、推送、舆情 | 查业务事件日历 |
| **口径毛刺** | 跳变后长期维持在新水平 | 口径变更 | 查指标字典变更记录 |

**判定口诀：跳完就回来的是毛刺，跳完不回来的是口径变更或趋势。**

## 九、脚本用法

```bash
# 基本异常判定
python scripts/anomaly_detect.py --file series.csv --metric dau

# 指定对比基准（同比/环比）
python scripts/anomaly_detect.py --file series.csv --metric dau --compare yoy

# 贡献度拆解
python scripts/anomaly_detect.py --file series.csv --metric dau \
    --dims "channel:app,mini,h5" "region:east,south,north"

# 假异常信号检查
python scripts/anomaly_detect.py --file series.csv --metric dau \
    --check-data-quality --delay-hours 2 --volume-threshold 100
```

**CSV 格式（`date` 与 `metric` 列必填）：**

| 列名 | 含义 |
|---|---|
| `date` | 日期（YYYY-MM-DD） |
| `metric` | 该日的指标值 |
| `dim_*` | 可选的维度列（如 `dim_channel`） |

脚本输出：均值/标准差/z-score、环比、同比、波动形态判定、异常等级，以及贡献度拆解与假异常信号检查结果。

## 十一、最常见的坑

**坑一：不查数据延迟就开始分析业务。**
今天跑了 8 小时的数据，跌了 15%，团队讨论「用户为什么流失」。实际上今天的任务 23 点才跑完。这就是**假异常**，而排查顺序把它放在第一位就是为了防这个。

**坑二：周一和周日比。**
DAU 周一通常比周日低 20%，这是结构性差异不是异常。**跨周比较必须用「上周同一天」（同比）**。

**坑三：小流量日用 ±10% 当异常。**
当日量 100 时，标准误约 10%，波动 ±20% 都可能纯属随机。**小流量日的正常波动必须靠 z-score 判断，不能靠肉眼。**

**坑四：只拆渠道不拆时间。**
各渠道均匀下跌，看起来是全局问题。但按时间拆发现「23:00 后数据为 0」——其实是凌晨任务挂了。**时间维度永远第一个。**

**坑五：辛普森悖论看不出来。**
总体下跌，各细分渠道全部上涨——因为高转化渠道的流量占比从 20% 掉到 10%。只看总体会得出「业务全面恶化」的错误结论。**必须同时看子项的绝对值和占比。**

**坑六：口径变更当成业务波动。**
「活跃用户」定义改了，数值阶跃上去了。跳完不回来就是口径变更，**查指标字典变更记录**。

**坑七：z-score 窗口取错了。**
用近 7 天算标准差，但这 7 天里正好有个大促，方差被拉大，真异常就被稀释了。**窗口应取「同星期几」的历史数据**，或剔除已知的异常期。

**坑八：只看绝对量不看占比。**
某渠道流量从 100 万降到 10 万，绝对量看是暴跌，但占比从 2% 变 0.2%，可能是主动下线了该渠道。**绝对量与占比要一起看。**

**坑九：把环比异常当同比结论汇报。**
环比 -15% 同比 -3%，说明只是周内效应。汇报时说「跌了 15%」会引发不必要的业务讨论。**环比用来发现变化，同比用来判断真假。**

**坑十：找到相关维度就当根因。**
按机型拆发现 iOS 跌了 20%，于是认定「iOS 有 bug」。但 iOS 版本 5.2 恰好在昨天灰度 50%——是灰度问题不是 bug。**定位到维度不等于找到根因，还要看时间与版本的对应关系。**

**坑十一：一次性拆六个维度，没有优先级。**
六个维度全拆需要几个小时，容易在错误的方向上耗尽时间。**按「时间→渠道→地区→机型→版本→用户群」固定顺序，每个限时 20 分钟。**

## 十二、边界与免责

- z-score 判定依赖历史窗口的稳定性；窗口内若含大促或异常期，方差被拉大会**低估**异常
- 贡献度分解是**描述性**的，找到「贡献最大的维度」不等于找到根因，根因需要结合业务事件与技术变更验证
- 辛普森悖论的识别依赖于维度划分的选择，换一个维度可能看不出同样的现象
- 涉及回溯补数、改历史数据、重跑任务的操作会**影响已产出报表**，须经人工确认并留痕，本技能不代为执行
- 数据缺失、埋点合规与用户数据使用须遵守本单位要求，**以现行规定和主管部门要求为准**
