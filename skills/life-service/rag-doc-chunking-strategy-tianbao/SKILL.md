# RAG文档切分策略与召回核查（rag-doc-chunking-strategy）

RAG 效果差，**七成问题出在切分，不在模型**。
切分错了，再贵的 embedding 模型也检索不到那一段。

排错的第一个问题永远是：**入库的东西本身完整吗？**
——很多「召回率低」其实是入库时表格丢了、代码块被截断了。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出四类切分策略的适用场景与取舍 | ❌ 保证按建议参数切完召回率就达标 |
| 给出 chunk size 与 overlap 的取值区间 | ❌ 替代真实业务文档上的召回率评测 |
| 给出表格/代码块/列表的切分处理方法 | ❌ 直接修改生产环境的切分与索引配置 |
| 给出入库完整性与切分质量的校验方法 | ❌ 决定 embedding 模型与向量库选型 |
| 给出召回下降的五步排查顺序 | ❌ 直接给出召回率与精确率的最优平衡点 |

**以下情况必须先做别的：**
- 文档本身没清洗（扫描件无文本层、乱码、页眉页脚混进正文） → 先清洗
- 还没做**切分前后的召回率基线评测** → 先建评测集，否则改参数无从判断好坏
- 文档是长表格或多级标题的制度文件 → 必须按结构切，不能用固定长度

## 二、完整工作流

```
第 1 步  读规则文件 rules/chunking_rules.md（策略对照表、参数区间、排查顺序）
第 2 步  建评测基线（最关键，不能跳过）
         挑 20-50 个真实问题，人工标出「标准答案在哪一段」
         跑基线：切分参数任意，先测出当前召回率
         ★ 没有基线，后面所有调参都是盲调
第 3 步  查入库完整性（不是召回问题，是数据问题）
         python scripts/chunk_params.py --file docs.txt --stats
         → 检查是否有超长未切块、空块、乱码、页眉页脚残留
第 4 步  选切分策略
         结构化文档（制度/手册/带标题）→ 按结构切
         长叙述文本（报告/论文/对话）→ 语义切分或固定长度
         超长文档需要兼顾精度 → 父子块
第 5 步  定参数
         python scripts/chunk_params.py --size 400 --overlap 15 --unit char
         → 输出 token 估算、预计块数、重叠率是否合法
第 6 步  改完重跑评测集，对比基线
         召回率提升 <2pp → 说明该参数不是瓶颈，别再纠结
第 7 步  召回仍不达标时，按五步顺序排查（见第七节）
```

## 三、四类切分策略对照表

| 策略 | 做法 | 适用文档 | 优点 | 缺点 |
|---|---|---|---|---|
| **固定长度** | 按字符/token 数硬切 | 长叙述文本：报告、论文、对话记录 | 简单、块大小均匀 | 破坏语义完整性，答案跨块时被切碎 |
| **按结构** | 按标题层级/段落/条目切 | 制度、手册、技术文档、FAQ | 保留语义边界，块大小自然对齐章节 | 依赖文档结构规整，结构缺失时退化 |
| **语义** | 按相邻句向量相似度的「断点」切 | 无结构的长文本、连贯叙述 | 语义完整，块大小不均 | 成本高，块大小不可控 |
| **父子块** | 小块检索、大块喂给模型 | 超长文档、需要在上下文中回答 | 兼顾检索精度与上下文完整 | 实现复杂度最高，需要维护父子索引 |

**选择顺序：**
```
文档有清晰结构 → 按结构切（首选）
无结构的长叙述 → 语义切分（预算充足）或固定长度（预算有限）
既要精度又要上下文 → 父子块
```

> **最常见的错误：用固定长度切结构化文档。** 一份 40 页的制度文件按 500 字硬切，会把「第三章 保修期条款」切成三块分别落在三个 chunk 里，检索到其中一块时上下文是残缺的。

## 四、chunk size 与 overlap 取值经验区间

### 按文档类型分档

| 文档类型 | chunk size（中文） | token 估算 | overlap | 说明 |
|---|---|---|---|---|
| FAQ / 短问答 | 150–300 字 | 200–400 | 10% | 一个问答完整落在一块 |
| 制度 / 手册（按结构） | 300–600 字 | 400–800 | 15%–20% | 对齐章节，含上下文 |
| 技术文档 / API 文档 | 400–800 字 | 550–1100 | 15% | 代码块单独处理 |
| 论文 / 报告（长叙述） | 600–1000 字 | 800–1400 | 10%–15% | 太大容易稀释主题 |
| 对话记录 | 200–400 字 | 280–560 | 20% | 按轮次切，不用硬切 |

### token 估算（中文）

```
中文：1 字 ≈ 0.7–1.2 token（保守按 1 字 ≈ 1 token 估）
英文：1 词 ≈ 1.3 token
混合文档：按中文占比加权估算
```

> **务必按 token 而不是字符设定。** 很多 embedding 模型的上下文上限是 512 或 8192 token，按字符设 500 实际可能超出模型限制。

### overlap 的作用与取值

```
overlap 作用：避免答案恰好落在切分边界上被切成两半
推荐区间：  chunk size 的 10%–20%
超过 25%   ：存储成本上升明显，收益递减
低于 5%    ：边界问题仍会出现
```

**用一段具体例子说明 overlap 的必要性：**

```
原始文本：……保修期为一年（cut）……
不切重：  [A: 保修期为一年] [B: 。……]
切重叠：  [A: 保修期为一年] [B: 一年（cut）……]
                    ↑ 边界处的「一年」在两块里都有
```

**一条反直觉的经验**：如果答案总是「差一点点」，多半是边界切开了句子。加大 overlap 到 20% 通常能解决，但更好的做法是**改成按段落/句子边界切**，而不是无限加大 overlap。

## 五、表格与代码块的特殊处理

| 内容类型 | 错误做法 | 正确做法 |
|---|---|---|
| **表格** | 按字符硬切，表头和数据行分离 | 表格**整体作为一个 chunk**，或「表头 + 若干数据行」，**每块都要带表头** |
| **代码** | 按字符硬切，函数被截断 | 按函数/类边界切；至少保证括号配对完整 |
| **公式** | 与正文混在一起 | 独立成块，保留 LaTeX 原文（不要转成纯文本） |
| **多级标题** | 只带一级标题 | 保留完整的标题路径（如「第三章 > 3.2 保修期」） |
| **列表** | 与上下文混排 | 列表整体成块，保留列表符号 |
| **页眉页脚** | 混进正文 | **清洗时删除**，页码、文档名、版权声明 |

**表格处理最重要的一条：每个数据块都要重复表头。**

```
❌ chunk1: | 地区 | 销售额 |     chunk2: | 北京 | 100 |  ← 缺表头，无法解读
✅ chunk1: | 地区 | 销售额 |     chunk2: | 地区 | 销售额 |
           | 北京 | 100    |                 | 北京 | 100    |
```

**否则 embedding 无法理解第二块讲的是什么**，检索到了也答不对。

## 六、切分质量的四个校验项

在讨论召回率之前，先确认这四项：

| 校验项 | 怎么查 | 合格标准 |
|---|---|---|
| **入库完整性** | 原文总字数 vs 所有 chunk 总字数 | 差异 < 1%（超出部分应为被删除的页眉页脚） |
| **块大小分布** | 统计 chunk 字数的最大/最小/均值 | 无长度超过上限 1.5 倍的块；无大量 < 50 字的碎块 |
| **重叠有效性** | 相邻块重叠率 | 在 10%–20% 区间；为 0 则有边界丢失风险 |
| **结构完整性** | 检查标题路径、表格表头是否齐全 | 每块的标题路径完整；表格块含表头 |

**先做完这四项再谈召回率。** 入库不完整时，召回率低是必然结果，调参数没用。

## 七、召回下降的五步排查顺序

```
第 1 步  入库完整性
         原文与 chunk 总字数对不对得上？有没有整块丢失？
第 2 步  切分参数
         最近的 chunk size / overlap 有没有改过？对比变更前后的值
第 3 步  检索参数
         top_k 是不是太小？相似度阈值是不是调高了？查询改写有没有变？
第 4 步  embedding 一致性
         索引用的 embedding 模型和查询用的模型是同一个吗？
         ★ 模型换了但索引没重建，是最隐蔽的召回崩塌原因
第 5 步  数据更新
         文档更新后有没有同步更新索引？旧 chunk 是否残留？
         （有残留时，检索会命中已删除的旧内容）
```

> **第 4 步是最容易被忽略的。** 换了 embedding 模型但没重建向量索引，新查询向量与旧索引向量不在同一个空间，相似度全部失真，召回率会断崖式下跌。**换模型必须重建全量索引。**

## 八、召回率与精确率权衡的三个杠杆

| 杠杆 | 调大的效果 | 代价 |
|---|---|---|
| **top_k** | 召回率↑（更多候选进入上下文） | 精确率↓（噪声进入上下文，答案被干扰） |
| **overlap** | 边界召回率↑ | 存储↑，索引中重复内容↑ |
| **chunk size** | 小块→精确率↑ | 上下文不完整→回答需要跨块推理→效果反而↓ |

**三个杠杆的通用调整方向：**

```
召回不足（该找到的没找到）
  → 先加大 chunk size（提供更多上下文）
  → 再加大 top_k
  → 最后加大 overlap 到 20%

精确率不足（找到的太多太杂）
  → 先减小 top_k
  → 再减小 chunk size
  → 最后加相似度阈值过滤

答案不完整（找到了但不完整）
  → 用父子块：检索用小块，喂给模型用大块
```

> **注意：`top_k` 越大不一定越好。** 检索到 10 个 chunk 塞进上下文，模型会被噪声干扰，甚至答非所问。**先检索出候选，重排（rerank）后再取 top 3-5 条**，通常比直接加大 top_k 效果更好。

## 九、脚本用法

```bash
# 参数计算与校验
python scripts/chunk_params.py --size 400 --overlap 15 --unit char

# 用中文 token 估算
python scripts/chunk_params.py --size 500 --overlap 20 --unit char --ratio 0.7

# 检查切分结果（文档 + 切分后的块）
python scripts/chunk_params.py --file docs.txt --stats

# 校验重叠率
python scripts/chunk_params.py --size 400 --overlap 15 --unit char --validate
```

| 参数 | 说明 |
|---|---|
| `--size` | chunk size（单位由 `--unit` 决定） |
| `--overlap` | 重叠长度 |
| `--unit` | `char`（字符）或 `token` |
| `--ratio` | 字符数转 token 的比例，默认 0.7 |
| `--file` | 文本文件，用于统计切分结果 |
| `--stats` | 输出块大小分布与入库完整性统计 |
| `--validate` | 校验重叠率是否在 10%–20% 区间 |
| `--selftest` | 跑内置自检 |

脚本输出：token 估算、预计块数、重叠率校验结果与切分问题分级提示。

## 十一、最常见的坑

**坑一：没建基线就开始调参。**
凭感觉把 chunk size 从 500 调到 800，感觉「好像好点了」，但没有数据支撑，改了三轮不知道哪一轮有效。**必须先有评测集和基线。**

**坑二：固定长度切结构化文档。**
40 页制度文件按 500 字硬切，一个条款被切成三块分散在不同 chunk。**有结构的文档必须按结构切。**

**坑三：表格按字符硬切，表头和数据分离。**
第二块只有数据没有表头，embedding 完全不理解它在说什么，检索到了也答不对。**每块都要带表头。**

**坑四：换 embedding 模型不重建索引。**
最隐蔽也最致命的坑。新查询向量与旧索引向量不在同一空间，召回率断崖式下跌，团队会花一周排查切分参数——问题根本不在切分。**换模型必须重建全量索引。**

**坑五：overlap 设为 0。**
答案恰好落在切分边界上时被切成两半，两块都不完整。**overlap 至少 10%**，但更好的做法是按句子边界切而不是靠 overlap 补救。

**坑六：chunk 太小导致上下文缺失。**
切成 100 字，问「保修期是多久」，检索到的块里只有「保修期为」，答案是「一年」在下一块。**小块让检索精确率上升，但回答质量下降**。要么加大 chunk，要么用父子块。

**坑七：无限加大 top_k。**
把 20 个 chunk 塞进上下文，模型被噪声干扰，开始答非所问。**先 rerank 再取 top 3-5**，通常比直接加大 top_k 效果好。

**坑八：入库不完整却一直在调参数。**
扫描件没有文本层，部分内容根本没入库，召回率当然上不去。**调参前先查入库完整性。**

**坑九：页眉页脚混进正文。**
每块都带着「XX公司内部资料 第 3 页」，占用上下文并稀释主题向量。**清洗时必须删除。**

**坑十：文档更新后索引没同步。**
旧内容仍在索引里，被检索到后给出过期答案；或者新旧内容冲突，模型看到矛盾信息。**文档更新必须同步更新索引并清理旧 chunk。**

**坑十一：只优化召回率，忘了精确率。**
召回率从 60% 提到 90%，但 top_k=15 塞进上下文，答案质量反而下降。**两个指标必须一起看。**

**坑十二：用字符而不是 token 设 chunk size。**
按 500 字设定，但模型上下文上限是 512 token，实际超限被截断。**必须按 token 设。**

## 十二、边界与免责

- 所有 chunk size 与 overlap 数值均为**经验区间**，实际最优值必须在自己的评测集上验证
- 文档的预处理质量（OCR 准确率、清洗彻底程度）对效果的影响可能大于切分策略本身
- embedding 模型、向量库、重排模型的选型与调优超出本技能范围
- 本技能处理的是**检索前的切分与检索参数**，提示词工程与生成约束属于另一环节
- 涉及企业内部文档入库，须遵守本单位的数据权限与保密要求，**以现行规定和主管部门要求为准**
