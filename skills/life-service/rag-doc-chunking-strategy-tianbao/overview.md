# RAG文档切分策略与召回核查 · 能力概览

## 你会得到什么

**四类切分策略的取舍表，以及选型顺序。** 结构化文档按结构切、长叙述用语义或固定长度、要兼顾精度与上下文用父子块。最常见的错误是**用固定长度切结构化文档**——40 页制度文件按 500 字硬切，一个条款会散落在三个 chunk 里。

**按文档类型分档的参数区间。** FAQ 150–300 字、制度手册 300–600 字、API 文档 400–800 字、论文报告 600–1000 字，overlap 一律 10%–20%。并强调**必须按 token 而不是字符设 chunk size**，否则会悄悄超出模型上下文上限。

**表格处理的唯一硬规则：每个数据块都要重复表头。** 缺表头的块 embedding 根本不理解在讲什么，检索到了也答不对。代码按函数边界切、公式保留 LaTeX、多级标题保留完整路径、页眉页脚清洗时删除。

**召回下降的五步排查顺序**，每步都带原因。第 4 步最隐蔽也最致命：**换 embedding 模型不重建索引**，新查询向量与旧索引不在同一空间，召回率断崖式下跌，团队却花一周调切分参数——问题根本不在那里。

**切分质量四项校验，建议在谈召回率之前做完。** 入库完整性（原文 vs chunk 总字数，差异 <1%）、块大小分布、重叠有效性、结构完整性。入库不完整时召回率低是必然结果，调参数没用。

**三个权衡杠杆的调整方向。** 召回不足→先加大 chunk size 再加 top_k；精确率不足→先减 top_k；答案不完整→父子块。特别提醒 **top_k 越大不一定越好**，塞 20 条噪声进上下文会让模型答非所问，先 rerank 取 top 3–5 通常更好。

## 典型用法

1. 新建知识库：先建 20–50 题评测集和基线，再按文档类型选策略和参数。
2. 「召回率上不去」：按五步排查，第一步就是查入库完整性。
3. 「表格答不对」：检查每个数据块是否带表头。
4. 「答非所问但检索结果看着挺对」：很可能是 top_k 过大导致噪声干扰，试 rerank 取 top 3–5。

## 边界

- 所有 chunk size 与 overlap 均为**经验区间**，最优值须在自己的评测集上验证
- 预处理质量（OCR、清洗）的影响可能大于切分策略本身
- embedding 模型、向量库、重排模型的选型与调优超出本技能范围
- 本技能处理检索前的切分与检索参数，提示词工程与生成约束属另一环节
- 企业文档入库须遵守本单位数据权限与保密要求，以现行规定和主管部门要求为准
