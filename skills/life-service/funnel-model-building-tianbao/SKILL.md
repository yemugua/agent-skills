# 漏斗模型搭建与转化率核查（funnel-model-building）

漏斗分析唯一的难点不是画图，是**口径**。
同一个漏斗，口径不同能算出差一倍的转化率；漏斗图本身几乎不带信息。

这个技能做三件事：**定口径** → **算转化率** → **定位流失**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出漏斗四要素的完整定义模板 | ❌ 代替业务方定义「什么算一次有效转化」 |
| 计算相邻转化率/总体转化率并说明各自用途 | ❌ 保证漏斗各步人数严格递减（真实数据常不递减） |
| 用流失贡献度排序定位优先优化节点 | ❌ 保证优化该节点一定能提升整体转化 |
| 检查跨端/跨天/去重/归因四类口径陷阱 | ❌ 直接给出产品改版方案 |
| 给出漏斗与 A/B 实验配合使用的口径 | ❌ 用漏斗替代因果推断（漏斗只能描述，不能证明） |

**以下情况必须先做别的：**
- 各步转化时间跨度差异极大（注册到下单 30 天）→ 必须先统一时窗，否则各步口径不可比
- 一个用户会多次进入某一步（如多次加购）→ 必须先定去重口径，否则分母膨胀
- 想回答「为什么下降」→ 漏斗只能告诉你**在哪**掉，**为什么**要去维度下钻或做实验

## 二、完整工作流

```
第 1 步  读规则文件 rules/funnel_definition.md（四要素、两类转化率、口径陷阱）
第 2 步  写清漏斗四要素（缺一项就不能开始）：
         ① 步骤集合与顺序  ② 时窗（各步是否共用一个时间窗）
         ③ 去重单位（用户/设备/订单/会话）  ④ 归因方式（严格顺序/任意顺序/末次）
第 3 步  算转化率（脚本一次给全）
         python scripts/funnel_audit.py --file funnel.csv
         → 输出 相邻转化率 / 总体转化率 / 每步流失率 / 流失贡献度占比 / 分级诊断
第 4 步  按「流失贡献度」排序定位优先处理的节点
         （不是按流失率绝对值排序，见第五节）
第 5 步  在该节点按维度下钻（渠道/端/机型/新老/地区），找出贡献最大的细分
第 6 步  提假设并用 A/B 实验验证——漏斗只是描述性工具，不能证明因果
```

## 三、漏斗四要素（缺一项，数据就不可比）

| 要素 | 必须写清 | 常见错误 |
|---|---|---|
| **① 步骤集合与顺序** | 每步的准确定义（触发事件 + 判定条件），以及是否要求严格顺序 | 把「浏览商品」和「加购」顺序颠倒后照样出漏斗 |
| **② 时窗** | 各步是否共用一个时间窗（如「注册后 7 天内完成」）；跨窗时各步窗口是否等长 | 首步窗口 30 天、末步窗口 1 天，两步人数完全不可比 |
| **③ 去重单位** | 用户 / 设备 / 订单 / 会话，一个周期内按什么去重 | 用事件数当分母，同一用户加购 5 次被算 5 次 |
| **④ 归因方式** | 严格顺序（A→B→C 必须按序）/ 任意顺序（只要都发生）/ 末次归因 | 混用归因方式，漏斗中间某步凭空变小 |

**归因三种模式的取舍：**

| 模式 | 定义 | 适合 | 风险 |
|---|---|---|---|
| 严格顺序 | 必须按 A→B→C 的时间顺序发生 | 真实用户旅程分析（主用） | 会漏掉跨步乱序的真实用户 |
| 任意顺序 | 只要周期内都发生过即可，不看顺序 | 各步独立的行为覆盖率 | 各步人数可能不递减（一人先 B 后 A 也计入） |
| 末次归因 | 只归因到最后一个发生的行为 | 广告/渠道归因 | 不适合流程漏斗 |

## 四、相邻转化率 vs 总体转化率（最容易混的两个数）

```
相邻转化率(step i) = 第 i 步人数 ÷ 第 (i-1) 步人数     ← 衡量这一步本身
总体转化率(末步)   = 第 n 步人数 ÷ 第 1 步人数       ← 衡量整条链路
累计转化率(step i) = 第 i 步人数 ÷ 第 1 步人数       ← 逐步累计到此处
```

| 指标 | 回答的问题 | 用来做什么 | 陷阱 |
|---|---|---|---|
| **相邻转化率** | 「这一步本身做得好不好」 | 定位问题节点、优化某一步 | 基数小的时候波动巨大（如第 4 步只有 50 人，掉 2 个就是 4pp） |
| **总体转化率** | 「整条链路一共成不成」 | 对外汇报、跨链路比较 | 无法定位问题在哪一步 |
| **累计转化率** | 「走到这一步还剩多少」 | 画漏斗图的宽度、做 cohort 比较 | 与相邻转化率混用会导致误判 |

**为什么两个都要给：**
一条「曝光→点击→加购→下单」的漏斗，总体转化率 2%，看起来很差。但拆开看：点击率 8%（正常）、加购率 20%（偏低）、下单率 12.5%（正常）。**问题在加购这一步**，而只看总体转化率会误判成「整条链路都不行」。

> **一句话记法：相邻转化率找病因，总体转化率看疗效。** 定位问题用相邻，汇报结果用总体。

## 五、流失贡献度（定位该优化哪一步的正确方法）

**错误做法**：找流失率最大的那一步去优化。
**正确做法**：按**流失绝对人数**排序，或按**对总体转化率的提升潜力**排序。

```
第 i 步流失人数        = 第 (i-1) 步人数 − 第 i 步人数
流失贡献度占比(step i) = 第 i 步流失人数 ÷ 总流失人数
总体提升潜力(step i)   = 第 i 步流失人数 ÷ 第 1 步人数   ← 若该步流失全部挽回，总体转化率能提升多少
```

**判定阈值：**

| 指标 | 阈值 | 含义 |
|---|---|---|
| 流失人数占比 | **≥ 30%** | 优先处理（贡献了 3 成以上总流失） |
| 流失人数占比 | 10%–30% | 次优先 |
| 流失人数占比 | < 10% | 暂不处理 |
| 总体提升潜力 | ≥ 2pp | 即使只挽回一半也值得做 |

**示例**（曝光 100,000 → 点击 8,000 → 加购 800 → 下单 80）：

| 步骤 | 本步人数 | 相邻转化率 | 流失人数 | 流失贡献度 | 总体提升潜力 |
|---|---|---|---|---|---|
| 曝光 | 100,000 | — | — | — | — |
| 点击 | 8,000 | 8.00% | 92,000 | **92.1%** | 92.0pp |
| 加购 | 800 | 10.00% | 7,200 | 7.2% | 7.2pp |
| 下单 | 80 | 10.00% | 720 | 0.7% | 0.7pp |

> 总流失 = 100,000 − 80 = 99,920；点击一步就占了 92.1%。
>
> 注意「相邻转化率最低」的不是第一步，而是点击和加购并列的 8%/10%；但**流失贡献度**指向第一步。此时要问的不是「怎么提高点击率」——第一步流失 92% 通常意味着**流量本身不精准**（曝光量虚高），而非点击设计有问题。

## 六、四类口径陷阱（数据对不上的根源）

| # | 陷阱 | 表现 | 处置 |
|---|---|---|---|
| 1 | **跨设备/跨端重复计数** | 同一用户手机+PC 各算一次，总人数虚高 | 用统一用户 ID 归并；未登录用户用设备 ID + 账号绑定，且两套口径分别出数 |
| 2 | **跨天归因** | 「今日曝光今日点击」算环比，「今日曝光任意天点击」算总体，两数不一致 | 明确定义归因窗口（如曝光后 7 天内点击才归因），并对窗口内的转化按曝光日回溯归集 |
| 3 | **时窗不等长** | 首步统计 30 天，末步统计 1 天，末步转化率被严重低估 | 各步用同一个时间窗，或按步骤耗时重新设定窗口并显式标注 |
| 4 | **重复行为分母膨胀** | 用加购事件数而非去重用户数当分母 | 所有步骤统一按去重单位统计，重复行为单独看「人均次数」指标 |

**额外两条容易被忽略的：**
- **分子分母的时间归属必须一致**：分子用「发生日」还是「归因到起点的发生日」？两种混用必然对不上。
- **测试流量与爬虫**：未剔除时，某一步的「访问」会被内部流量抬高。剔除规则两组/全漏斗必须一致。

## 七、为什么漏斗人数常常不严格递减

**因为大多数真实漏斗采用「任意顺序」或「跨天归因」口径。** 例如按自然日统计：用户周一加购、周二下单——按周二算，加购人数不包含他；按周一算，下单人数不包含他。各步骤按不同时点取数，人数自然不递减。

**处理方式（三选一，必须在报告里说明用了哪种）：**
1. **严格顺序 + 统一时窗**：人数必然递减，代价是漏掉乱序用户
2. **独立步骤口径**：各步单独统计，人数可能不递减，**此时必须用「非严格递减」漏斗，不能用传统漏斗图**（传统漏斗图宽度按人数画，非递减会视觉上失真）
3. **同一批用户的纵向追踪**：先圈定首步用户集合，再在这批人内追踪后续步骤，人数必然递减

**排查顺序**：先看是不是口径问题（跨天/乱序）→ 再看去重（跨端）→ 最后才怀疑数据丢失。

## 八、漏斗与 A/B 实验的配合

| 用途 | 漏斗 | A/B 实验 |
|---|---|---|
| 回答「在哪一步掉」 | ✅ | ❌ |
| 回答「改这一步有没有用」 | ❌ | ✅ |
| 回答「为什么掉」 | ❌ | ❌（需配合维度下钻） |

**正确配合方式：**
1. 用漏斗**定位**问题节点（相邻转化率最低处）
2. 用维度下钻在该节点**缩小假设范围**（哪个渠道/端/机型掉得最多）
3. 用 A/B 实验**验证**改动效果

**不要用漏斗的前后对比做因果推断**：改版前后转化率从 2.1% 涨到 2.4%，可能来自季节、渠道结构或流量来源变化，而非改版本身。**同期必须保留对照组。**

## 九、脚本用法

```bash
# 最简：步骤名与人数
python scripts/funnel_audit.py --file funnel.csv

# 指定去重单位与时窗（写入报告头部）
python scripts/funnel_audit.py --file funnel.csv \
    --unit user --window "7 days after step 1" --attribution strict

# 检查各步骤人数是否严格递减
python scripts/funnel_audit.py --file funnel.csv --check-monotonic

# 检查时窗与归因口径
python scripts/funnel_audit.py --file funnel.csv --check-definition
```

**CSV 格式（`step` 与 `users` 两列必填）：**

| 列名 | 含义 |
|---|---|
| `step` | 步骤名（如 exposure / click / add_cart / order） |
| `users` | 该步骤的去重人数 |
| `note` | 可选备注 |

脚本输出：相邻转化率、总体转化率、累计转化率、每步流失人数、流失贡献度占比、总体提升潜力，并按 错误/警示/提示 分级诊断（人数非递减、人数超出上一环节、样本量过小导致转化率虚高、口径字段缺失等）。

**小样本警告**：某一步人数 < 100 时，其相邻转化率的单次波动可达数个百分点，脚本会提示该步转化率不稳定，不应作为优化依据。

## 十、人工确认清单（这步不能省）

- [ ] 漏斗四要素（步骤/时窗/去重单位/归因方式）都写下来了吗？
- [ ] 各步时间窗**等长**吗？首步与末步的窗口是否一致？
- [ ] 去重单位是什么？跨端用户是否已归并？未登录用户怎么处理？
- [ ] 分子分母的时间归属是否一致（都是发生日，还是都归因到起点日）？
- [ ] 归因窗口有多长（曝光后 7 天内？）？是否已显式标注？
- [ ] 重复行为（多次加购）是否已按去重单位折叠？
- [ ] 测试流量、爬虫、内部账号是否剔除？漏斗内是否统一剔除？
- [ ] 人数非递减的话，报告里说明了用的是哪种口径吗？
- [ ] 定位优化节点用的是**流失贡献度**还是流失率绝对值？
- [ ] 小基数步骤（<100 人）有没有被当成优化依据？
- [ ] 「这个改动有效」的结论来自 A/B 实验还是漏斗前后对比？

## 十一、最常见的坑

**坑一：相邻转化率与总体转化率混着用。**
「我们的转化率从 3% 提升到 4%」——说的是哪一个？如果是相邻转化率，那是某一步改善；如果是总体，那是整条链路。**报告里每次出现转化率，必须写清是哪一种。**

**坑二：用漏斗找病因，用总体转化率下结论。**
总体转化率低不代表每一步都差。定位必须看相邻转化率：**相邻找病因，总体看疗效**。

**坑三：按流失率最大的一步去优化。**
流失率最大的是第一步（92%），但第一步流失通常来自「流量不精准」而非「第一步设计有问题」。**必须按流失人数/流失贡献度排序**，而不是流失率。

**坑四：时窗不等长却硬算转化率。**
「注册→浏览→加购→下单」里，注册到下单可能跨 30 天，但统计时首步取当日、末步取当日。人是同一个人，却因为跨天被算漏，末步转化率被低估一半。**时窗不等长是漏斗数据最常见的致命错误。**

**坑五：跨端重复计数，总人数虚高。**
用户在 App 和小程序各完成一次浏览，被算成 2 个人，首步人数虚高一倍，整体转化率直接减半。**未登录用户是重灾区**，只有设备 ID 时跨端无法归并，必须说明这个限制。

**坑六：分母用事件数而不是去重人数。**
「加购率 = 加购次数 ÷ 浏览次数」——一个用户加购 3 次就贡献 3 个分子。加购率高不代表用户想买，可能是一个人反复加购又删。

**坑七：用漏斗前后对比证明改版有效。**
改版前后转化率 +14%，但同期双十一预热开始、流量结构也变了。**漏斗是描述性工具，不能证明因果**。要证明必须留对照组。

**坑八：看到人数不递减就认为数据错了。**
采用「任意顺序」或跨天归因口径时，人数不递减是正常现象，不是数据错误。**先查口径，再查数据**，排查顺序不能反。

**坑九：小基数步骤的转化率被当成结论。**
某一步只有 50 人，今天 10 人明天 8 人，转化率从 20% 掉到 16%，团队讨论了一整天。**基数 < 100 的步骤转化率波动极大**，要么扩时间窗，要么合并同类步骤。

**坑十：漏斗只出总数，不出维度。**
漏斗告诉你「下单率 10%」，但哪个渠道的 10%？**每个关键步骤至少按渠道和端拆一次**，否则拿到一个无法行动的结论。

## 十二、边界与免责

- 漏斗是**描述性**分析工具，只能说明「在哪一步掉」，不能解释「为什么掉」，更不能证明因果
- 各步耗时差异大的链路（如注册到首次复购跨 60 天），单一时窗会严重失真，应改用 cohort 分析或按耗时分桶
- 多触点路径的用户（如多次加购、多次进购物车）用严格顺序口径会低估，应另建「行为次数分布」视图辅助
- 涉及用户标识合并的跨端口径，须遵守本单位数据合规要求，**以现行规定和主管部门要求为准**
- 漏斗的步骤定义最终须与业务方确认，本技能给出的是结构与判定口径，不代替业务定义
