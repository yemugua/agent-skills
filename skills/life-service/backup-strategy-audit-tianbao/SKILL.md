# 数据备份策略制定与恢复演练核查（backup-strategy-audit）

备份这件事的核心矛盾是：**备份任务显示成功，和数据真的能恢复，是两件事。** 只做前者，等于没做。

这个技能做三件事：**定策略** → **验有效性** → **核演练**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出 3-2-1 原则的落地核查口径 | ❌ 代替你执行恢复操作 |
| 给出 RPO/RTO 定义与分级建议 | ❌ 承诺「这个 RPO 能做到」 |
| 给出备份有效性校验方法 | ❌ 保证备份一定能恢复 |
| 给出恢复演练方案与验收标准 | ❌ 编造具体法规条款号与标准号 |
| 输出备份审计核查清单 | ❌ 代替内控/合规部门做合规认定 |

**出现以下情况，必须停下来人工处理：**

- 备份任务**连续失败**或最近成功时间超过一个备份周期 → 先修任务，不要继续设计策略
- 备份文件**大小为 0 或骤降** → 极可能是「备份了空气」，必须立即验证内容
- 备份成功但**从未恢复过**（超过演练周期）→ 按「备份不可用」处理，先做一次恢复验证
- 需要在**生产环境**执行恢复演练 → 必须先评估影响，走审批，通常应在同版本测试环境进行
- 涉及**勒索软件防护** → 备份不可与生产共用同一套凭据、同一网络域，否则加密会同步到备份
- 涉及金融、政务、医疗等**强监管场景**的留存期限 → **以现行规定和当地主管部门要求为准**

## 二、3-2-1 原则（含必须补的两个 1 和 0）

| 数字 | 含义 | 落地要求 |
|---|---|---|
| **3** | 至少 3 份副本 | 生产原始数据 + 2 份备份 |
| **2** | 至少 2 种不同介质/存储类型 | 例如「本地磁盘 + 对象存储」，不能是两块同盘阵列 |
| **1** | 至少 1 份异地（offsite） | 不同机房、不同可用区，最好不同城市 |
| **+1** | 至少 1 份**离线或不可变**（immutable） | 防勒索软件：对象存储的保留锁/WORM、离线磁带、光盘 |
| **+0** | **0 个错误**被信任 | 每份备份都必须经过验证 |

**为什么必须补「+1」和「+0」：**

- 原始的 3-2-1 解决的是「介质坏了、设备丢了」，**不解决「数据被加密或被删了」**。勒索软件会同步加密所有有权限访问的副本，包括备份。加不可变副本是当前最有效的防护之一。
- **没有验证的备份，只是占用空间的垃圾。** 3-2-1-1-0 里的「0 个错误」指的就是这一点：没有验证过的备份，等价于 0。

## 三、RPO 与 RTO：定义与区别

| 项 | 定义 | 问的问题 | 通俗说 |
|---|---|---|---|
| **RPO**（恢复点目标） | 能接受**丢失多少数据**（时间跨度） | 灾难后最多能回到多久之前？ | **能丢多少** |
| **RTO**（恢复时间目标） | 能接受**多久恢复**（时间跨度） | 灾难后多久能恢复业务？ | **能等多久** |

**关键区别：**

- RPO 决定**备份频率**（和同步/复制方式）
- RTO 决定**恢复方案**（技术手段、演练要求、备件与人员）
- **RPO 更小 → 备份更频繁 → 成本更高；RTO 更小 → 恢复能力要求更高 → 成本更高**
- 两者必须**分别定、分别验**。备份频率高不代表恢复速度快（可能恢复过程要一天）

**恢复顺序（演练与预案通用）：**

```
1. 数据恢复（按 RPO 取对应时间点）
2. 单系统可用（RTO 计时开始点要定义清楚）
3. 应用层恢复（中间件、队列、缓存）
4. 业务可用（对外服务恢复）
```

> RTO 的计时起点必须提前定义清楚：是「接到告警」还是「确认故障」还是「开始动手」？不定义清楚，同一次演练两次评估能得出完全不同的结论。

## 四、RPO/RTO 分级建议

| 系统/数据分级 | 典型内容 | RPO 建议 | RTO 建议 | 备份方式 |
|---|---|---|---|---|
| **一级（核心交易）** | 订单、支付、账务 | ≤ 5 分钟 | ≤ 1 小时 | 数据库同步复制 + 实时日志归档（归档可回放到任意时间点） |
| **二级（重要业务）** | 客户资料、订单查询、配置 | ≤ 1 小时 | ≤ 4 小时 | 数据库增量同步 + 每日全量 |
| **三级（一般业务）** | 内部系统、报表、日志 | ≤ 24 小时 | ≤ 24 小时 | 每日全量 + 本地保留 |
| **四级（可重建）** | 容器镜像、构建产物、静态资源 | ≤ 7 天 | ≤ 72 小时 | 代码仓库 + 制品库 |
| **日志/审计类** | 操作日志、审计日志 | 按现行规定 | 按现行规定 | 独立存储 + 长期留存，**不得与应用数据同库** |

> **RPO ≤ 5 分钟通常无法靠「定时备份」实现**，必须依赖数据库同步复制或日志归档。定时备份（哪怕每小时）的 RPO 就是一小时。

**分级原则**：先按业务影响定级，再由业务方**书面确认** RPO/RTO——这是技术侧无法单方面决定的。

## 五、备份频率与保留周期阶梯

### 5.1 频率

| 数据分级 | 全量备份 | 增量/日志 |
|---|---|---|
| 一级 | 每日 | 实时（同步复制或日志归档） |
| 二级 | 每日 | 每 15 分钟增量 |
| 三级 | 每周 | 每日增量 |
| 四级 | 每次发布 | — |

### 5.2 保留周期（周/年金字塔）

| 类型 | 保留 | 作用 |
|---|---|---|
| 日备 | 7–14 份 | 覆盖近两周的误操作 |
| 周备 | 4–8 份 | 覆盖一两个月前的事故 |
| 月备 | 6–12 份 | 覆盖跨季度问题 |
| 年备 | 1–3 份 | 覆盖长期数据错误（如误删整年数据） |
| **不可变/离线** | 按现行规定与业务要求 | 防勒索、防内部恶意删除 |

**黄金法则：黄金副本（备份）要像白银货币一样珍贵**——用到它意味着出事了；同时它又像白金一样**难以廉价再生**，所以才值得投入成本保护。

## 六、备份有效性校验：六层方法（核心）

**这是整个技能最重要的部分。备份任务成功 ≠ 数据能恢复。**

| 层 | 方法 | 能发现什么 | 频率 | 执行成本 |
|---|---|---|---|---|
| **L1 任务级** | 备份任务退出码、调度器状态 | 任务根本没跑、跑失败 | 每次 | 极低 |
| **L2 存在级** | 备份文件存在、大小 > 0、时间戳正确 | 备份了空气、路径写错 | 每次 | 极低 |
| **L3 完整性级** | 校验和/哈希比对、归档可解包（`tar -t`、`unzip -t`） | 文件损坏、截断 | 每次 | 低 |
| **L4 逻辑级** | 备份内含数据库逻辑导出且**能导入空库**、表数量与行数合理 | 备份内容不含数据、结构不对 | 每日/每周 | 中 |
| **L5 业务级** | 恢复到测试环境并跑通关键业务流程与数据校验 | 备份不完整、应用起不来 | **每月/每季** | 高 |
| **L6 灾备级** | 异地恢复演练，含灾难场景切换 | 异地链路、凭证、人员流程 | **每半年/每年** | 很高 |

**必须写进方案的两条：**

1. **L1–L4 必须自动化并有告警**；L5–L6 必须有人工参与并留记录。
2. **只要 L1–L4 通过、L5 从未做过，就不能声称备份有效。** 至少要做过一次 L5，才能说「备份可用」。

## 七、静默失败：备份最大的坑

**静默失败 = 备份任务显示成功，但备份内容是错的或不可用的。**

| 静默失败形态 | 典型原因 | 识别方法 |
|---|---|---|
| 备份了 0 字节文件 | 源路径错误、挂载点掉了 | **校验大小阈值**，不只看退出码 |
| 备份内容是上次的结果 | 增量基点错、缓存未刷新 | 比对内容哈希与时间戳 |
| 备份文件被删了但任务成功 | 无权限、无空间、被人删 | 定期抽检存在性 |
| 备份了加密的/损坏的数据 | 源已损坏、备份时源在写 | 恢复验证 + 一致性校验 |
| 只备份了结构没有数据 | 导出参数错误、只导 schema | **验证恢复后行数**，不只看结构 |
| 备份被加密（勒索） | 与生产共用凭据 | 不可变副本 + 凭据隔离 |
| 任务跑了但被磁盘配额截断 | 空间不足 | 监控备份分区剩余空间 |
| 时钟不同步导致时间戳错乱 | NTP 故障 | 先修时钟再核时间戳 |

**识别命令速查：**

```bash
# 1. 任务级：最近一次成功时间与退出码
crontab -l ; systemctl list-timers | grep -i backup
journalctl -u backup --since "-7d" | grep -iE "error|fail|exit code"

# 2. 存在级：文件大小与时间戳
ls -lhtr /backup/ | tail -20
find /backup -type f -size 0 -mtime -7        # 7 天内的 0 字节文件 -> 严重
find /backup -type f -mtime +2 -size +1G      # 超过 2 天未更新的备份

# 3. 完整性级：归档是否可解、校验和是否一致
tar -tf /backup/db_20261010.tar.gz > /dev/null && echo "归档可读"
gzip -t /backup/db_20261010.tar.gz && echo "gzip 完整"
sha256sum -c /backup/checksums.sha256
unzip -t /backup/app_20261010.zip | tail -3

# 4. 逻辑级：导出内容是否能导入空库、行列数是否合理
zcat /backup/db_20261010.sql.gz | head -50
zcat /backup/db_20261010.sql.gz | grep -c "^INSERT" 
# 数据库专用校验（以 MySQL 为例）
mysql -u root -p -e "SELECT table_schema, COUNT(*) FROM information_schema.tables 
  WHERE table_schema='appdb';"

# 5. 抽样恢复（最低成本的有效性验证）
#    每周至少抽 1 份备份恢复到测试环境，跑一次关键表查询

# 6. 静默失败监控：备份分区空间
df -h /backup
du -sh /backup/* | sort -h | tail

# 7. 备份成功率与趋势（应作为核心指标而非只报成功/失败）
#    近 30 天成功率、平均耗时、备份大小变化趋势
```

**备份大小趋势是极强的信号**：连续三天大小变化超过 20%，即使校验和通过，也应当人工确认。

## 八、恢复演练

### 8.1 演练频率建议

| 系统分级 | 演练频率 | 演练层级 | 建议环境 |
|---|---|---|---|
| 一级（核心交易） | **每季度** | L5 + L6 | 同版本测试环境 + 异地恢复 |
| 二级（重要业务） | **每半年** | L5 | 测试环境 |
| 三级（一般业务） | **每年** | L5 | 测试环境 |
| 四级（可重建） | 随发布验证 | L4 | CI/CD 流程内 |

> 具体演练频率**以现行规定、行业规范与本单位要求为准**。上表是实践建议，不是合规结论。

### 8.2 演练方案必须包含的六项

| 项 | 要求 |
|---|---|
| 目标 | 明确验证 RPO/RTO 是否达成，以及验证哪几层有效性 |
| 范围 | 恢复哪些系统、哪些数据量级 |
| 环境 | 同版本测试环境；不得直接在生产上做破坏性恢复验证 |
| 成功标准 | **可量化的**（例：RTO ≤ 60 分钟，关键接口校验通过） |
| 时间点 | 含具体日期与参与人 |
| 失败处理 | 演练失败后 3 个工作日内出改进项 |

### 8.3 演练验收标准

| 检查项 | 通过标准 |
|---|---|
| RPO 达成 | 能恢复到距演练时刻 ≤ 目标 RPO 的时间点 |
| RTO 达成 | 从开始恢复到业务可用 ≤ 目标 RTO |
| 数据完整性 | 关键表行数与备份时点一致（可容忍误差需事先约定） |
| 应用可用 | 应用能正常启动并通过冒烟用例 |
| **流程可用** | **在 RTO 时间内完成了所有步骤**，而不是「知道怎么做但做不完」 |
| 问题闭环 | 演练发现的问题有责任人与期限 |

**最后两项最容易被忽略**：很多团队技术上能恢复，但**实际恢复时间远超 RTO**，因为步骤不熟、缺凭证、缺备件、流程没人走通。演练要练的就是流程。

### 8.4 演练常见失败原因

| 原因 | 现象 |
|---|---|
| 备份没做过恢复 | 恢复时发现备份内容不完整或根本解不开 |
| 凭证没归档 | 到恢复时找不到数据库密码、证书私钥、密钥 |
| 版本不匹配 | 用几个月前的备份恢复到新版本应用，起不来 |
| 依赖清单缺失 | 数据恢复了，但依赖的中间件/配置/密钥找不全 |
| 没人参与 | 演练只由一人执行，人一走流程就断 |
| 时间超预算 | 逐步操作下来实际耗时是 RTO 的 3 倍 |

## 九、备份审计核查清单

### 9.1 策略层

- [ ] 有书面备份策略文档，含范围、频率、保留、责任分工
- [ ] 每类数据明确定级，且 RPO/RTO **经业务方书面确认**
- [ ] 策略覆盖全部关键系统（含容器镜像、配置、密钥、代码仓库）
- [ ] 明确不做备份的清单及原因（如可重建数据）

### 9.2 落实层（3-2-1-1-0）

- [ ] 副本数 ≥ 3
- [ ] 介质/存储类型 ≥ 2，且不是同盘双 RAID
- [ ] 异地副本 ≥ 1，异地位置已书面记录
- [ ] **不可变/离线副本 ≥ 1**
- [ ] 备份凭据与生产凭据**分离**，生产域被入侵无法删除备份

### 9.3 有效性层

- [ ] L1 任务级校验已自动化，失败有告警且**告警能到人**
- [ ] L2 存在级校验：大小阈值 + 时间戳
- [ ] L3 完整性级校验：校验和 + 归档可解
- [ ] L4 逻辑级校验：可导入空库 / 行数合理
- [ ] L5 业务级恢复验证：频率符合要求，**有记录**
- [ ] L6 异地恢复演练：有记录
- [ ] 备份大小趋势有监控与异常阈值

### 9.4 保留层

- [ ] 日/周/月/年备策略已配置
- [ ] 到期清理已配置，不会撑爆存储
- [ ] 保留期限满足现行规定与业务要求

### 9.5 监控层

- [ ] 备份成功率是核心指标而非只看最近一次
- [ ] 备份失败告警有接收人，且演练过「真失败能不能收到」
- [ ] 备份分区容量有告警
- [ ] 备份窗口与业务高峰不冲突（或有降速与限流）

## 十、脚本用法

```bash
python scripts/backup_policy_check.py --file policy.yaml --tier 1
```

| 参数 | 说明 |
|---|---|
| `--file` | 备份策略描述文件，`key=value` 每行一条（见下表） |
| `--tier` | 系统分级 `1`–`4`，决定 RPO/RTO 与频率的合规判定 |
| `--json` / `--out` | JSON 输出 / 写入指定报告文件 |
| `--selftest` | 跑内置自检（≥ 8 条断言） |

**输入文件键名：**

```
copies=3                  # 副本数
media=2                   # 存储类型数
offsite=1                 # 异地副本数
immutable=1               # 不可变/离线副本数
credential_isolated=1    # 备份凭据是否与生产隔离
rpo_minutes=5             # 策略声明的 RPO（分钟）
rto_minutes=60            # 策略声明的 RTO（分钟）
frequency=continuous      # continuous/hourly/daily/weekly
verify_l1=1               # 任务级校验
verify_l2=1               # 存在级校验
verify_l3=1               # 完整性级校验
verify_l4=1               # 逻辑级校验
verify_l5=1               # 业务级恢复验证
verify_l6=1               # 异地恢复演练
last_drill_days=30        # 距上次演练天数
monitoring=1              # 备份失败告警是否到人
trend_monitor=1           # 备份大小趋势监控
```

脚本做四件事：① 按分级核对 RPO/RTO 与频率是否匹配（关键：**声明 RPO ≤ 5 分钟但频率是 daily，直接判不合规**）；② 核 3-2-1-1-0 六要素；③ 核六层有效性校验的覆盖度，并识别「只有 L1–L4 没有 L5」这一最常见的假有效；④ 核演练是否超期。

## 十一、最常见的坑

**坑一：备份任务天天成功，但从没恢复过。**
任务成功只证明「文件被写出来了」，不证明「文件里的东西能用」。**只做备份不做恢复验证，等于没有备份。** 至少要定期做一次 L5 恢复验证。

**坑二：把 3-2-1 当成完整方案。**
原始 3-2-1 解决的是「介质坏了、设备丢了」，不解决「数据被加密或被删了」。备份与生产共用同一套凭据时，勒索软件会把备份一起加密。必须加不可变副本 + 凭据隔离。

**坑三：以为 RPO 是靠备份频率决定的，RTO 也是。**
RPO 决定备份频率，RTO 决定恢复能力。每小时备份的 RPO 就是一小时，靠备份无法达到 5 分钟 RPO——那需要同步复制或日志归档。

**坑四：RTO 写在文档上，从来没验证过。**
很多团队技术上能恢复，但逐步操作下来实际耗时是目标 RTO 的三倍。**演练要练的是流程**，包括找凭证、找备件、找对的人。

**坑五：备份了 0 字节文件也算成功。**
源路径写错、挂载点掉了、磁盘配额截断——退出码都是 0。必须校验大小阈值与时间戳，不能只看任务状态。

**坑六：备份大小变了没人管。**
连续三天大小变化超过 20% 是强信号，即使校验和通过也要人工确认。数据量突然减少往往意味着导出逻辑出了问题。

**坑七：备份告警发到了没人看的邮箱。**
「告警配了」不等于「有人收」。必须定期**演练一次真实失败**，验证告警真的能到人并且有人响应。

**坑八：保留策略没清理，存储满了备份静默失败。**
到期不清理，备份分区写不进去，任务可能仍报成功。这是最典型的静默失败路径。监控要覆盖备份分区空间。

**坑九：只在同机房做了备份。**
机房级故障（火灾、空调故障、误操作配电）会同时带走全部副本。异地副本必须真的在不同物理位置，且**异地副本也要被定期验证过**——没验证过的异地备份等于没有。

**坑十：用生产环境做破坏性恢复演练。**
恢复过程会覆盖数据。除非是专门设计的演练环境，否则应在同版本测试环境进行，生产只做只读验证。

**坑十一：备份了数据但没备份依赖。**
数据库恢复出来了，但应用配置文件、中间件参数、密钥、证书全找不全——业务照样起不来。备份范围必须包含配置与密钥。

**坑十二：把「有备份」当成合规结论对外承诺。**
留存期限、演练频率的具体要求，**以现行规定和当地主管部门要求为准**。内部策略文件不能替代合规认定。

## 十二、边界与免责

- 本技能给出的是**备份策略口径、有效性校验方法与演练方案设计**，不代替现场恢复操作
- RPO/RTO 的具体数值**必须由业务方书面确认**，技术侧无法单方面决定，也**不能承诺一定做得到**
- 留存期限、演练频率的具体要求**以现行规定、行业规范、当地主管部门要求与本单位制度为准**，本技能中的频率与周期是实践建议，**不是合规结论**
- 任何恢复操作，尤其在生产环境，**必须经审批后由授权人员执行**，并事先评估数据覆盖风险
- 涉及勒索软件防护的具体方案，**以安全专业人员的评估与本单位安全制度为准**
- 备份数据可能包含敏感信息，其存储、传输、访问与销毁须遵守现行规定与本单位的数据安全要求
