# 丢包判定规则表与业务影响对照

本文件是 `network-packet-loss-troubleshoot` 的核心资产。**判定丢包落在哪一层、是否需要报障之前，先读本文件，不要凭印象。**

---

## 一、四层定位执行表

| 层 | 区间 | 采集命令 | 样本量 | 通过标准 |
|---|---|---|---|---|
| L0 | 本机协议栈 | `ping -c 100 -i 0.1 127.0.0.1` | 100 | 0% 丢包 |
| L1 | 本机 → 默认网关 | `ping -c 100 -i 0.1 <gw>` | 100 | ≤ 0.5% |
| L2 | → 运营商/公网参照 | `ping -c 100 -i 0.1 223.5.5.5` | 100 | ≤ 0.5% |
| L3 | 跨运营商骨干 | `mtr -r -c 100 -n -b <target>` | ≥ 100 | 首跳丢包处之后无递增 |
| L4 | 目标侧 | `ping -c 100 -i 0.1 <target>` | 100 | ≤ 0.5% |

**铁律：**

1. **L1 不通过，绝不进入 L2。** 本机侧问题在公网侧的表现就是「全丢」
2. **样本量不足 100 的结论不成立。** 1% 在 100 包样本里只有 1 个包
3. **每一层都要单独记录时间戳**，混在一起无法对比
4. **双向都要测**：`mtr <target>` 与对端 `mtr <本机IP>`

## 二、丢包率判定阈值

| 丢包率 | 等级 | 处置时限 | 是否需升级 |
|---|---|---|---|
| 0% | 正常 | — | 否 |
| ≤ 0.5% | 可接受 | 观察 | 否 |
| 0.5–2% | 关注 | 当班内记录并复查 | 否 |
| 2–5% | 告警 | 4 小时内定位 | 是（通知负责人） |
| 5–10% | 严重 | 1 小时内定位 | 是 |
| ≥ 10% | 故障 | 立即处置 | 是（按故障流程） |

**统计显著性参考（100 包样本）：**

| 丢失包数 | 样本 | 表面丢包率 | 可信度 |
|---|---|---|---|
| 1 | 100 | 1.0% | **低，属噪声范围** |
| 3 | 100 | 3.0% | 中，需复测确认 |
| 5 | 100 | 5.0% | 中高，可作为结论 |
| 10 | 100 | 10.0% | 高，确定性问题 |

> 单次 1 包丢失在正常链路上也会出现。**结论需要重复观测支撑**，不是看一次就下判断。

## 三、业务影响对照表

| 业务类型 | 可容忍丢包 | 可容忍抖动 | 说明 |
|---|---|---|---|
| 网页浏览 / 邮件 | 2% | 200ms | TCP 重传可掩盖 |
| 文件传输 / 备份 | 1% | 500ms | 大文件对丢包敏感 |
| 数据库复制 | 0.1% | 50ms | 丢包触发复制补偿 |
| 在线交易 / 支付 | **0** | 20ms | 通常要求专线或 QoS |
| VoIP 语音 | 1% | 30ms | UDP 不重传，1% 已可察觉 |
| 视频会议 | 0.5% | 30ms | 抖动比丢包更影响体验 |
| 游戏联机 | 0.5% | 50ms | 延迟与抖动同样关键 |
| IoT / 遥测 | 5% | 5s | 可容忍，业务价值低 |
| DNS 解析 | 0.1% | 100ms | 失败直接影响可用性 |

**重要区分：**

| 场景 | TCP 丢包的表现 | UDP 丢包的表现 |
|---|---|---|
| 1% 丢包 | 延迟升高，吞吐略降 | 语音可察觉卡顿 |
| 5% 丢包 | 重传占用带宽，吞吐降 30%+ | 明显断续 |
| 10% 丢包 | 吞吐塌陷，连接易超时 | 不可用 |

## 四、分层现象 → 根因完整对照

### 4.1 L1（本机 → 网关）

| 现象 | 根因 | 验证命令 | 处置 |
|---|---|---|---|
| 100% 不通 | 网线/网卡/交换机端口 | `ip -br a`、`ethtool eth0 \| grep -i link` | 换线换口 |
| > 2% 随机 | 线缆质量 | 换线到已知良好口对比 | 换六类线，≤100 米 |
| > 2% 规律 | MTU/Offload | `ethtool -k eth0` | 临时关 GRO/LRO 对比 |
| 网关通外网全丢 | 默认路由错 | `ip route get 8.8.8.8` | 修路由 |
| `RX dropped` 增长 | **应用收包慢**（非链路） | `ethtool -S eth0`、`mpstat -P ALL 1` | 查 GC、绑核、调 ring buffer |
| `RX crc`/`errors` 增长 | 物理层错误 | `ethtool eth0` | 换线、查双工协商 |
| 1–3% 且业务正常 | ICMP 限速 | 对比 TCP 业务 | 通常不处理 |

### 4.2 L2（本段 → 运营商）

| 现象 | 根因 | 处置 |
|---|---|---|
| 出口设备侧丢包 | 本地路由器/防火墙 | 换设备或重启（需审批） |
| 同网段跳数内丢包 | 接入交换机拥塞/环路 | 换端口、拆广播域 |
| 到某公网全丢，到别的正常 | 特定路径问题 | 分别追踪 |
| 与业务量相关 | **上行打满，队列丢包** | `sar -n DEV 1 5` 看 txdrop |
| 高峰期丢包 | 链路不足或共享拥塞 | 报运营商扩容 |

### 4.3 L3（骨干）

| 现象 | 根因 | 结论 |
|---|---|---|
| 首现丢包跳之后丢包率相同或更高 | 丢在该跳或该跳之前 | 定责到该 AS，报运营商 |
| 某跳 100% 丢，后续 0% | 中间节点限速 ICMP | **正常，不报障** |
| 某跳 30%、下一跳 40% | 累加丢包，两跳之间链路 | 双向验证后定责 |
| 双向结果不一致 | 回程路径不同 | 常态，两份都报 |
| TCP 丢包但 ICMP 不丢 | **MTU 黑洞** | `ping -M do -s 1472` 探测 |

### 4.4 L4（目标侧）

| 现象 | 根因 | 验证 |
|---|---|---|
| 到目标全丢，traceroute 走到底 | 目标防火墙/安全组丢 ICMP | 从目标内网反向 ping |
| 到目标丢包，同网段其他 IP 正常 | 目标主机防火墙规则 | 目标本机 ping 网关 |
| 延迟高无丢包 | 目标负载或跨地域链路 | 目标侧性能排查 |
| 仅特定端口丢包 | 服务限流/连接打满 | `ss -s`、服务端日志 |
| 间歇 100% 丢包 | 双上行切换、ARP 震荡 | 交换机 MAC 表与日志 |

## 五、mtr 判读规则

| 字段 | 含义 | 判读 |
|---|---|---|
| `Loss%` | 丢包率 | **看递增处，不看单跳绝对值** |
| `Snt` | 已发包数 | 必须 ≥ 100，否则结论不成立 |
| `Last` | 最近一次延迟 | 单点值，参考意义小 |
| `Avg` | 平均延迟 | 业务体感的主要来源之一 |
| `Best` | 最小延迟 | 反映链路下限 |
| `Wrst` | 最大延迟 | **远大于 Avg = 存在偶发长延迟** |
| `StDev` | 抖动 | **大 = 业务体验差的隐形杀手** |

**三条核心规则：**

1. **看后续跳，不看本跳。** 第 N 跳丢包但第 N+1 跳正常 → 包没在第 N 跳丢，只是它不回 ICMP
2. **丢包率递增处即丢包点。** 0→0→25→25→50：丢在第 4 到第 5 跳之间
3. **双向都要做。** 去程与回程路径通常不同，报障需两份报告

## 六、MTU 探测

```bash
# 从 1500 开始逐步减小，找到临界值
ping -M do -s 1472 -c 5 <target>    # 1472+28=1500
ping -M do -s 1400 -c 5 <target>
ping -M do -s 1300 -c 5 <target>
# 出现 "message too long" 或本地报 Frag needed 即为路径 MTU
ip route get <target> ; cat /sys/class/net/eth0/mtu
```

**判定**：某个大小的包不通、更小的包通 → MTU 黑洞（小包正常所以 ping 看着没事）。
**常见原因**：隧道/VPN 叠加、PPPoE 的 1492、云环境 overlay 封装。
**处置**：调整接口 MTU 或 TCP MSS clamping，**改完必须同条件复测**。

## 七、Wi-Fi 判定标准（放宽）

无线环境丢包率天然高于有线，判定标准应放宽。

| 丢包率 | 判定 |
|---|---|
| ≤ 1% | 可接受 |
| 1–2% | 关注，查信号与信道 |
| 2–5% | 告警，查干扰与 AP |
| > 5% | 严重，考虑加 AP 或改部署 |

| 现象 | 根因 | 命令 |
|---|---|---|
| 特定客户端丢包 | 信号弱/距离远/隔墙 | `iw dev wlan0 link` |
| 全网同时丢包 | AP 或交换机 | 其他 AP 下对比 |
| 白天好晚上差 | 信道干扰 | `iw dev wlan0 survey dump` |
| 吞吐忽高忽低 | 干扰重传 | `iw dev wlan0 station dump` 看 tx retries |

**信道建议**：2.4GHz 用 1/6/11（非重叠三信道）；5GHz 优先 36–48 或 149–161。

## 八、报障取证清单

- [ ] **双向 mtr 报告**，各 ≥ 100 包
- [ ] 每份含**精确到分钟的时间戳**与**测试源 IP**
- [ ] `ping -c 100 <网关>` 完整输出
- [ ] mtr 中**首次丢包跳**及其 AS 号
- [ ] 丢包率具体数值与**持续时长**
- [ ] 是否与业务量相关（同时段带宽、连接数）
- [ ] 复现规律（时段、频率）
- [ ] 本侧设备无异常的证明（交换机无 CRC、无队列丢弃）
- [ ] 已尝试的处置与结果
- [ ] 业务影响量化（影响用户数、失败率）
- [ ] 抓包文件（必要时，注意脱敏与留存合规）

## 九、反误判清单

| 现象 | 常见误判 | 真实原因 | 正确做法 |
|---|---|---|---|
| ping 通 | 网络正常 | 只验证了 ICMP 与三层可达 | 同时验证 TCP 端口、MTU、应用 |
| 中间跳丢包 | 链路故障 | ICMP 限速 | 看后续跳丢包率 |
| 丢包 1% | 有故障 | 统计噪声 | 加大样本、复测 |
| 吞吐下降 | 带宽不足 | 丢包导致重传占带宽 | **先治丢包，升带宽无效** |
| 单向正常 | 网络正常 | 回程丢包 | 双向都测 |
| 大包不通 | 丢包 | MTU 黑洞 | `ping -M do -s` 探测 |
| 改完就好了 | 优化有效 | 未复测/时间巧合 | 同条件复测并留前后对比 |
