# 网络丢包定位与排查路径核查（network-packet-loss-troubleshoot）

丢包排查唯一的正确方法是**分层**：本机 → 网关 → 运营商 → 目标。跳过任何一层直接改配置，等于蒙。

这个技能做两件事：**给出四层执行顺序与每层的判定口径** → **把观测现象映射到具体根因**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出分层执行顺序与判定表 | ❌ 代替你在设备上执行命令或改配置 |
| 判读 ping/mtr/traceroute 输出 | ❌ 承诺「一定是运营商的问题」 |
| 给出丢包率与业务影响的对照 | ❌ 代替运营商报障与工单跟进 |
| 给出取证清单 | ❌ 提供绕过安全设备的丢包隐藏做法 |
| 识别常见诱因 | ❌ 代替网络架构师做链路改造设计 |

**出现以下情况，先停下来人工处理：**

- 网关就开始丢包（第一层就红）→ 先查本机网卡、网线、驱动、CPU 软中断，不要往后猜
- 丢包率 ≥ 10% → 业务基本不可用，按故障处理并立即升级，不要继续逐层排查
- 同一网段多台设备同时丢包 → 疑似交换机/接入设备问题，**先查交换机再查主机**
- 出现 `RX dropped` 持续增长 → 是**应用收包慢于内核缓冲**，属主机侧问题，不是链路问题
- 需要抓包定位 → 抓包会占用 CPU 与磁盘，**生产高峰慎用**，先限速与限时
- 运营商侧问题需报障 → 必须先完成本侧取证（见 §8），否则报障单会被退回

## 二、四层定位法（核心流程）

```
第 0 步  确认丢包是真的：多源验证 + 排除本机因素
         ├ ping 127.0.0.1 100 次   → 本机协议栈正常
         ├ ping 默认网关 100 次    → 第 1 层
         ├ ping 运营商 DNS 100 次   → 第 2 层（出公网）
         └ ping 目标 100 次         → 第 3/4 层
第 1 步  第 1 层：本机到网关
         现象 → 根因表见 §4.1
第 2 步  第 2 层：网关到运营商（跨网段）
         现象 → 根因表见 §4.2
第 3 步  第 3 层：运营商骨干
         现象 → 根因表见 §4.3
第 4 步  第 4 层：目标侧（目标主机/目标网络/目标机房）
         现象 → 根因表见 §4.4
第 5 步  每层都要留下取证：命令、时间、丢包率、结论
第 6 步  按 §8 取证清单决定：自己修 / 换设备 / 报运营商
```

**为什么必须分层**：丢包是**逐跳累加**的。mtr 显示第 7 跳开始丢包、第 8 跳开始正常，说明丢包发生在第 7 跳本身（第 8 跳之后的回复说明包已经过去了，是回程丢）。不回传的中间节点丢包无法直接观测——这就是必须看后续节点的原因。

## 三、丢包率阈值与业务影响

| 丢包率 | 判定 | TCP 表现 | UDP 实时语音/视频 | 业务体感 |
|---|---|---|---|---|
| 0% | 正常 | — | — | — |
| < 0.5% | 可接受 | 基本无感 | 无感 | 正常 |
| 0.5–2% | 关注 | 偶发重传，延迟毛刺 | 可察觉轻微卡顿 | 偶发卡顿 |
| 2–5% | 告警 | 重传明显，吞吐下降 10–30% | 明显卡顿、断续 | 页面加载慢、通话断续 |
| 5–10% | 严重 | 吞吐显著下降，连接易超时 | 严重卡顿 | 业务不可用倾向 |
| ≥ 10% | 故障 | TCP 吞吐塌陷 | 不可用 | 按故障处理 |

**TCP 与 UDP 的差别（必须记住）：**

- **TCP**：丢包会触发重传，表现为**延迟升高 + 吞吐下降**，通常不会「断」，但会「卡」。TCP 的问题常被误认为「带宽不够」，实际是丢包导致重传占了带宽
- **UDP 实时业务**：丢包**不重传**，直接丢帧。1% 丢包在语音上就明显，10% 基本无法通话
- **ICMP（ping）丢包 ≠ 业务丢包**：路由器限速 ICMP 是常见做法，ping 有 5% 丢包但业务正常的情况很普遍

**抖动（jitter）同样致命**：平均延迟 30ms 但波动 ±80ms 的链路，通话体验比稳定 120ms 更差。`mtr` 的 `Loss%` 之外要看 `Avg/Best/Wrst` 三个值。

## 四、各层现象 → 根因对照表

### 4.1 第 1 层：本机 → 默认网关

| 现象 | 可能根因 | 验证命令 | 处置 |
|---|---|---|---|
| ping 网关 100% 不通 | 网线松脱/断、网卡 down、交换机端口故障 | `ip -br a`、`ethtool eth0 \| grep Link` | 换线换口，查交换机端口 |
| 丢包 > 2% 且随机 | 网线质量差（水晶头氧化、超五类以下）、距离超限 | 换线到已知良好端口对比 | 换六类线，控制在 100 米内 |
| 丢包 > 2% 且**规律性** | 与网卡 MTU/Offload 有关 | `ethtool -k eth0` | 临时关 GRO/LRO 对比测试 |
| 网关通但外网全丢 | 默认路由错误、路由表异常 | `ip route get 8.8.8.8` | 修路由 |
| 网卡 `RX dropped` 增长 | **应用收包慢于内核缓冲**（CPU/GC/软中断） | `ethtool -S eth0`、`mpstat -P ALL 1` | 查应用 GC、绑核、调 ring buffer |
| 网卡 `errors`/`crc` 增长 | 物理层错误：线缆/接头/双工协商 | `ethtool eth0` | 换线、查双工 |
| ping 网关丢包 1–3%，业务正常 | ICMP 限速 | 对比 TCP 业务是否正常 | 通常无需处理 |

### 4.2 第 2 层：本段网关 → 运营商网关

| 现象 | 可能根因 | 验证 | 处置 |
|---|---|---|---|
| 到运营商 DNS 丢包，到网关正常 | 本地出口设备（路由器/防火墙）问题 | 在出口设备上自查 | 换设备/重启（需审批） |
| 到运营商 DNS 丢包，跳数在同网段内 | 接入交换机拥塞、环路 | 查交换机端口流量与告警 | 换端口、拆分广播域 |
| 到公网全丢，到运营商 IP 通 | 运营商出口或 NAT 设备 | 换目标 IP 对比 | 报运营商 |
| 丢包与业务量相关 | 上行带宽打满 → 队列丢包 | `sar -n DEV 1 5` 看 `txdrop` | 升带宽或限速 |
| 丢包与时段相关（高峰期） | 链路带宽不足或共享链路拥塞 | 对比不同时段 | 报运营商扩容 |
| 到运营商 DNS 丢包但到别的公网正常 | 单一 IP 路径问题 | 换多个目标 IP | 分别追踪路径 |

### 4.3 第 3 层：跨运营商骨干

| 现象 | 可能根因 | 处置 |
|---|---|---|
| 某一跳开始持续丢包，后续跳丢包率一致 | **该跳本身丢包**（上一跳发出即在此丢失） | 定位到具体 AS，报对应运营商 |
| 某一跳丢 100%，后续跳正常 | 中间节点**限速或过滤 ICMP**，业务正常 | 忽略，不要报障 |
| 某一跳丢包 30%，下一跳丢 40% | 丢包是累加的，**丢在两跳之间的链路上** | 归因到前一跳或后一跳，需双向验证 |
| 双向 mtr 结果不一致 | **回程路径不同**（这是常态，不是异常） | 分别看两个方向 |
| 丢包集中在某几个 AS | 该 AS 拥塞 | 报对应运营商，附双向 mtr |
| 跨省/跨网延迟 > 100ms 且有丢包 | 绕路或链路故障 | 报运营商查路由 |
| 只在 TCP 业务丢包，ICMP 不丢 | MTU/分片问题（ping 默认小包正常） | `ping -M do -s 1472` 测 MTU，见 §4.5 |

### 4.4 第 4 层：目标侧

| 现象 | 可能根因 | 验证 |
|---|---|---|
| 到目标 100% 丢包，traceroute 走到底 | 目标防火墙/安全组丢弃 ICMP | 从目标内网 ping 反向验证 |
| 到目标丢包，但到同网段其他 IP 正常 | 目标主机自身问题（防火墙规则/限速） | 目标本机 ping 网关是否正常 |
| 到目标延迟高但无丢包 | 目标负载高、跨地域链路 | 目标侧性能排查 |
| 只有特定端口丢包 | 服务端口被限流/连接数打满 | `ss -s`、服务端日志 |
| 目标侧间歇 100% 丢包 | 双上行/双电源切换、ARP 震荡 | 目标侧日志与交换机 MAC 表 |

### 4.5 容易被误判为丢包的三件事

| 现象 | 真实原因 | 验证 |
|---|---|---|
| ping 通但网页打不开 | 不是丢包。DNS 解析慢、TCP 被墙、服务端 502 | `curl -v` 分段看卡在哪一步 |
| 大包不通小包通 | **MTU 黑洞**（路径上有设备丢弃大包） | `ping -M do -s 1472 -c 5 <目标>`，逐步减小 s 值找到临界大小 |
| 白天正常晚上丢包 | 无线干扰、共享链路高峰、家宽 QoS | 换有线对比；看时段曲线 |

## 五、命令速查（按顺序执行）

```bash
# 0. 排除本机协议栈
ping -c 100 -i 0.1 127.0.0.1

# 1. 网关（关键：第一层）
ping -c 100 -i 0.1 <默认网关>

# 2. 运营商 DNS / 公网参照
ping -c 100 -i 0.1 223.5.5.5

# 3. 目标
ping -c 100 -i 0.1 <目标>

# 4. 长路径丢包定位（首选工具）
mtr -r -c 100 -n -b <目标>        # 报告模式，100 包，不做 DNS 反解
mtr --report --report-cycles 100 <目标>
mtr -T -P 443 -r -c 100 <目标>      # 指定 TCP 端口（mtr 的 -T 需较新版本）
traceroute -n <目标>                # 传统工具，只到 IP
traceroute -n -T -p 443 <目标>      # 指定 TCP 端口，绕开 ICMP 过滤

# 5. MTU 探测（怀疑大包不通时）
ping -M do -s 1472 -c 5 <目标>     # 1472 + 28 = 1500
ping -M do -s 1400 -c 5 <目标>
cat /sys/class/net/eth0/mtu

# 6. 抓包：确认包是否发出、是否收到
tcpdump -i eth0 -n -c 100 host <目标>              # 双向
tcpdump -i eth0 -n -c 100 src host <目标>          # 只看发出（发出少=本机侧问题）
tcpdump -i eth0 -n -c 100 dst host <目标>          # 只看收到（收到少=链路或对端问题）
tcpdump -i eth0 -n -c 100 icmp                    # 只看 ICMP
ss -ti | grep -A2 <目标>                          # 看 TCP 重传与拥塞

# 7. 网卡丢包计数
ip -s link show eth0
ethtool -S eth0 | grep -i drop
cat /proc/net/dev | awk 'NR<3 || /eth0/'

# 8. 带宽与队列丢弃（上行打满的典型特征）
sar -n DEV 1 10
iftop -i eth0 -n                  # 实时看谁在吃带宽
nload eth0                        # 简单看总吞吐
```

## 六、mtr 输出怎么读

```
Host                   Loss%   Snt   Last   Avg  Best  Wrst StDev
1. 192.168.1.1         0.0%   100    0.4   0.5   0.3   2.1   0.2
2. 10.0.0.1            0.0%   100    1.2   1.4   1.1   3.0   0.3
3. 203.0.113.1        25.0%   100    8.1   8.9   7.8  12.2   1.1   ← 关注点
4. 198.51.100.1        0.0%   100    8.0   8.8   7.9  11.5   1.0   ← 关键判据
```

**判读规则：**

| 规则 | 说明 |
|---|---|
| **看「后续跳」，不看「本跳」** | 第 3 跳 25% 但第 4 跳 0%，说明包**没有**在第 3 跳丢失——是第 3 跳不回复 ICMP 而已，业务正常 |
| **Loss% 递增处即丢包点** | 第 3 跳 25%、第 4 跳 25%、第 5 跳 50% → 丢在第 4 到第 5 跳之间 |
| **Snt 必须 ≥ 100** | 100 包样本的 1% 抖动只是统计噪声，不构成结论 |
| **StDev 大 = 抖动严重** | 业务体感差往往来自抖动而非平均延迟 |
| **Wrst 远大于 Avg** | 存在偶发长延迟（丢包重传或队列），要查队列深度与 bufferbloat |
| **中间节点 100% 丢但后续正常** | 限速 ICMP，忽略 |

**mtr 双向都要做**：`mtr <目标>` 与 `mtr <本机>`（在对端执行）结果不一致是常态，因为**回程路径通常与去程不同**。报障时两份都要给。

## 七、Wi-Fi 场景专项

无线环境丢包率天然高于有线，**判定标准要放宽**：家庭/办公 Wi-Fi 的 1–2% 属可接受范围。

| 现象 | 根因 | 验证 | 处置 |
|---|---|---|---|
| 丢包集中在特定客户端 | 信号弱、距离远、隔墙 | `iw dev wlan0 link` 看 signal/rssi | 移位、加 AP |
| 全网同时丢包 | AP 或交换机问题 | 其他 AP 下正常？ | 换 AP |
| 白天好晚上差 | 邻居信道干扰 | `iw dev wlan0 survey dump` 看信道占用 | 换信道，见 5GHz/2.4GHz |
| 吞吐忽高忽低 | 干扰重传 | `iw dev wlan0 station dump` 看 tx retries | 排查干扰源 |
| 只在有线上正常、无线差 | AP 到交换机段问题 | 有线接入同 AP 对比 | 查网线与交换机端口 |
| 丢包与设备距离正相关 | 信号强度 | 同上 | 加 AP 或改部署 |

**信道建议**：2.4GHz 用 1/6/11（非重叠），5GHz 优先选 DFS 之外的 36–48 或 149–161。5GHz 带宽更大但覆盖更小。

## 八、取证清单（报障前必须齐）

报运营商或提交内部工单时，缺任何一项都可能被退回重测。

- [ ] **双向 mtr 报告**（各 100 包以上），两个方向各一份
- [ ] 每份含**具体时间戳**（精确到分钟）与**测试源 IP**
- [ ] `ping -c 100 <网关>` 的完整输出
- [ ] `mtr` 中**首次出现丢包的那一跳**，以及它所属的 AS 号
- [ ] 丢包率的具体数值与**持续时长**（不是「偶尔」）
- [ ] 是否与业务量相关（同时段的带宽、连接数）
- [ ] 是否可复现（每天什么时段、多久一次）
- [ ] 本侧设备无异常的证明（交换机端口无 CRC 错误、无流量丢弃）
- [ ] 已尝试过的处置与其结果
- [ ] 业务影响量化（影响多少用户、失败率多少）

## 九、脚本用法

```bash
python scripts/packet_loss_triage.py --file observations.txt --target example.com
```

| 参数 | 说明 |
|---|---|
| `--file` | 各层观测结果，每行 `层=值` 或 `层\|值`，如 `gateway_loss\|3.5` |
| `--target` | 目标域名/IP，用于生成排查命令清单 |
| `--gateway` | 本地网关，用于生成具体命令 |
| `--json` / `--out` | JSON 输出 / 写入指定报告文件 |
| `--selftest` | 跑内置自检（≥ 8 条断言） |

脚本做四件事：① 按四层顺序判定丢包落在哪一层；② 按丢包率给业务影响等级；③ 识别「ICMP 丢包但业务正常」这类需要人工确认的情形；④ 输出下一步该做什么的命令清单与取证提醒。

> 脚本输入的是**你已经观测到的数据**，它不发起任何网络请求，也不会替你抓包。它的价值在于**把散落的观测结果按分层规则归拢成结论**，并防止「跳过第一层直接往后猜」。

## 十、最常见的坑

**坑一：ping 通就认为网络没问题。**
ping 只验证了 ICMP 与三层可达，不验证 TCP 端口、不验证 MTU、不验证应用。大包不通（MTU 黑洞）时，ping 完全正常而网页打不开。

**坑二：看到 mtr 中间某一跳丢包就报障。**
中间节点限速 ICMP 是普遍做法，那一跳 100% 丢包而后续 0% 丢包是**完全正常**的。**必须看后续跳的丢包率是否相同或更高。**

**坑三：丢包 1% 就报运营商。**
100 包样本下 1% 就是 1 个包，统计意义很弱。要么加大样本（`mtr -c 500`），要么看**持续性**。一次性的 1 包丢失在正常链路上也会出现。

**坑四：把 TCP 重传当带宽不足。**
TCP 丢包 → 重传 → 重传占带宽 → 吞吐下降，很容易误判成「带宽不够」而去升带宽。**升带宽不解决丢包**，反而可能因队列变深让延迟更糟。正确做法是定位并消除丢包。

**坑五：只做单向测试。**
去程正常、回程丢包是最常见的组合之一，而回程路径往往完全不同。**双向都要测**，报障时两份都要给。

**坑六：跳过第一层直接从公网测。**
本机网线松了、网卡 down、交换机端口故障，在公网侧表现就是「全丢包」。不测网关就无法区分「本机问题」和「运营商问题」，报障必被退回。

**坑七：拿丢包率当唯一判据，不看抖动。**
平均 20ms 但 StDev 200ms 的链路，视频通话一样卡。业务体感来自延迟分布的尾部，不只是平均值。

**坑八：生产高峰抓包把机器拖垮。**
`tcpdump` 全量抓包会吃满 CPU 和磁盘，可能在排查丢包时制造新的丢包。生产环境务必加 `-c` 限制包数、`-w` 限制大小、限时抓取，优先在**镜像口/旁路**抓。

**坑九：忽略 ICMP 限速与业务丢包的区别。**
路由器对 ICMP 做速率限制很普遍。因此「ping 丢包但业务正常」不一定是问题，而「ping 正常但业务丢包」才是真问题。判定必须结合业务侧数据。

**坑十：改了配置不复测就结单。**
调整 MTU、关 offload、改队列参数后，必须用**同一条命令、同一个目标、同样样本量**复测，并保留前后对比数据。没有前后对比的「已优化」等于没做。

## 十一、边界与免责

- 本技能给出的是**排查路径与判读口径**，不代替现场网络操作，也不能保证定位结果正确——链路问题常需多视角交叉验证
- 阈值（0.5% / 2% / 10%）为通用起点，**不同业务、不同接入方式的容忍度差异很大**：金融交易类对丢包极敏感，音视频通话对丢包和抖动都敏感，办公上网几乎无感
- 涉及运营商链路的最终定责与故障等级，**以运营商与用户的责任划分约定为准**
- 涉及链路改造、QoS 策略、路由调整的方案设计，需由网络专业人员在现场评估后实施
- 抓包可能涉及敏感数据，抓取、留存、传输须遵守**现行规定与本单位的数据安全要求**
