# 网络丢包定位与排查路径核查 · 能力概览

## 你会得到什么

一套**按层推进、不跳步**的丢包定位流程，以及每一步的现象-根因对照表——丢包排查唯一的正确方法是分层，跳过任何一层直接改配置都等于蒙。

**分层框架**：L0 本机协议栈 → L1 本机到网关 → L2 到公网参照 → L3 跨运营商骨干 → L4 目标侧。铁律是 L1 不通过绝不进入 L2：本机网线松了、网卡 down、交换机端口故障，在公网侧的表现就是「全丢包」，不测网关就无法区分本机问题与运营商问题。

**阈值层面**：丢包率五级判定（≤0.5% 可接受 / 2% 关注 / 5% 告警 / 10% 严重 / ≥10% 故障），以及按业务类型给出的可容忍丢包与抖动对照——在线交易要求 0 丢包、视频会议 0.5% 丢包 + 30ms 抖动、IoT 遥测可容忍 5%，用错标准会把小问题当故障、把真问题当正常。

**判读层面**：mtr 七个字段的含义与「看后续跳不看本跳」「丢包率递增处才是丢包点」两条核心规则；traceroute 中间跳 100% 丢包的正确解读（ICMP 限速，不要报障）；TCP 丢包与 UDP 丢包的表现差异；以及三种最容易被误判为丢包的现象——ping 通但网页打不开、大包不通小包通（MTU 黑洞）、白天正常晚上丢包。

**脚本**：`scripts/packet_loss_triage.py` 读取四层观测数据，输出定位层、业务影响等级、下一步该执行的命令清单，以及报障前的取证清单。它会强制区分「ICMP 丢包但业务正常」和「真实业务丢包」，并把无法解析的数值标记为采集失败而不是当作 0。

## 典型用法

1. 排查前先拿到执行顺序：从 L0 开始逐层采集，每层样本不少于 100 包。
2. 拿到 mtr 报告想知道丢在哪：按「看后续跳」规则读，脚本会指出首现丢包跳。
3. 准备报运营商：先跑一遍取证清单，缺项先补——双向 mtr、时间戳、AS 号、持续时长这四项缺任何一项都可能被退回重测。
4. Wi-Fi 环境偶发丢包：按放宽后的无线标准判定，脚本会给出信号与信道排查命令。
5. 改完配置要结单：必须同一条命令、同一个目标、同样样本量复测，保留前后对比。

## 边界

- 只做**定位路径规划与现象判读**，不代替现场网络操作，也不能保证定位结果正确——链路问题常需多视角交叉验证
- 脚本**不发起任何网络请求**，只归拢你已观测到的数据。缺任何一层的观测数据时，结论只能定位到已有数据的边界
- 丢包阈值（0.5% / 2% / 10%）是通用起点，**不同业务的容忍度差异极大**，必须结合业务侧 SLA 与现场基线确定
- 涉及运营商链路的最终定责与故障等级，**以运营商与用户的责任划分约定为准**
- 抓包会占用 CPU 与磁盘，生产高峰可能**制造新的丢包**，务必限包数、限大小、限时抓取
- 抓包涉及敏感数据，抓取、留存、传输须遵守现行规定与本单位的数据安全要求
