# 消防设施检测报告与维保核查（fire-testing-report-check）

一份检测报告，**看结论只是入门，看机构、看项目、看周期、看闭环才是过关**。每年花几千上万块做的检测，报告锁在抽屉里没人核，等于白做。

这个技能做四件事：**查机构** → **核报告** → **对周期** → **跟整改**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 讲解报告核查方法与清单 | ❌ 替代法定检测与技术服务机构责任 |
| 生成核查清单与整改台账 | ❌ 出具检测结论或验收意见 |
| 整理维保合同与记录口径 | ❌ 判定报告真伪 |
| 输出周期预警 | ❌ 保证设施完好 |

**报告核查发现下列情况，先固定证据（报告原件、公示信息截图），再与机构和单位负责人交涉，必要时向主管部门反映：**
- 机构不具备从业条件或未在信息系统公示却出具报告
- 报告签字人非本单位人员、签字章造假
- 检测日期与现场实际明显不符

**永远不要**把"结论合格"当"设施没问题"——问题项才是报告的正文。

## 二、完整工作流

```
第 1 步  明确场景：收到报告初核 / 年度周期盘点 / 维保合同与记录核查 / 迎检
第 2 步  读规则文件 rules/report_check_rules.md
第 3 步  按场景取用：
    - 查机构 → 第三节（从业条件与公示查询）
    - 核报告 → 报告七要点（第四节）
    - 对项目 → 必备检测项目清单（第五节）
    - 对周期 → 周期红线（第六节）
    - 体检表 → python scripts/report_check.py --file 报告核查.json
第 4 步  按 templates/检测报告核查清单.md 输出
第 5 步  人工确认：机构公示信息、签字人、现场抽查
```

## 三、机构与人员核验

1. **从业条件**：消防技术服务机构应具备企业法人资格、相应工作场所与仪器设备、相应数量的注册消防工程师和取得职业资格证书的操作人员等（以应急管理部消防技术服务机构从业条件为准）。
2. **公示查询**：机构应在**社会消防技术服务信息系统**公示基本信息与承诺，核查时以系统可查为准；查不到的要提高警惕。
3. **报告签章**：报告应加盖机构公章，有项目负责人和操作人员签字；涉及注册消防工程师执业活动的，应有相应注册工程师签章。
4. **口头核验**：签约主体、检测主体、报告主体应一致；"借资质""挂名报告"是红线。

---

## 四、报告七要点核查

| # | 核查点 | 合格口径 |
|---|---|---|
| 1 | 机构名称与公示信息一致 | 系统可查、名称一字不差 |
| 2 | 项目名称与本单位一致 | 楼宇、楼层、系统范围对得上 |
| 3 | 检测日期与报告日期逻辑正确 | 报告日期 ≥ 检测日期；日期在检测周期内 |
| 4 | 检测项目覆盖必备清单 | 按场所类型逐项核对（第五节） |
| 5 | 结论与问题项一致 | "合格"结论下存在未整改问题项即矛盾 |
| 6 | 问题项有整改闭环 | 整改措施、期限、复查记录 |
| 7 | 下次检测日期已排定 | 与本次检测日期间隔 ≤ 12 个月 |

---

## 五、按场所必备检测项目清单

| 场所/系统 | 必备检测项 |
|---|---|
| 通用基础 | 消火栓系统、灭火器、应急照明与疏散指示 |
| 设自动消防设施的 | 火灾自动报警系统、自动喷水灭火系统、消防电源 |
| 高层建筑 | 另含防排烟系统、防火分隔设施（卷帘/门）、消防电梯 |
| 人员密集场所 | 另含防火分隔、广播（如有） |
| 有燃气场所 | 可燃气体报警装置 |

> 具体项目以检测标准（如 XF 503、GB 25201 等）和本单位设施台账为准；**没有的项目在报告里也不应出现**。

---

## 六、周期红线

| 事项 | 要求 |
|---|---|
| 建筑消防设施全面检测 | **每年至少一次**，委托具备从业条件的机构 |
| 设施维护保养 | 按合同约定执行（月度/季度为通行口径），维护保养记录留存 |
| 下次检测排期 | 与本次间隔 ≤ 12 个月，提前 1-2 个月启动 |

> 《消防法》要求单位按照标准配置设施器材并**定期组织检验、维修**；超期未检测属于管理缺口，迎检必问。

## 七、脚本用法（报告核查体检）

```bash
python scripts/report_check.py --file "D:\消防\报告核查.json"
```

| 参数 | 说明 |
|---|---|
| `--file` | 必填。报告与维保信息 JSON |
| `--today` | 核查基准日，默认今天 |
| `--format` | `md`（默认）或 `json` |
| `--selftest` | 跑内置样例自检 |

脚本检查五类问题：**机构资质与签章、项目覆盖缺口、周期超期、结论与问题项矛盾、维保合同与记录缺口**。

> ⚠️ 脚本只做资料结构与逻辑核查，**不判定报告真伪与设施实际状态**；最终以现场抽查和技术服务机构责任为准。

---

## 八、人工确认（这步不能省）

- [ ] 机构在社会消防技术服务信息系统公示信息是否可查
- [ ] 报告签字人是否为注册消防工程师、注册单位是否一致
- [ ] 报告结论与问题项是否矛盾
- [ ] 问题项整改是否有证据（更换记录、复测记录）
- [ ] 现场抽查 2-3 个"合格"项验证（如消火栓出水、应急灯放电）
- [ ] 维保合同是否约定响应时限、月报/季报义务

---

## 九、输出结构（固定三段）

1. **能不能过关**——结论先行：报告可用 / 有缺口 / 有红线问题
2. **核对清单**——逐项标合规/缺失/存疑
3. **整改与补资料建议**——先后顺序、责任岗位、留存材料

---

## 十、最常见的坑

**坑一：只看结论，不看问题项。** "基本合格"四个字下面压着一串未整改问题，等于报告白出。

**坑二：报告日期早于检测日期。** 时间线倒挂，检查人员第一眼就能看出报告是凑的。

**坑三：机构公示信息查不到。** 钱花了、报告拿了，机构可能不具备从业条件，报告效力存疑。

**坑四：超期未检测。** 去年 3 月做的检测，今年 5 月被检查，间隔 14 个月，直接写进问题清单。

**坑五：问题项年年同一批。** 三年报告问题一样，整改从没闭环，迎检时从轻直接变从重。

**坑六：维保存在月记录、没有响应记录。** 维保不是打卡，故障报修响应时限才是关键。
