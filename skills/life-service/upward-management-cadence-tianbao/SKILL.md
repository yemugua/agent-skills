# 向上管理节奏与汇报对齐核查（upward-management-cadence）

向上管理不是「多汇报」，而是**在正确的时间，用正确的形式，把正确的信息给到正确的人**。

大部分人向上管理失败在两处：一是**没有节奏**，想到才报，坏消息拖到爆雷才说；二是**没有对齐**，领导按 A 标准考核你，你按 B 标准努力，年底才发现整年白干。

这个技能做三件事：**排一张节奏表** → **把每次汇报写成三段式** → **把预期对齐做在前面而不是年底**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出日/周/月/季四档汇报节奏表 | ❌ 代替你与直属上级确认真实汇报频率 |
| 给出三段式/四段式汇报模板与填空句 | ❌ 保证领导看完一定满意 |
| 判定坏消息属于「当天报/次日报/可并入周报」 | ❌ 替你决定是否要承担某项责任 |
| 给出预期对齐四问与话术 | ❌ 代替绩效目标确认与考核制度 |
| 给出越级汇报的四条红线边界 | ❌ 鼓励绕开直属上级 |
| 诊断汇报空转与信息过载 | ❌ 判断某领导个人的管理风格偏好 |

**必须先停下来确认的情形：**
- 涉及未公开的重大风险、负面舆情、客户投诉 —— **先按公司重大事项报告制度上报，再决定沟通范围**
- 涉及他人责任的重大失误 —— 必须先核实事实，**不得在未核实前上报结论性判断**
- 涉及薪酬、编制、组织调整等信息 —— 按公司保密要求处理，不写入书面汇报
- 你的公司/部门已有既定汇报制度 —— **以本单位制度为准**，本技能的频率仅为通用参考

## 二、完整工作流

```
第 1 步  盘点你的汇报对象：直属上级、跨部门接口人、隔级领导，按「关心什么」分档
第 2 步  先读 rules/cadence_table.md，把四档节奏表填成你自己的版本
第 3 步  做预期对齐：按 rules/alignment_checklist.md 的四问写成一页对齐记录，双方确认
第 4 步  跑脚本体检：python scripts/report_cadence_check.py --file cadence.json
第 5 步  看四个数：节奏完整率、汇报空转率、坏消息延迟、越级依赖度
第 6 步  套 templates/report_templates.md 的三段式写每次汇报
第 7 步  按 §六 做「甩锅自查」：结论句必须落在自己的动作上
第 8 步  每月末复盘一次节奏表，按领导实际关注点调整权重
```

**顺序不能颠倒**：第 3 步预期对齐没做，第 2 步的节奏表再漂亮，也只是把错误方向汇报得更快。

## 三、四档汇报节奏表（核心资产）

| 档位 | 报什么 | 报给谁 | 什么形式 | 时长上限 | 频率 |
|---|---|---|---|---|---|
| **日** | 昨日完成、今日计划、**阻塞项**（一句话） | 直属上级 | IM/工作群短消息 | ≤5 行 | 每日一次或仅在有阻塞时 |
| **周** | 本周关键进展、下周计划、需要协调的事 | 直属上级 | 一页文档或表格 | ≤1 页 | 每周固定 1 次 |
| **月** | 关键指标达成、风险预警、资源需求、复盘结论 | 直属上级（抄送隔级仅在必要时） | 结构化文档 | ≤3 页 | 每月 1 次 |
| **季** | 目标达成率、方向调整建议、下季资源盘、风险趋势 | 直属上级 | 汇报材料 + 会上过一遍 | ≤10 页 + 15 分钟 | 每季 1 次 |

**节奏表的三个设定规则：**

1. **固定时点 > 频率**。定在每周五下午三点，比「随时汇报」更让人信任——领导能提前安排时间。
2. **形式跟着内容走**。3 行以内不要写成文档（成本高），3 页以上不要塞进 IM（读不完）。
3. **阻塞项走日档，不许攒到周报**。这一条单独拎出来，因为它是坏消息时机的核心。

## 四、三段式与四段式汇报（照抄填空）

### 三段式（日常周报/月报用，90% 的场合够用）

```
【结论】本周 X 事项已达成 / 未达成，核心原因是一句话。
【进展】1. 事项A：结果 + 关键数据（做了什么 → 变成什么）
        2. 事项B：结果 + 关键数据
        3. 事项C：卡在XX，等XX方回复，预计XX时间可动
【需要】需要XX决策 / 需要XX资源 / 无需支持，本周仅同步。
```

**第三段「需要」不能省**。写了「无需支持」也是一条有效信息，它告诉领导这件事在你的掌控内。

### 四段式（季度/半年度/重大事项汇报用）

```
【结论】本季目标整体达成 XX%，A/B 达成，C 未达成。
【数据】指标1：目标 100 → 实际 120（120%）｜指标2：目标 50 → 实际 38（76%）
【问题】C 未达成的根因是 XX，已启动 XX 动作，预计 XX 见效。
【计划】下季目标值 XX，三项关键动作，需要 XX 支持。
```

四段式只在**涉及评价与资源**的场合用。日汇报硬套四段式是浪费彼此时间。

## 五、坏消息什么时候必须报（最容易做错的一处）

判定用两个维度：**是否可逆** × **是否影响他人动作**。

| 情况 | 上报时限 | 为什么 |
|---|---|---|
| 目标/里程碑延期，且**下游已被依赖** | **当天**（发现后 4 小时内） | 下游不调整就全线报废 |
| 涉及资金、合规、安全、法律风险 | **立即**（不隔夜） | 留痕与止损窗口以小时计 |
| 涉及客户投诉且已扩散 | **当天** | 越晚说越像隐瞒 |
| 与他人承诺冲突（两个部门各答应一次） | **当天** | 越晚说越像挑事 |
| 自身进度偏慢但下游无依赖 | 次日，并入次日日档 | 有缓冲，不必制造紧张 |
| 个人能力缺口，暂不影响交付 | 周报中提一句 + 单独申请辅导 | 用日档会显得失控 |
| 纯情绪、不影响任何事 | 不进汇报，放进一对一闲聊 | 汇报位是稀缺的，别稀释 |

**「怕挨骂所以不说」是最大的误判**：领导对「坏消息本身」的容忍度，远高于对「我早就知道但没人告诉我」的容忍度。

**报告坏消息的四步走：**

```
1. 事实   ：一句话讲清发生了什么，不加形容词，不加自我保护
2. 影响   ：具体到谁、损失多少、影响哪条时间线
3. 归因   ：区分「我的原因」「外部原因」「尚未定论」，未定论就写未定论
4. 方案   ：给 1 个已启动的动作 + 1 个需要你拍板的选择
```

| 错误写法 | 正确写法 |
|---|---|
| 这个项目可能要延期 | A 项目原定 3/15 交付，目前进度 70%，延期约 2 周，主因是接口方未确认字段（已两次催办）。我已启动 B 方案保核心功能，需要你决定是否升级协调 |
| 因为资源不够所以做不完 | 本月计划 5 项，完成 3 项；受人力限制，剩余 2 项需增援 1 人 2 周，或延至下月。你倾向哪个方案 |
| 客户有点不满 | 客户 X 对 A 功能提出投诉（工单号 T123），诉求是退款，已二次沟通。金额约 X 元，需你确认是否按退款处理 |
| 我尽力了 | 我在 X 环节已做 A、B 两步，剩余卡在对方 X 响应，需你协调 |

## 六、预期对齐（做在前面，不做在年底）

**对齐四问**，每次换季度、换项目、接新任务时各做一次，写成一页，双方签字或 IM 确认留痕：

| 问什么 | 怎么问（可直接抄） | 为什么必须问 |
|---|---|---|
| **成功标准** | 「这个任务做到什么程度算完成？」 | 60% 的返工来自双方标准不一致 |
| **优先级** | 「如果两件事撞车，先保哪个？」 | 上级以为都在做，实际都在延 |
| **节奏** | 「你想多久听到一次进展？什么情况要立刻说？」 | 避免你憋大招、他干着急 |
| **边界** | 「哪些事我可以直接定，哪些要报你？」 | 越界和不敢决策，都出在这条上 |

**对齐必须留痕。** 口头对齐在绩效面谈时等于没对齐。留痕三选一：IM 文字确认、会议纪要里写一段、共用一份文档让对方回复「确认」。

## 七、越级汇报的四条红线

越级汇报本身不是禁区，但下面四条踩了，基本等于给自己埋雷：

| # | 红线 | 说明 |
|---|---|---|
| 1 | **不是紧急情况就一律不越级** | 紧急的定义：涉及安全/合规/资金/重大客户，或本级已沟通 2 次无响应且继续等待有实质损失 |
| 2 | **越级前必须先告知直属上级** | 除非是涉及其自身不当行为；否则事后得知被绕过的信任损失，比问题本身严重得多 |
| 3 | **只同步信息，不下结论、不做评价** | 对隔级说「我直属领导能力不行」，无论事实如何都是职场事故 |
| 4 | **不越级要资源、不越级要承诺** | 要决策走本级，这是组织的权力结构 |

**合规做法**：先本级沟通 → 记录已沟通的事实与时间 → 确有损失风险时，**以「同步一个进展」的名义**发给隔级，并抄送直属上级 → 只讲事实、时间线、已采取的动作，不评价人。

## 八、脚本用法

```bash
python scripts/report_cadence_check.py --file cadence.json --out 汇报节奏体检.md
python scripts/report_cadence_check.py --selftest
```

| 参数 | 说明 |
|---|---|
| `--file` | 汇报节奏 JSON，见下方结构 |
| `--text` | 直接给 JSON 字符串 |
| `--out` | 结果写入文件，默认 `scripts/_last_result.txt` |
| `--format` | `md`（默认）或 `json` |
| `--selftest` | 运行内置自检 |

输入 JSON：

```json
{
  "title": "2026 Q4 向上管理节奏体检",
  "owner": "本人",
  "audiences": [
    {"name": "直属上级", "level": "direct", "cadence": "week", "cares": "指标与风险"},
    {"name": "部门负责人", "level": "skip", "cadence": "quarter", "cares": "方向与资源"}
  ],
  "cadence_plan": [
    {"level": "day", "content": "昨日完成/今日计划/阻塞项", "audience": "直属上级", "form": "IM", "fixed_time": "10:00"},
    {"level": "week", "content": "关键进展/下周计划/需协调", "audience": "直属上级", "form": "一页文档", "fixed_time": "周五 15:00"},
    {"level": "month", "content": "指标达成/风险预警/资源需求", "audience": "直属上级", "form": "结构化文档", "fixed_time": "月末 3 个工作日内"},
    {"level": "quarter", "content": "目标达成/方向建议/资源盘", "audience": "直属上级+隔级", "form": "汇报材料", "fixed_time": "季末后 5 个工作日内"}
  ],
  "bad_news": [
    {"item": "A 项目里程碑延期", "discovered_hours_ago": 3, "has_downstream": true, "reported": true}
  ],
  "upward_skips": [
    {"reason": "接口方三次未响应，交付有实质损失", "told_direct_first": true, "conclusion_only": true}
  ]
}
```

| 字段 | 说明 |
|---|---|
| `audiences[].level` | `direct` 直属上级 / `peer` 平级 / `skip` 隔级 |
| `cadence_plan[].level` | `day` / `week` / `month` / `quarter` |
| `cadence_plan[].fixed_time` | 固定时点，留空会被判为「无固定节奏」 |
| `bad_news[].reported` | 是否已上报 |
| `upward_skips[].told_direct_first` | 是否先告知直属上级 |

脚本输出：节奏完整率、汇报空转率（无固定时点/无受众/无内容占比）、坏消息延迟判定与越级红线提示，以及三条整改建议。

> 脚本只做结构与时限核查，**不判断你的领导喜欢什么风格**。

## 九、人工确认清单（这步不能省）

- [ ] 节奏表已按本公司/本部门实际制度核对过（不是照抄本文）
- [ ] 四档中缺的档位，已写明「不需要」的理由（如「团队仅 3 人，月报与周报合并」）
- [ ] 每次汇报都写清了「需要对方做什么」，而不是只汇报事实
- [ ] 坏消息判定用的是「可逆性 × 是否影响他人动作」，不是「怕不怕挨骂」
- [ ] 预期对齐四问在上一个周期内至少做过一次，且有留痕
- [ ] 越级沟通前已告知直属上级（除涉及其不当行为的情形）
- [ ] 汇报内容已按保密要求脱敏，不含薪酬、未披露数据、个人信息
- [ ] 结论句落在自己的动作上，没有出现「因为 XX 部门……」作为主因句

## 十、最常见的坑

**坑一：把向上管理做成汇报数量竞赛。**
错误做法：每天发五条 IM 报流水账。正确做法：日档只报阻塞项，无阻塞就静默；周档才是常规汇报位。**领导对消息的容忍度是有限的，刷屏会让你真正紧急的事被淹没。**

**坑二：只在有进展时汇报，坏消息一律憋着。**
错误做法：项目明显要延期了，先想着「等做完再报告进度 90%」。正确做法：发现后 4 小时内，按「事实-影响-归因-方案」四步报出去。**领导能接受问题，不能接受被瞒。**

**坑三：预期从不对齐，只在年底解释。**
错误做法：一整年按自己理解的方向做，绩效面谈才说「您当时没说过」。正确做法：每次接新任务做一次对齐四问并留痕。**年底的口头解释约等于零证据。**

**坑四：汇报只讲事实，不讲需求。**
错误做法：「A 事项已完成，B 事项进行中，C 事项待启动。」正确做法：补第三段「需要：A 无需支持；B 需要 XX 部门在 X 日前回复；C 需要 1 人 2 周」。**汇报的目的不是让他知道，是你让他做决定或给资源。**

**坑五：归因句写成甩锅。**
错误做法：「因为其他部门不配合，项目才延期。」正确做法：「接口方未确认字段，我已两次催办仍未回复，需你协调升级；我已启动 B 方案保核心功能」。**客观原因可以提，但结论句必须落在自己能改的动作上。**

**坑六：越级沟通用完不告知直属上级。**
错误做法：直接找领导的领导反映问题，觉得这样更快。正确做法：先本级沟通并记录 → 确有损失风险时以「同步进展」名义同步隔级并抄送本级。**被绕过的信任损失，比问题本身难修复。**

**坑七：抄送全员当「透明」。**
错误做法：所有汇报都抄送大群，觉得这样显得积极。正确做法：抄送要写清理由，且抄送内容不得含他人绩效评价、未披露财务、人事变动。**无理由抄送会被读成展示，敏感内容被抄送会造成合规风险。**

**坑八：汇报模板照抄别人的，与自己岗位无关。**
错误做法：把运营岗的周报模板改成销售岗用。正确做法：按「你这个岗位的直属上级关心什么」重写内容字段——销售关心管道与转化，技术关心交付与故障，职能关心流程与成本。**模板是壳，字段要按受众重填。**

**坑九：写完汇报不看一遍就发。**
错误做法：结论句里带情绪词（「这个需求真的过分了」）。正确做法：发出前删掉所有形容词、抱怨句和反问句，只留事实、数据、请求。**情绪不会帮你达成目的，只会制造解读成本。**
