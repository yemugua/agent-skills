# 年终述职PPT结构与量化核查（year-end-review-ppt）

述职 PPT 丢分，八成不是因为干得少，而是**看不出来**：一堆「积极参与」「大幅提升」，评委听完不知道你把什么从多少变成了多少。

这个技能做三件事：**按五段排页序** → **把每页压成一句话结论** → **用四个口径把业绩算实**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出页序结构与页数时长配比 | ❌ 代替公司绩效考核制度与评级规则 |
| 给出每页一句话结论的写法 | ❌ 替你编造没有发生过的数据 |
| 核算同比、环比、达成率、人均效能 | ❌ 代替与直属上级的目标确认 |
| 指出堆工作量、只讲过程等忌讳 | ❌ 保证评级结果或晋升通过 |
| 给出逐页质检表 | ❌ 建议把团队成果写成个人成果 |

**必须先停下来确认的情形：**
- 数据来自未上线、未验收、内部未确认的项目 —— **不得按已达成口径写**
- 目标值是年中调整过的 —— 必须写明调整前后，只报调整后目标属于口径操纵
- 涉及他人承担主要工作的成果 —— 必须写明角色与分工
- 涉及保密项目与未披露财务数据 —— 按公司披露口径脱敏
- 与人力部门考核口径不一致时 —— **以公司制度与上级确认为准**

## 二、完整工作流

```
第 1 步  确认口径：考核周期、目标值来源（年初定 / 年中调）、评审关注点
第 2 步  选 5-8 项指标（规则见 rules/quantify_rules.md §1），每项配权重
第 3 步  收集四个数：本期值、上年同期值、上一周期值、目标值
第 4 步  跑脚本核算：python scripts/yearend_ppt_check.py --file ppt.json
第 5 步  看四个数：页序完整度、量化覆盖率、结论句覆盖率、堆工作量信号数
第 6 步  按 rules/ppt_structure.md 排页序，每页按一句话结论模板写
第 7 步  按 §六 做逐页质检，改掉「参与了」「负责了」类无结果表述
第 8 步  按页数配比计算讲述时长，预演一次并掐表
```

**顺序不能颠倒**：第 4 步算不出数的指标，说明它本来就不该进述职。

## 三、五段页序结构（结论先行）

| 段 | 页序位置 | 页数占比 | 每页必须回答 | 一句话模板 |
|---|---|---|---|---|
| **结论** | 第 1 页 | 1 页 | 这个周期我干成了什么、达成多少 | 「本期 X 项核心指标加权达成 XX%，A、B 超额，C 未达」 |
| **数据** | 中段前部 | 40% | 各指标目标值、实际值、达成率、同比、环比 | 「销售额 1200 万，同比 +26%，目标达成 104%」 |
| **亮点** | 中段中部 | 20% | 哪 2-3 件事最值得说，难在哪、结果如何 | 「把 X 环节从 A 天压到 B 天，关键动作是……」 |
| **问题** | 中段后部 | 20% | 1-2 个真问题 + 根因 + 已做动作 | 「C 未达，根因是 X，已启动 Y，预计 Z 见效」 |
| **计划** | 最后一页 | 1 页起 | 下周期目标值 + 关键动作 + 需要的资源 | 「下期目标 X，三项动作，需要 XX 支持」 |

### 为什么结论必须放第 1 页

评委一天要看十几份述职。**第 1 页给结论，后面才是证据。** 反过来（先讲过程再给结论）的 PPT，评委在第 5 页还没听到你想说什么，就已经在看时间了。

### 页数与时长配比

| 汇报形式 | 页数 | 时长 | 每页平均 |
|---|---|---|---|
| 5-10 分钟短述职 | 8-12 页 | 5-10 分钟 | 30-50 秒 |
| 10-15 分钟标准述职 | 12-18 页 | 10-15 分钟 | 40-60 秒 |
| 20 分钟答辩 | 18-25 页 | 20 分钟 | 50 秒 |

**一页讲了超过 90 秒还讲不完，就是内容太多。** 拆成两页或删掉。

## 四、每页一句话结论的四种写法

### 写法一：数字型

```
「[指标] 从 [基线] 到 [结果]，同比 [±X%]，目标达成 [XX%]」
```

### 写法二：对比型

```
「[原做法] 单均 [X]，改为 [新做法] 后降到 [Y]」
```

### 写法三：动作—结果型

```
「把 [环节] 前移到 [时点]，返工率从 [X%] 降到 [Y%]」
```

### 写法四：结论—动作型（用于问题页）

```
「[问题] 未达成，根因是 [可控原因]，已启动 [动作]，预计 [时间] 见效」
```

**每页标题就是这句话，不要另写标题。** 评委只扫标题时，也应该能读懂这一页在讲什么。

## 五、四个量化口径

```
同比     =（本期值 - 上年同期值）÷ 上年同期值 × 100%
环比     =（本期值 - 上一周期值）÷ 上一周期值 × 100%
目标达成率（越大越好类） = 本期值 ÷ 目标值 × 100%
目标达成率（越小越好类） = 目标值 ÷ 本期值 × 100%   ← 故障率、成本、耗时
人均效能 = 本期产出 ÷ 本期平均在岗人数
加权达成率 = Σ(单项达成率 × 权重) ÷ Σ权重
量化覆盖率 = 有数值且基线完整的指标数 ÷ 指标总数
```

### 三个数要一起看

| 同比 | 达成率 | 真实情况 | 述职怎么写 |
|---|---|---|---|
| ↑ | ≥100% | 真增长真达成 | 重点写，给关键动作 |
| ↑ | <100% | 增长但没够到目标 | 说明目标定得高，或增长集中在后半段 |
| ↓ | ≥100% | **目标定低了** | **必须主动说明**，否则被追问很被动 |
| ↓ | <100% | 下滑 | 写根因与止损动作 |

> 「同比下降但达成率 104%」是最容易被抓的一栏。**自己先说出来，比被问出来好。**

### 越小越好类指标别算反

故障次数从 25 降到 18，写成「达成率 72%」是错的，正确是 20 ÷ 18 = 111%。

### 人均效能的分母

```
本期平均在岗人数 =（期初在岗人数 + 期末在岗人数）÷ 2
```

**中途入职的人怎么算**：按实际在岗月数折算，写明口径。**分母口径不写明，这个数没有意义。**

## 六、五类忌讳

### 忌讳一：堆工作量

```
✗ 本年度参与各类项目 15 项，承担 XX 工作 300 余天，完成会议纪要 120 份。

✓ 项目 A：负责 XX 模块，交付 XX，联调一次通过，节省人工 Y 人日
   项目 B：主导 XX 改造，耗时从 X 天降到 Y 天
   项目 C：协同 3 个部门，落地 Z 项流程
```

**数量不是成果。评委看到「15 项、300 天」只会想「做了很多事」，看不到「造成了什么变化」。**

### 忌讳二：只讲过程不讲结果

```
✗ 「积极参与项目建设」「认真负责」「加班加点完成任务」

✓ 「把 X 环节从 A 压到 B，单次节省 C 小时」
```

### 忌讳三：每页没有结论句

```
✗ 标题写「项目进展」，正文列了 8 条内容

✓ 标题写「项目 A 按期交付，返工率下降 12%」
```

### 忌讳四：数据无来源

```
✗ 「满意度提升 12%」（说不清怎么统计的）

✓ 「按季度问卷，样本 428 份，2026 年 11 月采集」
```

**没有来源的数字等于没写。**

### 忌讳五：问题页甩锅

```
✗ 「因产品需求频繁变更，导致上线延期」

✓ 「需求变更 3 次，我在第 2 次后引入评审机制，后续变更影响下降 XX%」
```

**结论句必须落在自己能改的动作上。**

## 七、逐页质检表

每页过一遍，任意一条不过就改：

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 标题是否就是结论句 | 是，不另写标题 |
| 2 | 结论句里是否有一个数 | 是 |
| 3 | 数据是否有来源 | 系统 / 台账 / 抽样，抽样写样本量 |
| 4 | 是否区分了个人贡献与团队成果 | 写清人数、分工与自己承担的那段 |
| 5 | 同比与环比是否与结论方向一致 | 不一致时主动解释 |
| 6 | 越小越好类指标的达成率是否算反 | 故障/成本/耗时用「目标÷实际」 |
| 7 | 图上数字与文字数字是否一致 | 图表与正文一致 |
| 8 | 是否存在无结果的表述 | 删除「积极参与」「认真负责」类词 |
| 9 | 问题页是否甩锅 | 结论句主语是自己的动作 |
| 10 | 本页讲述是否 ≤90 秒 | 超时拆页 |

## 八、脚本用法

```bash
python scripts/yearend_ppt_check.py --file ppt.json --out 述职PPT体检.md
python scripts/yearend_ppt_check.py --selftest
```

| 参数 | 说明 |
|---|---|
| `--file` | PPT 结构 JSON，见下方结构 |
| `--text` | 直接给 JSON 字符串 |
| `--out` | 输出文件，默认 `scripts/_last_result.txt` |
| `--format` | `md`（默认）或 `json` |
| `--selftest` | 运行内置自检 |

输入 JSON：

```json
{
  "title": "2026 年度述职",
  "owner": "本人",
  "minutes": 12,
  "pages": [
    {"no": 1, "section": "conclusion", "has_conclusion_sentence": true,
     "has_number": true, "has_source": true},
    {"no": 2, "section": "data", "has_conclusion_sentence": true,
     "has_number": true, "has_source": true},
    {"no": 3, "section": "data", "has_conclusion_sentence": false,
     "has_number": true, "has_source": false},
    {"no": 4, "section": "highlight", "has_conclusion_sentence": true,
     "has_number": true, "has_source": true},
    {"no": 5, "section": "problem", "has_conclusion_sentence": true,
     "has_number": true, "has_source": true},
    {"no": 6, "section": "plan", "has_conclusion_sentence": true,
     "has_number": true, "has_source": true}
  ],
  "metrics": [
    {"name": "销售额", "unit": "万元", "current": 1200, "baseline": 950,
     "previous": 1110, "target": 1150, "direction": "up", "weight": 0.4,
     "headcount": 12},
    {"name": "线上故障次数", "unit": "次", "current": 18, "baseline": 25,
     "previous": 22, "target": 20, "direction": "down", "weight": 0.3,
     "headcount": 12},
    {"name": "交付周期", "unit": "天", "current": 15, "target": 12,
     "direction": "down", "weight": 0.3}
  ],
  "workload_wording": ["积极参与项目建设", "认真负责", "加班加点完成任务"],
  "blame_sentences": ["因产品需求频繁变更，导致上线延期"]
}
```

| 字段 | 说明 |
|---|---|
| `pages[].section` | `conclusion` / `data` / `highlight` / `problem` / `plan` |
| `pages[].has_conclusion_sentence` | 该页是否有结论句 |
| `metrics[].headcount` | 本期平均在岗人数，用于人均效能 |
| `workload_wording` | 堆工作量表述原文 |
| `blame_sentences` | 疑似甩锅句 |

脚本输出：五段页序完整度、每页结论句覆盖率、量化覆盖率、加权达成率、人均效能、页数与时长配比，以及缺页、堆工作量用语、甩锅句、指标无基线等提醒。

> 脚本只做结构与算术核查，**不判断你的目标定得合不合理、数据真不真实**。

## 九、人工确认清单（这步不能省）

- [ ] 五段页序齐全，结论在第 1 页
- [ ] 每页标题就是结论句
- [ ] 5-8 项指标，每项有目标值/实际值/来源
- [ ] 同比用的是上年同期，不是去年全年
- [ ] 越小越好类指标的达成率没算反
- [ ] 目标年中调过的已写明调整前后
- [ ] 所有数字都有来源，抽样写了样本量与区间
- [ ] 团队成果已写清人数、分工与自己承担的部分
- [ ] 已删除「积极参与」「认真负责」类无结果表述
- [ ] 问题页没有以「别的部门」「资源不足」作为结论句
- [ ] 页数与讲述时长匹配，每页讲述 ≤90 秒
- [ ] 图表数字与正文数字一致
- [ ] 涉及保密与未披露数据的已按公司口径脱敏
- [ ] 已交直属上级核过一遍数字口径

## 十、最常见的坑

**坑一：结论放最后一页。**
错误做法：先讲背景、再讲过程、最后给结论。正确做法：第 1 页就是结论，后面全是证据。**评委在第 5 页还没听到你想说什么。**

**坑二：把工作量当成果。**
错误做法：「参与项目 15 项，承担工作 300 天」。正确做法：「负责 A 模块，交付 X，节省 Y 人日」。**数量不是成果，评委只看到「做了很多事」，看不到「造成了什么变化」。**

**坑三：每页没有结论句。**
错误做法：标题写「项目进展」，正文列 8 条。正确做法：标题写「项目 A 按期交付，返工率下降 12%」。**评委只扫标题时也应该读懂这一页。**

**坑四：只报达成率不报同比。**
错误做法：达成率 104%，写得很底气。正确做法：先算同比。同比 -6% 却达成 104%，说明目标被调低了。**主动说明比被问出来好。**

**坑五：故障率类指标算反。**
错误做法：故障 25 → 18，写「达成率 72%」。正确做法：越小越好类 = 目标 ÷ 实际 = 20 ÷ 18 = 111%。**算反了会把漂亮的成绩写成未达标。**

**坑六：目标年中调过，只报调整后的。**
错误做法：年初 1500 年中改 1100，述职写「达成 109%」。正确做法：写明「年初 1500，因 XX 调整为 1100，实际 1200，调整后达成 109%」。**隐去调整属于口径操纵。**

**坑七：数据没有来源。**
错误做法：写「满意度提升 12%」但说不清怎么统计的。正确做法：注明「按季度问卷，样本 428 份」或「按客服工单台账统计，区间 2026-01 至 2026-12」。**没有来源的数字等于没写。**

**坑八：问题页全在甩锅。**
错误做法：「因产品需求频繁变更、测试资源不足，导致上线延期」。正确做法：归因落到自己能改的动作——「需求变更 3 次后我引入评审机制，后续变更影响下降 XX%」。

**坑九：一页讲了三分钟。**
错误做法：一页塞 8 条内容。正确做法：一页 1 个结论 + 最多 3 个支撑点，超时就拆页。**一页讲了超过 90 秒还讲不完，就是内容太多。**

**坑十：图表数字和正文数字不一致。**
错误做法：柱状图写 1200，正文写 1150。正确做法：定稿前逐页核对图表与正文数字。**评委发现一处不一致，会怀疑所有数字。**
