# MySQL 联合索引失效排查 · 能力概览

## 你会得到什么

一套能直接判定的口径，而不是「合理使用索引」这类废话。

**三条基准**：① 必须从最左列开始且连续不断；② 范围条件右侧全部截断（只能索引下推，不能减少扫描行数）；③ 索引列一旦被加工（套函数、隐式 CAST、算术运算）就失效。所有失效场景都能归到这三条里。

**具体到句式**：7 种 WHERE 组合对应「实际用到第几列」的对照表；`(tenant_id, create_time, status)` 与 `(tenant_id, status, create_time)` 为什么差一个量级；`IN` 不算范围截断而 `BETWEEN` 算；`LIKE 'abc%'` 能走而 `'%abc'` 不能，以及后缀匹配怎么救（反向列 + 函数索引）、包含匹配怎么救（FULLTEXT）；`IS NULL` **能**走索引而 `!=` / `NOT IN` 走不了——这两条经常被搞反。

**容易忽略的部分**：隐式类型转换的方向性（数字列给字符串没事，字符串列给数字必挂）、ORDER BY 顺序与 ASC/DESC 混用导致的 filesort、联表字符集不一致导致被转换侧失效、`SELECT *` 怎么把覆盖索引扼杀掉、深分页为什么线性变慢。

**脚本**：`scripts/composite_index_check.py` 吃 `INDEX name (a,b,c)` 声明加任意条 SQL，逐列推演实际可用列并给出截断原因，同时扫出注意力清单：`SELECT *`、OR、列上算术、深分页、ORDER BY 不一致、GROUP BY 临时表。

## 典型用法

1. 「索引明明建了为什么不走」：拿 SHOW CREATE TABLE 的定义，配实际 SQL 跑一遍，先看缺哪一列。
2. 设计新索引：把候选列顺序填进去，用 range/等值混合的真实 WHERE 验证右侧是否被截断。
3. Review 别人的 SQL：跑静态检查，重点看隐式转换与列参与运算。
4. key_len 对不上：用脚本推断的列数对比 EXPLAIN 的 key_len，定位优化器与预期不同的原因。

## 边界

- 静态推演不等于优化器结果，最终以 EXPLAIN / EXPLAIN ANALYZE 为准
- MySQL 5.6 / 5.7 / 8.0 在跳跃扫描、降序索引、直方图上差异明显
- 增删索引影响写入性能与磁盘，生产变更前先在预发验证
- 索引优化替代不了数据归档与容量治理，数据量级失控要考虑分区或分库分表
