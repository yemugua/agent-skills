# 埋点方案设计与校验 · 能力概览

## 你会得到什么

**埋点清单六要素，每项写明填写标准和缺失后果。** 事件名、触发时机、属性、上报时机、优先级、去重规则。其中**上报时机**最常被写成「实时」，实际上必须精确到「立即/批量/结束时」——因为它直接决定去重策略和丢数风险。

**曝光与点击时机对照表，把最容易搞混的一处钉死。** 列表曝光是「进入视口 ≥50% 且停留 ≥500ms」而不是「渲染即报」；**接口请求发出不算成功，必须在成功回调里上报**——否则成功率永远接近 100%，线上接口大面积失败也看不出来。

**一个藏得很深的错误：曝光去重而点击不去重。** 同一 item 曝光报 1 次、点击报 3 次，转化率算出 300%。分子分母的去重口径必须一致，这是最难自查的一类 bug。

**去重上报三方案与端职责分工。** 曝光类用端内去重、转化类用服务端上报、不去重只用于天然幂等动作。最重要的一条是**同一次行为只在一端上报**——端报点击、服务端报成功，混在一起算点击转化必然错。

**命名规范与「埋点名不含界面文案」这条硬规则。** 运营把「立即购买」改成「马上抢」，埋点名跟着改，历史数据就断了。

**联调三方对账法与阈值。** 抓包 / 端上日志 / 服务端入库三方比对，差异 ≤1% 才通过，量级合理性 ≤20%。抓包必查三项：请求是否真的发出、字段值是否正确、有没有重复请求。

**灰度期按版本分组核对。** 新埋点只在新版本上报，灰度 10% 时按总量统计会以为「丢了 90%」——这是灰度期最常见的误判。

## 典型用法

1. 提埋点需求：用模板填六要素，特别把触发时机和上报时机写死。
2. 联调验收：三方对账，差异 ≤1% 才算通过。
3. 「转化率怎么这么高」：按排查顺序走一遍，五步之内通常能定位。
4. 排查数据对不上：对照丢数六个原因，重点查版本灰度与去重口径。

## 边界

- 给出的是设计规范与校验方法，视口比例、停留时长等参数需结合业务场景调整
- 涉及个人信息采集与传输须做合规评估，以现行规定和主管部门要求为准
- SDK 选型与存储策略超出本技能范围
- 历史数据补数会影响已产出报表，须人工决策并留痕，本技能不代为执行
- 埋点业务口径须与业务方确认后写入指标字典
