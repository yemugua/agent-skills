# 埋点方案设计与校验（event-tracking-design）

埋点出错的代价不是「少一个数」，而是**这个数被拿去做决策之后才发现它一直是错的**。
更糟的是错得很有规律：曝光埋成了点击，转化率会稳定偏高，永远发现不了。

这个技能做三件事：**写清单** → **定时机** → **三方对账**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出埋点清单六要素与填写标准 | ❌ 代替业务方确定「什么算一次有效曝光」 |
| 给出曝光/点击的上报时机差异与选择依据 | ❌ 保证埋点上线后一定不丢（须实际对账） |
| 提供命名规范与重复检测 | ❌ 直接修改客户端或服务端代码 |
| 给出三方对账方法与验收阈值 | ❌ 处理需要补数据的历史缺口（须人工决策） |
| 列出埋点丢失与重复的常见原因 | ❌ 替代数据质量监控与告警建设 |

**以下情况必须先做别的：**
- 埋点方案还没和业务方对齐「什么算一次转化」 → 先对齐口径，再写清单
- 客户端与服务端埋点职责没划分 → 先定「同一次行为只在一端上报」
- 涉及用户个人信息的属性 → 先做合规评估，**以现行规定和主管部门要求为准**

## 二、完整工作流

```
第 1 步  读规则文件 rules/tracking_spec.md（六要素、时机表、去重方案、对账法）
第 2 步  与业务方对齐口径：什么算曝光？什么算点击？什么算转化？
         这三件事没对齐就开始写代码，后面必然返工
第 3 步  划分端职责：同一次行为只在一端上报（端内触发 → 端上报；
         服务端结果 → 服务端上报，不两边都报）
第 4 步  写埋点清单，每条填满六要素
第 5 步  跑完备性校验
         python scripts/tracking_check.py --file events.csv
         → 输出 缺要素/命名违规/时机不合理/去重缺失 四类分级问题
第 6 步  开发完成后做三方对账（见第九节）
         抓包 vs 端上日志 vs 服务端入库，差异 >1% 则不通过
第 7 步  上线后 T+1 复核：端上上报量 vs 入库量 vs 业务预期量级
```

## 三、埋点清单六要素

| # | 要素 | 填写标准 | 缺失后果 |
|---|---|---|---|
| 1 | **事件名** | 规范命名，全局唯一，不随文案变化 | 改个按钮文案就要改埋点名 |
| 2 | **触发时机** | 精确到「什么条件下触发」 | 曝光与点击时机搞混，转化率失真 |
| 3 | **属性** | 属性名 + 类型 + 取值范围 + 是否必填 | 后续加维度要重新发版 |
| 4 | **上报时机** | 立即上报 / 批量上报 / 结束时上报 | 丢失时机决定去重策略 |
| 5 | **优先级** | P0 必须 / P1 重要 / P2 可选 | 上线后才发现漏了 P0 |
| 6 | **去重规则** | 是否去重 + 去重键 + 去重周期 | 重复上报，数据虚高 |

**属性设计的三个硬要求：**

| 要求 | 说明 |
|---|---|
| 提前枚举 | 枚举类属性（如页面来源、失败原因）必须提前列出全量取值，不能上线后加 |
| 维度可下钻 | 每个埋点至少预留渠道、端、版本、用户分群四个维度属性 |
| 敏感信息不落 | 手机号、身份证、银行卡等**不进埋点属性**，只传脱敏 ID 或加密串 |

## 四、曝光与点击的上报时机（最容易搞混的一处）

| 场景 | 正确时机 | 错误做法 | 后果 |
|---|---|---|---|
| **列表曝光** | 元素进入视口且**停留 ≥N 毫秒**（如 500ms） | 元素渲染即上报 | 快速滑动时大量假曝光，曝光率虚高 |
| **曝光计数** | 按 **item_id 去重**，同一次会话内同一 item 只报一次 | 每次进入视口都报 | 滚动来回时曝光翻倍 |
| **点击** | 用户触发交互时**立即**上报 | 延迟到页面跳转后报 | 跳转失败则丢失 |
| **页面访问** | 页面真正渲染完成（`onLoad` + 首屏渲染） | 进入路由即上报 | 加载失败也算访问 |
| **结果上报** | 接口**成功回调**后上报 | 请求发出即上报 | 把失败当成功，成功率虚高 |

> **铁律：接口请求发出不算成功，必须在成功回调里上报。** 「请求发出」上报会让成功率永远接近 100%，线上接口大面积失败也看不出来。

**列表曝光的三个配套参数（必须同时定）：**

| 参数 | 建议值 | 说明 |
|---|---|---|
| 触发视口比例 | ≥ 50% 元素可见 | 露一条边不算曝光 |
| 最短停留时长 | ≥ 500ms | 防止快速滑动误报 |
| 去重键 | `item_id + session_id` | 同会话内不重复 |

---

## 五、去重上报三方案

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **端内去重** | 客户端维护已上报集合 | 省流量，不重复上报 | 占内存，重启丢失，跨端不去重 | 曝光类埋点 |
| **服务端去重** | 服务端按唯一键去重 | 口径唯一，跨端可靠 | 服务端压力 | 关键转化埋点 |
| **不重不漏** | 上报即认为有效 | 简单 | 必然有重复 | 天然幂等的动作（下单成功） |

**选择原则：**
- **曝光类**（会重复触发的）→ 必须去重，用端内去重 + 服务端兜底
- **转化类**（一次性的）→ 服务端上报，不去重（服务端天然只成功一次）
- **绝对不要**同一次行为在端和服务端各报一次

## 六、命名规范

```
格式：  业务域_对象_动作_位置
示例：  trade_order_submit_cart_button
       content_video_play_start
       user_profile_click_avatar
```

| 规则 | ❌ | ✅ |
|---|---|---|
| 全小写 + 下划线 | `ClickButton` | `click_button` |
| 不含中文与空格 | `点击 按钮` | `click_button` |
| 不含文案 | `buy_now_btn` | `trade_order_submit_button` |
| 动宾结构 | `order_button` | `order_click_submit` |
| 位置必带 | `click` | `click_submit_button` |

**一条硬规则：埋点名不能包含界面文案。** 运营把「立即购买」改成「马上抢」，埋点名跟着变，历史数据就断了。

## 七、埋点丢失与重复的六个常见原因

| # | 原因 | 表现 | 检查方法 |
|---|---|---|---|
| 1 | **用户提前退出** | 页面停留时间短的会话丢数据 | 对比页面停留时长分布 |
| 2 | **App 被杀/闪退** | 内存中的队列未上报 | 看崩溃率与丢报时间的相关性 |
| 3 | **网络中断** | 弱网下队列未 flush | 看弱网会话的数据缺口 |
| 4 | **上报时机太晚** | 结束才上报，用户已退出 | 改为关键节点立即上报 |
| 5 | **版本灰度不一致** | 老版本没有新埋点 | 按版本分组核对上报量 |
| 6 | **去重规则不一致** | 端与端规则不同 | 检查各端去重实现 |

**第 5 条最容易在灰度期被忽略**：新埋点只在新版本上报，灰度 10% 时按总量统计会以为「丢了 90%」。**必须按版本分组核对。**

## 八、曝光转化率偏高的排查顺序

转化率 = 点击 / 曝光。如果转化率异常高（接近 100%），按顺序查：

```
1. 曝光埋点是否漏报？     → 对比曝光量与页面访问量
2. 曝光是否去重过度？     → 同一 item 只报一次，但滚动多次看到只算一次，
                            而点击可以多次 → 分子分母口径不匹配
3. 点击时机是否晚于曝光？ → 点击在曝光之前也算，两者顺序未约束
4. 曝光与点击是否同源？   → 端上报曝光、服务端上报点击，口径不一致
5. 分子分母的时间窗是否一致？ → 曝光当天、点击不限时间
```

> **第 2 条最隐蔽**：曝光按「会话+item」去重，点击不去重。同一个 item 曝光 1 次、点击 3 次，转化率 300%。**分子分母的去重口径必须一致。**

## 九、联调校验：三方对账法

```
        端上上报  ──┐
                    ├── 比对 ──→ 差异 ≤1% ?
        抓包结果  ──┤
                    │
        服务端入库 ──┘
```

| 环节 | 校验方法 | 阈值 |
|---|---|---|
| **端 → 网关** | 抓包（Charles/Fiddler/mitmproxy）看请求是否发出、字段是否正确 | 差异 ≤ 0.5% |
| **端 → 服务端** | 服务端入库量 vs 端上上报量 | 差异 ≤ 1% |
| **服务端 → 数仓** | 数仓分区记录数 vs 服务端落库数 | 差异 ≤ 1% |
| **量级合理性** | 端上上报量 vs 业务预期量级（如 PV/UV） | 差异 ≤ 20% |

**抓包时必查三项：**
1. **请求是否真的发出**（有些队列未 flush 就杀进程）
2. **字段值是否正确**（枚举值是否是预期的那个）
3. **重复请求**（滑动列表是否触发多次）

**验收清单：**

- [ ] 三方对账差异均 ≤1%
- [ ] 关键路径的埋点全部 P0 且已上线
- [ ] 枚举属性取值与设计一致
- [ ] 去重规则生效（重复操作只上报一次）
- [ ] 弱网与提前退出场景数据可接受
- [ ] 老版本（无新埋点）已单独标注，不计入异常
- [ ] 属性中无个人敏感信息

## 十、脚本用法

```bash
# 校验埋点清单
python scripts/tracking_check.py --file events.csv

# 检查命名规范与时机合理性
python scripts/tracking_check.py --file events.csv --check-naming --check-timing

# 检查去重规则
python scripts/tracking_check.py --file events.csv --check-dedup
```

**CSV 格式（`event` 与 `trigger` 两列必填）：**

| 列名 | 含义 | 必填 |
|---|---|---|
| `event` | 事件名 | ✅ |
| `trigger` | 触发时机描述 | ✅ |
| `report_timing` | 上报时机（立即/批量/结束） | ✅ |
| `properties` | 属性描述 | ✅ |
| `priority` | P0/P1/P2 | ✅ |
| `dedup_rule` | 去重规则 | ✅ |
| `owner` | 负责人 | 建议 |
| `platform` | ios/android/web/h5/server | 建议 |

脚本输出四类分级问题：
- **错误（ERROR）**：事件名缺失或重复、缺触发时机、缺上报时机、P0 缺去重规则
- **警示（WARN）**：命名不规范、曝光类埋点未标停留时长、结果类埋点时机为「请求发出」
- **提示（INFO）**：建议补负责人与平台

## 十一、人工确认清单（这步不能省）

- [ ] 曝光、点击、转化的业务口径与业务方对齐了吗？
- [ ] 同一次行为只在**一端**上报，职责划分清楚了吗？
- [ ] 每条埋点的六个要素填全了吗？
- [ ] 列表曝光定了视口比例、停留时长、去重键三个参数吗？
- [ ] 结果类埋点在**成功回调**里上报，而不是请求发出时？
- [ ] 分子分母（曝光与点击）的去重口径一致吗？
- [ ] 枚举属性的取值枚举全了吗？
- [ ] 属性里有没有个人敏感信息？
- [ ] 三方对账做了吗？差异多少？
- [ ] 按版本分组核对过吗？（灰度期老版本没有新埋点）
- [ ] 弱网、提前退出、闪退场景验证过吗？
- [ ] 灰度期间的低上报量归因清楚了吗？

## 十二、最常见的坑

**坑一：曝光埋点用「请求发出」而不是「成功回调」。**
成功率永远接近 100%，线上接口大面积失败也看不出来。**结果类埋点必须在成功回调里上报。**

**坑二：列表曝光不做停留时长限制。**
用户快速滑动列表，每个元素露 50ms 就触发曝光，曝光量翻十倍，转化率被压到接近 0。**必须加 ≥500ms 停留时长 + ≥50% 可见比例。**

**坑三：曝光去重、点击不去重。**
同一 item 曝光报 1 次、点击报 3 次，转化率 300%。**分子分母的去重口径必须一致**，这是最容易藏住的错误。

**坑四：埋点名里含界面文案。**
运营把「立即购买」改成「马上抢」，埋点名跟着改，历史数据断掉。**埋点名只描述动作与位置，不含文案。**

**坑五：端和服务端各报一次。**
端上报「点击了提交按钮」，服务端上报「下单成功」，分析时算「点击转化」会把这两个数混在一起。**同一次行为只在一端上报。**

**坑六：App 被杀导致队列未上报。**
用户在提交页停留 2 秒后杀掉 App，队列里 10 条数据全丢。关键节点应该**立即上报**而不是攒着批量发。

**坑七：灰度期按总量统计，误判为埋点丢失。**
新埋点只在新版本上报，灰度 10% 时总量看起来「丢了 90%」。**必须按版本分组核对。**

**坑八：属性没提前枚举。**
失败原因只在联调时想到两个值，上线后出现第三个值就存不进去，分析时全被归到「其他」。**枚举类属性必须提前列全。**

**坑九：把个人敏感信息放进埋点属性。**
传了手机号、地址、身份证。**埋点属性只传脱敏 ID 或加密串**，且涉及个人信息的采集须做合规评估，以现行规定和主管部门要求为准。

**坑十：曝光与点击的时间窗不一致。**
曝光统计「当天」，点击统计「不限时间」，转化率必然虚高。**分子分母的时间窗必须一致。**

**坑十一：去重键选得不对。**
用 `user_id` 去重，用户今天点 3 次只算 1 次；用 `timestamp` 去重，等于没去重。**去重键要匹配业务语义**（如「会话+item」表示「本次会话看到并点了这个商品」）。

**坑十二：埋点上线没人验收。**
上线后没人对账，一周后做分析才发现埋点根本没上报。**上线验收必须包含三方对账，差异 ≤1% 才算通过。**

## 十三、边界与免责

- 本技能给出的是**埋点设计规范与校验方法**，具体埋点参数（视口比例、停留时长）需结合业务场景调整
- 涉及用户个人信息采集与传输的，须做合规评估并遵守本单位要求，**以现行规定和主管部门要求为准**
- 端与服务的具体实现（SDK 选型、存储策略）超出本技能范围
- 历史数据缺口的补数会**影响已产出报表**，须人工决策并留痕，本技能不代为执行
- 埋点的业务口径（什么算「有效曝光」）须与业务方确认后写入指标字典
