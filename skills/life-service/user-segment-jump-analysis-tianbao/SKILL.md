# 用户分层跃迁分析核查（user-segment-jump-analysis）

跃迁分析最有价值的一句话不是「多少人升层了」，
而是「**哪一层的用户正在漏向下一层**」。

难点在于：**跃迁率是个纯口径产物**。阈值动一下、窗口变一下，
升层率能从 12% 变成 8%，而真实用户行为一点没变。

这个技能做三件事：**定口径** → **算跃迁** → **验恒等式**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出跃迁矩阵四要素与三条恒等式校验 | ❌ 代替业务方定义分层规则与阈值 |
| 计算升层率/降层率/层内留存率/跨层跃迁率 | ❌ 判定分层规则本身是否合理（那是业务决策） |
| 检查阈值漂移、窗口不等长、去重不一致 | ❌ 直接给出分层阈值应该设成多少 |
| 说明跃迁率与留存率的关系与换算 | ❌ 把跃迁当成因果（用户升层未必因某次运营） |
| 定位流失贡献最大的层间通道 | ❌ 预测未来跃迁或给出跃迁提升方案 |

**以下情况必须先做别的：**
- 分层阈值在上期和本期之间被改过 → **历史数据必须按新阈值重算**，否则无法比较
- 分层依据是行为数据（如 RFM）→ 必须先固定观察窗口，否则每期分层依据不同
- 用户规模过小（某层 < 100 人）→ 跃迁率波动大，不能作为结论

## 二、完整工作流

```
第 1 步  读规则文件 rules/transition_rules.md（四要素、恒等式、阈值表、漂移信号）
第 2 步  冻结四件事（缺一件就不能出数）：
         ① 分层规则与阈值（本期与上期必须同一套）
         ② 本期/上期的分层时点（必须是同一时刻类型的两个截面）
         ③ 观察窗口（分层依据的行为数据窗口是否等长）
         ④ 去重口径（用户 ID 归并规则是否一致）
第 3 步  算跃迁矩阵并做恒等式校验
         python scripts/transition_audit.py --file transition.csv \
             --layers "S4,S3,S2,S1" --prev-col prev_layer --cur-col cur_layer
第 4 步  校验三条恒等式（脚本自动做）：
         行和 = 本期各层人数；列和 = 上期各层人数；
         层内留存率 + 跨层迁出率 = 100%
第 5 步  定位漏损通道：找出「迁出绝对人数最多」的层间路径
         （不是迁出率最高的——见第五节）
第 6 步  交叉验证：把跃迁结论与同期运营动作、版本发布对齐，无对应动作
         则只报事实不报因果
```

## 三、跃迁矩阵四要素

| 要素 | 要求 | 违反后果 |
|---|---|---|
| **① 分层规则与阈值** | 同一套规则与阈值用于本期和上期 | 数字全是假的（口径漂移） |
| **② 两个分层截面** | 「上期分层」和「本期分层」必须来自同一类时刻 | 跨类型比较无意义 |
| **③ 观察窗口** | 两期分层依据的行为数据窗口必须等长 | 活跃层虚高 |
| **④ 去重口径** | 用户 ID 归并规则一致；跨端已合并 | 人数不可比 |

**上期/本期的标准定义：**
- 上期分层 = 「上一周期末」这一时刻的用户所处层级
- 本期分层 = 「本周期末」这一时刻的用户所处层级
- 跃迁矩阵的每一行/列都是**用户数**，不是占比

---

## 四、跃迁率四种定义（写报告时必须区分）

设跃迁矩阵 `M[i][j]` = 上期在层 i、本期在层 j 的用户数。

```
升层率(从 i 升到 j>i) = M[i][j] / Σ_j M[i][j]      分母是上期层 i 的总人数
降层率(从 i 降到 j<i) = M[i][j] / Σ_j M[i][j]      分母同上
层内留存率(i)         = M[i][i] / Σ_j M[i][j]      人没换层
跨层迁出率(i)         = 1 − 层内留存率(i)
整体升层率            = Σ_{i<j} M[i][j] / Σ_{i,j} M[i][j]   分母是全部用户
净升层率              = 整体升层率 − 整体降层率
```

| 指标 | 分母 | 用途 | 陷阱 |
|---|---|---|---|
| 升层率/降层率 | 上期层 i 人数 | 分析单层的进出 | 小层人数少时波动大 |
| 层内留存率 | 上期层 i 人数 | 看该层用户「留住了多少」 | **不是留存分析里的留存**，见第六节 |
| 整体升层率 | 全部用户 | 汇报总体健康度 | 掩盖分层间的差异 |
| 净升层率 | 全部用户 | 比较两期升降是否平衡 | 净值为正不代表分层健康 |

**三条恒等式（脚本自动校验）：**

```
恒等式 1：Σ_j M[i][j] = 上期层 i 的总人数          （行和）
恒等式 2：Σ_i M[i][j] = 本期层 j 的总人数          （列和）
恒等式 3：层内留存率(i) + 跨层迁出率(i) = 100%
```

对不上 → **先查口径，绝不先查业务**。

---

## 五、定位漏损通道（按绝对人数，不按率）

**错误做法**：找迁出率最高的那一层去优化。
**正确做法**：按**迁出绝对人数**排序。

```
通道迁出人数(i→j)      = M[i][j]              (j < i，即降层)
通道占该层比(i→j)       = M[i][j] / Σ_j M[i][j]
通道占总降层比(i→j)     = M[i][j] / Σ_{i,j< i} M[i][j]
```

**判定阈值：**

| 指标 | 优先处理 | 次优先 | 暂不处理 |
|---|---|---|---|
| 通道占总降层比 | **≥ 20%** | 8%–20% | < 8% |
| 通道迁出人数 | ≥ 100 人 | 30–100 人 | < 30 人 |

> 例：S4→S3 迁出 800 人（占总降层 45%，S4 层共 1000 人迁出率 80%）vs S2→S1 迁出 120 人（占总降层 7%）。**前者优先**，虽然它的层内迁移可能只是正常下沉（用户生命周期），需要结合业务判断；后者虽然率低，但绝对人数小。

## 六、跃迁率与留存率的关系（容易混）

| 指标 | 所属分析 | 定义 | 分母 |
|---|---|---|---|
| **层内留存率** | 跃迁分析 | 上一期在层 i、本期仍在层 i 的人 / 上期层 i 人数 | 上期层人数 |
| **N 日留存率** | 留存分析 | 第 N 天活跃的用户 / 队列人数 | 队列人数 |

**两者可以互推（当分层依据就是「本期是否活跃」时）：**

```
层内留存率(i) ≈ 该层用户的 N 日留存率
```

但**只是近似**：分层依据可能是 RFM（近 M 个月消费次数 × 近 R 个月最近消费），而留存只问「活跃与否」。用户可能 RFM 层级没变但活跃天数不足，或层级降了但仍活跃。

**必须说明**：报告里的「层内留存率」是跃迁矩阵里的概念，**不要直接等同于留存分析里的 D7/D30 留存率**，除非分层规则明确就是按活跃定义的。

## 七、口径漂移的四个识别信号

| # | 信号 | 表现 | 处置 |
|---|---|---|---|
| 1 | **阈值被改** | 新版分层规则上线，历史数据用旧规则算过 | **全部历史数据按新规则重算**，或显式标注断点 |
| 2 | **未分层用户被丢弃** | 各层人数之和 ≠ 总用户数 | 未分层用户单独成层（U 层），不要静默丢弃 |
| 3 | **窗口不等长** | 上期用 30 天行为、本期用 14 天 | 统一窗口后重算 |
| 4 | **去重口径变化** | 跨端归并规则改过（如新增小程序） | 同口径重算或标注断点 |

**最隐蔽的是第 1 和第 2。** 阈值改了但历史没重算，跃迁矩阵里会出现大量「升层」——其实只是新规则把用户重新归类了。**判断方法：如果某层人数突然剧烈变化而业务上无对应事件，优先怀疑口径漂移。**

## 八、脚本用法

```bash
# 计算跃迁矩阵并校验
python scripts/transition_audit.py --file transition.csv \
    --layers "S4,S3,S2,S1" --prev-col prev_layer --cur-col cur_layer

# 指定总人数（校验各层之和是否覆盖全部用户）
python scripts/transition_audit.py --file transition.csv \
    --layers "S4,S3,S2,S1" --total-users 50000

# 检查口径漂移四类信号
python scripts/transition_audit.py --file transition.csv \
    --layers "S4,S3,S2,S1" --check-drift \
    --threshold-version v1 --prev-window 30d --cur-window 30d
```

**CSV 格式（两列必填）：**

| 列名 | 含义 |
|---|---|
| `prev_layer` | 上期所属层（需与 `--layers` 中的值一致） |
| `cur_layer` | 本期所属层 |
| `users` | 该组合的用户数（若 CSV 是逐用户明细，此列可省略，按行计数） |

`--layers` 从**高到低**排列（如 `S4,S3,S2,S1`），脚本据此判断升层/降层方向。

脚本输出：跃迁矩阵、各层升层率/降层率/层内留存率、整体升层率与净升层率、漏损通道排序（按占总降层比）、三条恒等式校验结果、口径漂移诊断。

## 九、人工确认清单（这步不能省）

- [ ] 本期与上期用的是**同一套分层规则和阈值**吗？
- [ ] 上期分层是「上一周期末」的截面吗？截面类型与本期一致吗？
- [ ] 两期的行为观察窗口**等长**吗？
- [ ] 去重口径一致吗？跨端归并规则有没有变？
- [ ] 未分层用户怎么处理？各层人数之和等于总用户数吗？
- [ ] 阈值改过吗？改过的话历史数据重算了吗，还是标了断点？
- [ ] 跃迁率的**分母**写清了吗（上期层人数 vs 全部用户）？
- [ ] 定位漏损用的是**绝对人数**还是迁出率？
- [ ] 样本量够吗？各层迁出人数 < 30 的通道不作为优化依据？
- [ ] 结论是描述（谁降了）还是因果（因为某次运营所以降了）？
- [ ] 「层内留存率」有没有被误当成留存分析里的 D7/D30？

## 十、最常见的坑

**坑一：改了阈值却没重算历史数据。**
旧规则把「近 90 天消费 5 次以上」算 S4，新规则改成「近 60 天消费 3 次以上」。历史数据没重算，跃迁矩阵里 S4→S3 突然多出几万人，全是规则变化不是用户行为。**阈值一改，历史必须全部重算。**

**坑二：未分层用户被静默丢弃。**
各层人数加起来只有 92% 的用户，剩下 8%（数据不足、未消费、未注册完成）不见了。跃迁矩阵的分母变成了「已分层用户」，升层率虚高。**未分层用户必须单独成层（U 层）并在报告中出现。**

**坑三：按迁出率最高挑通道，忽略了绝对人数。**
S4 迁出率 80%（800 人）、S2 迁出率 5%（120 人）。按率挑会选 S4，但 S4 的下沉可能只是用户生命周期的正常流转。**必须看绝对人数和占总降层的比例，两个一起看。**

**坑四：把层内留存率当成留存率的 D7。**
「S4 层留存率 78%」——这是「上期在 S4、本期还在 S4」的比例，和「这批用户第 7 天还活跃吗」完全是两回事。RFM 分层里两者可能差很多。**报告里必须写清「层内留存率（跃迁）」而不是「留存率」。**

**坑五：两期观察窗口不等长。**
上期用「近 30 天」判定活跃，本期因为数据延迟只能用「近 14 天」。活跃层人数凭空少一大截，全员「降层」。**窗口不等长是跃迁分析最严重的口径错误。**

**坑六：跃迁率的分母没写清。**
「升层率 15%」——分母是全部用户还是上期某层？两种算法能差好几倍。**每次写跃迁率必须带分母：「S3 升层率（S3 上期人数为分母）15%」。**

**坑七：把跃迁当成因果。**
某次运营后升层率从 8% 涨到 12%，说「运营活动提升了用户分层」。但同期也上了新版本、渠道结构也变了。**跃迁是同期观察，不是实验**。要证明因果必须有对照组。

**坑八：忽略「不变」这个最大的格子。**
跃迁矩阵里对角线（层内不变）通常占 60–80%，是最健康的部分。很多分析只盯着跨层格子，忽略了「绝大多数用户本来就稳定」这个事实，导致过度解读小幅变动。

**坑九：小层样本量不足。**
某层只有 40 人，掉 5 个人就是 12.5% 迁出率。**迁出人数 < 30 的通道不作为优化依据**，报告里必须标注。

**坑十：跨端去重规则变了 unnoticed。**
上期只有 App 数据，本期接入了小程序，同一用户被算两次，本期各层人数虚增，全员看起来「升层」。**去重口径变更属于口径漂移，必须重算或标断点。**

## 十一、边界与免责

- 跃迁分析是**同期观察性分析**，描述「谁换了层」，不能证明「因为什么换了层」
- 分层规则本身的合理性（阈值取值、层数）是业务决策，本技能不给出推荐阈值
- RFM 等基于行为窗口的分层，其「层内不变」不等价于用户满意，可能只是行为频次未跨阈值
- 分层阈值变更属于口径变更，跨断点的数据不可直接比较，须以现行口径重算
- 涉及用户标识合并与用户级分层数据，须遵守本单位数据合规要求，**以现行规定和主管部门要求为准**
