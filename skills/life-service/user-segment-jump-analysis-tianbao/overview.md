# 用户分层跃迁分析核查 · 能力概览

## 你会得到什么

**三条恒等式当校验器。** 跃迁矩阵的行和应等于上期各层人数，列和应等于本期各层人数，层内留存率加跨层迁出率应等于 100%。任何一条对不上都是**口径问题**，不要先怀疑业务。脚本每次自动校验这三条。

**升层率/降层率的分母写清就不怕吵。** 单层升层率的分母是「上期该层人数」，整体升层率的分母是「全部用户」——两种算法能差好几倍。报告里每次写跃迁率都要带分母。

**定位漏损按绝对人数，不按率。** S4 迁出率 80%（800 人）vs S2 迁出率 5%（120 人）：只看率会选前者，但前者可能只是用户生命周期的正常下沉。判定阈值给到「占总降层比 ≥20% 且迁出人数 ≥100」双条件，小于 30 人的通道明确标注不作优化依据。

**口径漂移的四个识别信号。** 阈值改版未重算历史（最隐蔽，表现为大量假「升层」）、未分层用户被静默丢弃（分母变成「已分层用户」，升层率虚高）、两期观察窗口不等长（全员假降层）、跨端去重规则变更（本期各层人数虚增）。处置方式分三种：可重算就重算，不可重算就标断点，层名改而阈值没改才能直接比。

**层内留存率 ≠ 留存分析的 D7。** 层内留存率是「上期在 S4、本期还在 S4」的比例；D7 是「第 7 天还活跃吗」。只有分层依据恰好是「本期是否活跃」时两者才近似。报告里必须写「层内留存率（跃迁口径）」。

## 典型用法

1. 升层率从 12% 掉到 8%：先查阈值有没有改、窗口是否等长、去重口径是否变化，再看业务。
2. 定位该救哪层：跑脚本拿到通道排序，按「占总降层比 + 绝对人数」双条件选。
3. 和别人的跃迁数对不上：三条恒等式 + 分母约定 + 未分层用户处理方式，三处最容易产生差异。
4. 团队规范：把跃迁矩阵模板（必含口径冻结四行 + 恒等式校验位）贴进 wiki。

## 边界

- 跃迁是**同期观察**不是实验，描述「谁换了层」但不证明「因为什么换了层」
- 分层规则与阈值取值是业务决策，本技能不推荐具体阈值
- RFM 分层的「层内不变」不等价于用户满意，可能只是频次未跨阈值
- 阈值变更属口径变更，跨断点数据不可直接比较，须以现行口径重算
- 用户级分层数据与标识合并须遵守本单位数据合规要求，以现行规定和主管部门要求为准
