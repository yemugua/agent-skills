# 服务器巡检阈值表与判定口径

本文件是 `server-daily-inspection` 的核心资产。**生成巡检表、配置告警、写报告前先读本文件，不要凭印象写阈值。**

---

## 一、Linux 通用阈值表

### 1.1 CPU

| 指标 | 采集命令 | 正常 | 关注 | 告警 |
|---|---|---|---|---|
| CPU 整体使用率 | `top -bn1 \| grep '%Cpu'` 的 `100 - %id` | < 70% | 70–85% | > 85% |
| 用户态 `us` | 同上 | < 55% | 55–75% | > 75% |
| 系统态 `sy` | 同上 | < 15% | 15–25% | > 25% |
| IO 等待 `wa` | `vmstat 1 5` 第 3 列 | < 10% | 10–25% | > 25% |
| 单核最高使用率 | `mpstat -P ALL 1 3` | < 70% | 70–90% | > 90% |
| 上下文切换率 | `vmstat 1 5` 的 `cs` 列 | < 20k/s | 20k–50k/s | > 50k/s |
| 硬中断率 | `vmstat 1 5` 的 `in` 列 | < 10k/s | 10k–30k/s | > 30k/s |

**判定口径**

- 「持续」= 连续 3 个采集周期都越线，或用 `sar -u 1 60` 确认 5 分钟以上
- `sy > 25%` 且 `cs` 同时很高 → 优先查**系统调用/中断风暴**，不是业务代码慢
- 单核打满而整体不高 → 查是否单线程程序没做并发、是否有正则回溯、是否有 GC 停顿集中在一核

### 1.2 负载

| 指标 | 采集命令 | 正常 | 关注 | 告警 |
|---|---|---|---|---|
| load1 / 核数 | `cat /proc/loadavg` | < 0.7 | 0.7–1.0 | > 1.0 |
| load5 / 核数 | 同上 | < 0.7 | 0.7–1.0 | > 1.0 |
| load15 / 核数 | 同上 | < 0.7 | 0.7–1.0 | > 1.0 |
| 运行队列 `r` | `vmstat 1 5` 第 1 列 | ≤ 核数 | 核数+1 ~ 2×核数 | > 2×核数 |
| 阻塞队列 `b` | `vmstat 1 5` 第 2 列 | 0 | 1–3 | > 3 |

**判定口径（关键）**

`load average` 统计的是**运行中 + 不可中断睡眠（D 状态）**的任务数。所以：

| 现象 | 结论 | 下一步 |
|---|---|---|
| load 高，`us+sy` 高，`b≈0` | **CPU 瓶颈** | 找 Top 进程、看火焰图 |
| load 高，`us+sy` 低，`b>0` | **IO 瓶颈** | 查磁盘 await、NFS、网络驱动 |
| load 高，`wa` 高 | 磁盘饱和 | `iostat -x` + `iotop` |
| load 高，`D` 状态进程是 `nfsd`/`rpc` | **NFS 卡住** | 查挂载点与服务端 |
| load 缓慢上涨后回落 | 正常批处理/定时任务 | 核对 cron 时点 |
| load 高但 CPU/IO 都闲 | 进程大量 fork 或状态异常 | `ps -eo stat,pid,comm \| awk '$1 ~ /D/'` |

### 1.3 内存

| 指标 | 采集命令 | 正常 | 关注 | 告警 |
|---|---|---|---|---|
| `available` 占 MemTotal | `free -m` | > 25% | 10–25% | < 10% |
| swap 使用率 | `free -m` | 0 | > 0 且 < 30% | > 30% |
| swap in/out 速率 | `vmstat 1 5` 的 `si`/`so` | < 1 KB/s | 1–100 KB/s | > 100 KB/s 持续 |
| OOM 次数（24h） | `journalctl -k \| grep -ci 'out of memory'` | 0 | 1 | ≥ 1 |
| 大页与 THP 失败 | `grep -i thp /proc/meminfo` | 正常 | — | `direct reclaim` 频繁 |

**判定口径**

- **看 `available`，不看 `free`。** `free` 低是缓存策略的正常结果
- swap 一旦被用上就**不再回落**是常态（内核不主动换出），所以更该看 `si`/`so` 速率而不是累计值
- `available < 10%` 且 `si/so` 持续 → **正在换页抖动**，此时延迟会显著上升，即使 CPU 很低
- `si`/`so` 高但 `b≈0` → 是内存压力导致的抖动，与磁盘 IO 饱和是两回事，别混判

### 1.4 磁盘与文件系统

| 指标 | 采集命令 | 正常 | 关注 | 告警 |
|---|---|---|---|---|
| 分区使用率 | `df -h` | < 70% | 70–85% | > 85% |
| 分区使用率（硬上限口径） | 同上 | — | — | > 90% 必须当日处理 |
| inode 使用率 | `df -i` | < 60% | 60–80% | > 80% |
| IO await | `iostat -x 1 3` | < 10 ms | 10–30 ms | > 30 ms |
| %util | 同上 | < 70% | 70–90% | > 90% |
| 读写吞吐 vs 盘标称 | 同上 | < 60% | 60–85% | > 85% |
| 挂载点 RO | `mount \| grep ' ro[,/]'` | 0 | — | ≥ 1 需确认 |
| SMART 状态 | `smartctl -H /dev/sdX` | PASSED | — | FAILED |

**判定口径**

- **`df -h` 与 `df -i` 必须成对执行。** 报错 `No space left on device` 但 `df -h` 有空间 → inode 用尽
- await 高而 %util 不高 → 是**平均排队深度**问题（并发小请求多），调大队列深度往往比换盘有效
- %util 接近 100% 表示设备已饱和，新增 IO 只会拉长延迟
- 云盘/网络盘要看**基线**，IOPS 配额与突发额度不同，性能表现与物理盘差异大

### 1.5 网络与连接数

| 指标 | 采集命令 | 正常 | 关注 | 告警 |
|---|---|---|---|---|
| ESTABLISHED 数 | `ss -tan state established \| wc -l` | < 5000 | 5000–10000 | > 10000 |
| TIME-WAIT 数 | `ss -tan state time-wait \| wc -l` | < 2000 | 2000–5000 | > 5000 |
| `somaxconn` | `cat /proc/sys/net/core/somaxconn` | ≥ 4096 | 1024–4096 | < 1024 |
| 端口范围容量 | `cat /proc/sys/net/ipv4/ip_local_port_range` | ≥ 28000 | 15000–28000 | < 15000 |
| 网卡丢包/错误 | `ip -s link show eth0` | 0 | — | `errors` 或 `dropped` > 0 |
| 网卡队列丢包 | 同上 `RX dropped` | 0 | 1–100/分钟 | > 100/分钟 |

**判定口径**

- TIME-WAIT 堆积通常是**短连接高频**或没开连接池，不是「泄漏」
- 本机端口耗尽时症状是「连不上但服务端没拒绝」，日志报 `cannot assign requested address`
- `dropped` 上升说明**应用收包速度跟不上内核缓冲**，是 CPU/GC/网卡队列问题，不是链路问题

### 1.6 时钟与 NTP

| 指标 | 采集命令 | 正常 | 关注 | 告警 |
|---|---|---|---|---|
| 同步状态 | `timedatectl show -p NTPSynchronized` | yes | — | no |
| 与标准时偏移 | `chronyc tracking` 的 `System time` | < 1 秒 | 1–30 秒 | > 30 秒 |
| 偏移（严重） | 同上 | — | 30–120 秒 | > 120 秒 |
| 使用的时区 | `timedatectl show -p Timezone` | 业务时区 | — | UTC 且业务按本地时间 |

**判定口径**

- 偏移 > 120 秒时，**所有日志时间线都不可信**，跨主机比对日志会得出错误结论 —— 必须先修 NTP 再做其他分析
- 容器内时区与宿主机不一致会导致定时任务错位，检查镜像是否带 TZ
- 夏令时地区与不变时区地区混用会让「今天」的定义不一致

### 1.7 日志与错误

| 指标 | 采集命令 | 正常 | 关注 | 告警 |
|---|---|---|---|---|
| ERROR 级条数（24h） | `journalctl -p err --since "-24h" \| wc -l` | < 20 | 20–100 | > 100 |
| 失败的 systemd 单元 | `systemctl --failed` | 0 | — | ≥ 1 |
| 关键字命中 | `grep -iE 'oom\|I/O error\|segfault\|panic'` | 0 | — | ≥ 1 立即处理 |
| 日志目录增长 | `du -sh /var/log` | 周增长 < 20% | 20–50% | > 50% |

**判定口径**

- ERROR 条数要**按来源聚合**再看数量，200 条来自同一个必然失败的 cron 任务 ≠ 200 个不同问题
- 出现 `I/O error`、`EXT4-fs error`、`XFS metadata corruption`、`lost page` → 转存储/文件系统处理，**不要在线 fsck**
- `Out of memory: Killed process` → 必须记录被 kill 的进程名与 cgroup，这是 OOM 定性的关键
- `segfault` 反复出现在同一进程 → 转应用排查，不要重启了事

### 1.8 权限与访问合规（台账一致性核对）

这一类不做数值分级，而是**与本单位台账逐条核对一致性**。台账由账号管理台账、变更单与开放端口清单提供，
巡检只负责确认「机器上的现状 == 台账上的应有」，出现差异即转安全事件流程。

| 核对对象 | 核对方式（对照台账，不是现场抓取） | 期望 |
|---|---|---|
| 特权账号清单 | 与「特权账号授权台账」逐条比对 | 与台账完全一致，无未登记账号 |
| 账号口令策略 | 与「口令基线」核对策略项（有效期、长度、锁定阈值） | 全部符合基线要求 |
| 远程接入策略 | 与「远程接入基线」核对策略项 | 符合基线要求，无例外未登记 |
| 近期登录记录 | 与「授权来源地与账号清单」比对 | 无非授权来源、无非授权账号 |
| 计划任务清单 | 与「变更单 / 发布记录」比对 | 每条任务都有对应变更单 |
| 对外监听端口 | 与「开放端口台账」比对 | 与台账一致，无未登记对外端口 |

**这一类**不适用「正常/告警」分级，**发现差异直接转安全事件流程**。

> 为什么改成「对照台账」而不是给现场命令：这六项的判定基准是**本单位的管理台账**，不是机器本身。
> 巡检人按台账核对即可，账号与接入策略的实际修改统一走既有的账号申请与变更审批流程，巡检环节不介入变更。

## 二、按角色的阈值微调

| 角色 | CPU 告警 | 内存告警 | 磁盘告警 | 特有必查项 |
|---|---|---|---|---|
| `web` | > 80% 持续 10 分钟 | `available` < 15% | > 85% | 5xx 比例、连接池、上游超时 |
| `db` | > 85% 持续 5 分钟 | 缓冲池命中率 < 95% | > 80% | 慢查询、锁等待、主从延迟、binlog 堆积 |
| `middleware` | > 80% | > 85% | > 80% | 连接数、大 key、慢命令、持久化延迟 |
| `batch` | 不设告警 | 内存 > 90% 需评估 | > 80% | 任务成功率、运行时长对比基线 |
| `generic` | > 85% | `available` < 10% | > 85% | — |

> 数据库与中间件按通用阈值设告警**几乎必然误报**：它们的内存高是设计使然。阈值必须结合自身历史分位数（P95/P99）设定，而不是拍一个绝对值。

## 三、误判识别清单（看到现象先对照这里）

| 现象 | 容易误判为 | 实际结论 | 正确动作 |
|---|---|---|---|
| `free` 接近 0 | 内存不足 | 缓存占用正常 | 看 `available` |
| load 高 CPU 闲 | CPU 不足 | IO/NFS 阻塞 | 看 `vmstat` 的 `b` 列 |
| 磁盘没满但写不进去 | 磁盘满 | inode 用尽 | `df -i` |
| TCP 连接数高 | 连接泄漏 | 短连接/无连接池 | 看 TIME-WAIT 比例与 `ss -tan` |
| 日志突然暴涨 | 正常 | 某个服务在刷错误/循环重试 | 按来源聚合 `journalctl -u` |
| 某一核 CPU 高 | 整机 CPU 高 | 单线程/GC/正则回溯 | `mpstat -P ALL` |
| 容器内内存高 | 宿主机内存高 | cgroup 限额问题 | `docker stats` + cgroup 限额 |
| swap 使用率高 | 需要加内存 | 可能早已稳定，非实时压力 | 看 `vmstat` 的 `si`/`so` |
| 磁盘 `%util` 100% | 磁盘坏了 | 设备饱和 | 看 `await` 与队列深度 |
| NTP 未同步 | — | 日志时间线不可信 | 先修 NTP |

## 四、巡检频次建议

| 巡检类型 | 频次 | 内容 |
|---|---|---|
| 自动采集 | 1 分钟 | CPU、内存、磁盘、连接数（指标类） |
| 班次巡检 | 每班一次（8h） | 阈值判定 + 服务状态 + 日志 ERROR 聚合 |
| 每日巡检 | 每天一次 | 加：安全项、补丁、备份任务结果 |
| 每周巡检 | 每周一次 | 加：容量趋势、慢查询、账号与权限复核 |
| 每月巡检 | 每月一次 | 加：恢复演练、阈值基线校准、文档核对 |

**每日必查的三件事**：磁盘与 inode、备份任务是否成功、`systemctl --failed` 是否有失败单元。这三项漏掉最容易出大事。

## 五、巡检记录写法规范

| 字段 | 要求 |
|---|---|
| 采集时间 | 精确到分钟，带时区 |
| 指标值 | 原始数值 + 单位，不写「较高」 |
| 判定 | 正常 / 关注 / 告警 / 采集失败（四选一，不允许留空） |
| 证据 | 告警项必须附命令输出片段或日志行 |
| 处置动作 | 「动作 + 验证结果」，如「清理 journal 至 42%，复查 df -h 为 42%」 |
| 责任人 | 告警项必须有名字 |
| 关闭 | 写明关闭时间与关闭依据 |

**反模式：**

- ❌「网络正常」—— 不可执行、不可复核
- ❌「已处理」—— 没有动作也没有验证
- ❌「无异常」—— 没区分「检查过没问题」和「没检查」
- ✅「`ping 10.0.0.1` 20 次全通，平均 0.42 ms，丢包 0%」
- ✅「已清理 `/var/log/journal` 至 42%，复查 `df -h` 为 42%」
