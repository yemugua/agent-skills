# 服务器日常巡检清单与阈值核查 · 能力概览

## 你会得到什么

一份**能直接发给值班人执行**的巡检体系：不是「检查网络是否正常」这种没法落地、也没法复核的条目，而是每一项都带采集命令、具体阈值区间、判定依据和处置动作。

**阈值层面**：CPU（整体 / 用户态 / 系统态 / IO 等待 / 单核）、负载（load 比值 + 运行队列 + 阻塞队列三重口径）、内存（`available` 而非 `free`、swap 使用率与换页速率）、磁盘（容量与 inode 成对查、IO await 与 %util 分开看）、网络（连接数构成、网卡 dropped）、时钟（NTP 同步状态与偏移秒数）、日志（按来源聚合而非只看条数）、合规（特权账号、口令基线、远程接入策略、计划任务、开放端口的台账一致性核对）。每项都给出「正常 / 关注 / 告警」三档的具体数值，并按 web / db / middleware / batch / generic 五种角色做微调。

**判定层面**：脚本会识别那些**单项看起来都正常、组合起来才出事**的情况——负载高但 CPU 低（瓶颈其实在 IO 或 NFS，先加 CPU 是错的方向）、磁盘容量 38% 但 inode 93%（容量没满却写不进，报错却显示 No space left on device）、内存 available 偏低但 swap 未使用（真正的线索是内存泄漏）、TIME-WAIT 多于 ESTABLISHED（是短连接高频而非连接泄漏）。

**记录层面**：巡检记录表模板把「采集失败」设为独立一档，强制和「正常」区分开——命令报错、权限不足被填成 0，是巡检记录最常见的假闭环。

## 典型用法

1. 新机器上线前定阈值：填角色与核数，拿到该角色的完整阈值表与必查项清单。
2. 每日班次巡检：采集结果写成 `指标|数值` 一行一条，跑脚本出报告，直接贴进巡检表。
3. 告警集中爆发想快速定位：脚本的组合型异常规则会告诉你「这不是 CPU 问题」「这不是磁盘空间问题」。
4. 复核历史巡检记录：检查有没有把采集失败写成 0、有没有只写「已处理」而无验证结果。
5. 准备审计材料：巡检表模板的证据栏与处置汇总栏可直接对应审计口径。

## 边界

- 只做**阈值判定与记录整理**，不代替你在机器上执行命令，也不代替监控告警系统的阈值配置
- 阈值是通用起点，**同一台机器凌晨 3 点的 30% CPU 正常、早上 9 点的 30% 异常**，绝对阈值只适合兜底，告警最终要基于同机同时段的基线
- 出现 `I/O error`、文件系统损坏、阵列降级、SMART 失败、与台账不一致等情形，**立即转存储/硬件/安全专业处理**，不要按巡检流程自行在线修复
- 数据库与中间件按通用阈值设告警几乎必然误报，它们的高内存是设计使然，必须结合自身历史分位数设定
- 脚本做的是**静态检查**，不知道你这台机器的历史基线，也不判断业务是否真的受影响
