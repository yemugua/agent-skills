# 堡垒机部署与权限审计核查 · 能力概览

## 你会得到什么

一套能回答「这套堡垒机到底有没有用」的核查框架——因为堡垒机最大的失败不是装不上，而是**装了但运维照样直连**。

**部署形态层**：旁路 / 网关 / 代理 / 云原生四种形态的选型对照，以及每种形态的**安全前提**。其中最关键的一条：旁路模式唯一的价值来自「目标侧封堵直连」，不封堵就等于多了一个可选入口。

**权限模型层**：最小权限的四个维度（资产范围、命令范围、时间范围、数据范围、提权范围）、必须分离的五类职责（授权 vs 使用、审计 vs 操作、生产 vs 测试、应用账号 vs 人工账号、备份执行 vs 备份删除）、以及认证方式的强度阶梯。核心考核口径只有一条：**堡垒机账号数 ≥ 实际运维人数，共享账号 = 0**。

**审计能力层**：必须审计的四类行为（登录登出、命令操作、会话录像、文件传输）、十二条审计有效性自检项，以及留存期限参照表——并明确标注这是实践参照区间而非合规结论，具体期限以现行规定和本单位审计要求为准。

**拦截层**：高危命令清单（数据销毁、提权逃逸、历史清除、关审计、审计库篡改等）逐条对应防护手段，五层拦截强度对照，以及一个致命漏洞的识别——**`sudo su -` 进入新 shell 后命令过滤完全失效**，白名单里放了 `su`/`bash`/`-i` 的话，后面所有命令审计都是摆设。

**边界层**：VPN / 堡垒机 / 零信任三者的职责边界表。一句话结论：**VPN 通了不代表访问有审计；堡垒机上了不代表网络受控。**

## 典型用法

1. 上堡垒机前定方案：选形态、定权限矩阵、算清哪些资产纳管。
2. 审计说不合规：逐条对照验收清单，重点看 AllowUsers 误解、sudo 逃逸路径、共享账号三条。
3. 设计 sudo 白名单：用高危命令清单和提权逃逸清单逐条对照，确保没有任何能开启交互 shell 的路径。
4. 有人问「能不能直连服务器」：给出明确答案与验证方法（从非堡垒机网段 telnet 必须失败）。
5. 复核日志留存要求：区分「实践参照」和「合规结论」，避免用参照表对外承诺。

## 边界

- 只做**部署方案、配置口径与审计核查清单**，不代替现场部署实施、网络改造与合规认定
- 留存期限表是**实践参照区间，不是合规结论**，不得据此对外承诺合规
- 三权分立、强监管场景的具体设置要求**以现场合规要求为准**
- 不提供任何绕过审计的方法，也不建议用「紧急模式」长期规避管控
- 脚本读的是**配置文件文本，不是运行中的堡垒机**——它能告诉你配置有没有写错，但不能告诉你堡垒机是否真的在拦截、审计是否真的在录像，那两件事必须实测
- 权限变更、封堵端口等动作**必须经审批后由授权人员执行**并保留变更记录
