# 述职汇报撰写与业绩量化核查（performance-review-report）

述职被扣分，八成不是因为干得少，而是**说不清**：一堆「积极参与」「大幅提升」，评委听完不知道你到底把什么从多少变成了多少。

这个技能做三件事：**定四段结构** → **把业绩算成三个数** → **堵住自夸与甩锅两个坑**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出述职结构与四段字数配比 | ❌ 代替公司绩效考核制度与评级规则 |
| 按同比/环比/达成率三个口径核算业绩 | ❌ 替你编造没有发生过的数字 |
| 指出缺失基线、口径不清、定性词混入 | ❌ 代替与直属上级的目标确认 |
| 给出功劳表述与问题表述的安全写法 | ❌ 建议把团队成果写成个人成果 |
| 输出可直接照读的述职稿骨架 | ❌ 保证评级结果或晋升通过 |

**必须先停下来确认的情形：**
- 数据来自未上线、未验收或内部尚未确认的项目 —— **不得按已达成口径写**
- 涉及他人承担主要工作的成果 —— 必须写明角色与分工，不写「我负责」以外的模糊表述
- 涉及保密项目、未披露的财务数据 —— 按公司披露口径脱敏后再写
- 目标值是年中调整过的 —— 必须写明调整前后，只报调整后的目标属于**口径操纵**
- 与人力部门考核口径不一致时，**以公司制度与上级确认为准**

## 二、完整工作流

```
第 1 步  确认口径：考核周期、目标值来源（年初定 / 年中调）、公司评级维度
第 2 步  先读 rules/quantification_rules.md，再按 §1 选 5-8 项指标并配权重
第 3 步  收集每项指标的四个数：本期值、上年同期值、上一周期值、目标值
第 4 步  跑脚本核算：python scripts/perf_metric_calc.py --file metrics.json
第 5 步  看三个数：加权达成率、量化覆盖率、指标健康度（同比涨但没达标 / 达标但同比跌）
第 6 步  按 templates/review_report_outline.md 填四段：结论-数据-问题-计划
第 7 步  做自夸与甩锅自查（§六），改掉定性词与模糊主语
第 8 步  交直属上级过一遍数字，确认口径与公司一致
```

**顺序不能颠倒**：第 4 步算不出数的指标，说明它本来就不该进述职。

## 三、四段结构（照这个比例写）

| 段落 | 占比 | 写什么 | 一句话模板 |
|---|---|---|---|
| **结论** | 10% | 一句话说清这个周期干成了什么、达成多少 | 「本期 X 项核心指标加权达成 XX%，其中 A、B 超额，C 未达」 |
| **数据** | 50% | 5-8 项指标，每项给「本期值 + 同比 + 环比 + 达成率 + 关键动作」 | 「销售额 1200 万，同比 +26%，环比 +8%，目标达成 104%」 |
| **问题** | 20% | 2-3 个真问题 + 根因 + 已做的动作，**不甩锅** | 「C 指标未达，根因是 XX，已启动 XX，预计 XX 见效」 |
| **计划** | 20% | 下周期目标值 + 关键动作 + 需要的资源 | 「下期目标 XX，关键动作三项，需要 XX 支持」 |

**最常见的比例错误**：数据段只写 20%，问题段写 40%。述职的说服力在数据，不在反思。

## 四、三个量化口径（不能只给一个）

```
同比 =（本期值 - 上年同期值）÷ 上年同期值 × 100%
环比 =（本期值 - 上一周期值）÷ 上一周期值 × 100%
目标达成率（越大越好类）= 本期值 ÷ 目标值 × 100%
目标达成率（越小越好类）= 目标值 ÷ 本期值 × 100%   ← 故障率、成本、耗时
加权达成率 = Σ(单项达成率 × 权重) ÷ Σ权重
量化覆盖率 = 有数值且基线完整的指标数 ÷ 指标总数
```

**三个数要一起看**，只看达成率会被误导：

| 同比 | 达成率 | 真实情况 | 述职怎么写 |
|---|---|---|---|
| ↑ | ≥100% | 真增长真达成 | 重点写，给关键动作 |
| ↑ | <100% | 增长但没够到目标 | 说明目标定得高，或增长集中在后半段 |
| ↓ | ≥100% | **目标定低了** | 必须主动说明，否则会被追问 |
| ↓ | <100% | 下滑 | 写根因与止损动作，不解释客观原因了事 |

> 「同比下降但达成率 104%」是最容易被评委抓的一栏。**自己先说出来，比被问出来好。**

**越小越好类指标别算反**：故障次数从 25 降到 18，写成「达成率 72%」是错的，正确是 20 ÷ 18 = 111%。

## 五、定性变定量（述职含金量就在这一步）

| 定性说法 | 换成什么数 | 数据来源 |
|---|---|---|
| 大幅提升效率 | 处理时长从 X 降到 Y，降幅 Z% | 系统日志 / 工单记录 |
| 积极参与协作 | 跨部门协同 N 次，推动 M 项落地 | 会议纪要 / 项目清单 |
| 优化了流程 | 环节从 N 步减到 M 步，单均节省 T 分钟 | 流程图 + 计时 |
| 保障了稳定性 | 可用率 X%，故障 N 次，同比 -Y% | 监控平台 |
| 获得好评 | 满意度 X 分，同比 +Y；投诉 N 件，同比 -M | 问卷 / 客服工单 |
| 完成了日常运维 | 处理请求 N 件，平均响应 T 分钟，一次解决率 X% | 工单系统 |

**没有系统数据的口径**：写「按抽样统计（样本 N）」或「按 XX 台账统计」，并注明统计区间。**不写来源的数字等于没写。**

## 六、自夸与甩锅自查（这两条决定观感）

**自夸边界**：用「我们 + 我在其中的角色 + 具体动作」，不用「我主导了公司级……」。团队成果要写清人数与分工，个人贡献写清你做的那一段。

**甩锅边界**：问题段不出现「因为别的部门……」「由于资源不足……」作为结论句。可以写「协同链路长，我在 XX 环节提前介入后改善」，把归因落在**自己能改的动作**上。

| 错误写法 | 正确写法 |
|---|---|
| 我主导了整个项目，成果显著 | 我在项目中负责 XX 模块，交付 XX，联调一次通过 |
| 因为产品需求变更频繁导致延期 | 需求变更 3 次，我在第 2 次后引入评审机制，后续变更影响下降 |
| 在数据支撑不足的情况下完成了工作 | 数据缺口为 XX，我用抽样 N 条补全口径，误差在 X% 内 |
| 基本完成了年度目标 | 8 项指标达成 6 项，加权达成 96%，未达项为 C、D |

## 七、脚本用法

```bash
python scripts/perf_metric_calc.py --file metrics.json --out 述职量化核算.md
python scripts/perf_metric_calc.py --selftest
```

| 参数 | 说明 |
|---|---|
| `--file` | 指标 JSON，见下方结构 |
| `--text` | 直接给 JSON 字符串 |
| `--out` | 结果写入文件，默认 `scripts/_last_result.txt` |
| `--format` | `md`（默认）或 `json` |
| `--selftest` | 运行内置自检 |

输入 JSON：

```json
{
  "title": "2026 年度述职",
  "owner": "本人",
  "period": "2026 年度",
  "metrics": [
    {"name": "销售额", "unit": "万元", "current": 1200, "baseline": 950,
     "previous": 1110, "target": 1150, "direction": "up", "weight": 0.4},
    {"name": "线上故障次数", "unit": "次", "current": 18, "baseline": 25,
     "previous": 22, "target": 20, "direction": "down", "weight": 0.3}
  ]
}
```

| 字段 | 说明 |
|---|---|
| `current` / `baseline` / `previous` / `target` | 本期值 / 上年同期 / 上一周期 / 目标值 |
| `direction` | `up` 越大越好，`down` 越小越好 |
| `weight` | 权重，默认均分 |

脚本输出：逐指标的同比、环比、达成率与等级，加权达成率、量化覆盖率、整体判定，以及基线缺失、口径不清、达成超标但同比下滑、权重不为 1、指标数量失衡等提醒。

> 脚本只做算术与结构核查，**不判断你的目标定得合不合理、数据真不真实**。

## 八、人工确认清单（这步不能省）

- [ ] 每项指标的目标值是年初定的还是年中调的，调整过的已写明
- [ ] 同比用的是**上年同期**，不是去年全年
- [ ] 越小越好类指标（故障、成本、耗时）的达成率没有算反
- [ ] 所有数字都有来源（系统 / 台账 / 抽样），抽样已注明样本量与区间
- [ ] 指标数控制在 5-8 项，权重合计为 1
- [ ] 团队成果已写清人数、分工与自己承担的那一段
- [ ] 问题段没有以「别的部门」「资源不足」作为结论句
- [ ] 下周期计划写到了**具体数值**和**需要的资源**
- [ ] 已交直属上级核过一遍数字口径

## 九、最常见的坑

**坑一：通篇定性词，没有一个数。**
错误做法：「积极参与项目建设，大幅提升系统稳定性，获得团队一致好评」。正确做法：换成「可用率 99.95%，故障 18 次同比 -28%，参与 3 个项目并负责其中 XX 模块」。**评委记不住形容词，只记得住数字。**

**坑二：把故障率当成越大越好算。**
错误做法：故障次数 25 → 18，写「达成率 72%」。正确做法：越小越好类达成率 = 目标 ÷ 实际 = 20 ÷ 18 = 111%。算反了会把一笔漂亮的成绩写成未达标。

**坑三：只报达成率，不报同比。**
错误做法：达成率 104%，写得很有底气。正确做法：先算同比。同比 -6% 却达成 104%，说明目标被调低了，评委一追问就很被动。**主动说明比被问出来好。**

**坑四：目标年中调过，只报调整后的。**
错误做法：年初目标 1500，年中改成 1100，述职只写「达成 109%」。正确做法：写「年初目标 1500，年中因 XX 调整为 1100，实际 1200，调整后达成 109%」。**隐去调整属于口径操纵，被发现一次，整套数字都不再可信。**

**坑五：把团队成果全写成自己的。**
错误做法：「我完成了 XX 平台重构」。正确做法：写清角色、人数、分工。集体成果被说成个人成果，是述职里最容易失分且最伤信任的一条。

**坑六：问题段全在甩锅。**
错误做法：「因产品需求频繁变更、测试资源不足，导致上线延期」。正确做法：归因落到自己能改的动作——「需求变更 3 次后我引入评审机制，后续变更影响下降 XX%」。客观原因可以提一句，**结论句必须是自己的动作**。

**坑七：计划段写成了口号。**
错误做法：「明年继续提升系统稳定性，加强跨部门协作」。正确做法：写下周期目标值、三项关键动作、需要的资源与预计见效时间。**没有数字和时间的计划，等于没写。**

**坑八：指标堆了十几项，一项都不深。**
错误做法：列 15 项指标，每项一句话。正确做法：5-8 项，每项给「数值 + 变化 + 关键动作」。评委对述职的记忆容量有限，宁深不宽。

**坑九：数据没有来源。**
错误做法：写「满意度提升 12%」但不说怎么统计的。正确做法：注明「按季度问卷，样本 428 份」或「按客服工单台账统计，区间 2026-01 至 2026-12」。**没有来源的数字，等于没写。**

- 本技能提供述职结构、量化口径与表述边界，**不构成对评级、晋升或薪酬结果的任何承诺**
- 考核维度、权重、评级规则**以公司制度与人力部门口径为准**，本技能的档位仅为通用参考

- 涉及保密项目与未披露财务数据的，按公司披露口径脱敏
- 脚本只做算术与结构核查，不判断目标合理性与数据真实性
