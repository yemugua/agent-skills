# 服务器无法远程登录排查 · 能力概览

## 你会得到什么

一套**从两份日志出发**的 SSH 登录失败排查方法——这个技能的第一条建议是：**没有客户端 `-vvv` 日志就不要开始猜**。

**五层定位**：客户端（本地配置、密钥、代理、时钟）→ 网络与端口（22 可达性）→ sshd 服务（状态、监听、配置语法）→ 认证策略（关键项、Match 块、账号状态、fail2ban）→ 连接数与资源（MaxStartups、磁盘、OOM）。

**客户端日志逐行判读表**：十三种关键日志片段对应明确结论——`Connection refused`（端口未监听）、`Operation timed out`（端口被过滤）、`Connection closed by remote host`（服务端主动断）、`Too many authentication failures`、`no matching host key type`（算法无交集）、`Host key verification failed`（**先核实，不要盲目忽略**）等。

**最容易误判的场景。** `Permission denied` 经常**不是凭据错**：客户端会依次尝试 agent 与 `~/.ssh/` 里所有密钥，密钥数量超过服务端 `MaxAuthTries` 后，正确密钥根本没机会被验证——**看起来像凭据错，实际是尝试次数耗尽**。加 `IdentitiesOnly=yes -i <指定密钥>` 即可。这个问题在不同机器上表现不一致，极具隐蔽性。

**两个隐蔽的配置陷阱。** 一是 `sshd` 对无法识别的配置项**不报错**，键名拼错会静默走默认值，所以改完必须用 `sshd -T` 看**实际生效值**而不是看配置文件写了什么。二是 `Match` 块之后的配置只在该上下文生效，且本地 `sshd -T` 不带 `-C` 显示的是默认上下文值，**必须用 `sshd -T -C user=<用户>,addr=<客户端IP>` 验证**。

**防锁死的安全顺序**：确认有其他入口 → 备份配置 → 改 → `sshd -t` → `sshd -T` → **保留当前会话不退出** → 开新会话验证 → 通过后再 reload → 最后关旧会话。先关旧会话再验证，是标准的事故制造流程。

**隐蔽根因清单**：磁盘/inode 满导致 sshd 无法写入登录记录、24 小时内的 OOM、`MaxSessions` 超限、客户端与服务端时钟偏差过大导致协议时间戳校验失败。

**脚本**：`scripts/ssh_login_check.py` 读取观测数据，输出根因分类、分层判定、按层推进的排查命令，以及那份防锁死的配置变更安全顺序。

## 典型用法

1. SSH 连不上：先拿 `ssh -vvv` 与 `journalctl -u sshd` 两份日志。
2. 密码没错却登不上：查客户端是否带了过多密钥，加 `IdentitiesOnly=yes` 复测。
3. 偶发连不上：查 `MaxStartups` 与是否正在被爆破，**不要只调大 MaxStartups**。
4. 被 fail2ban 封了：`fail2ban-client set sshd unbanip <你的IP>`，不要停服务。
5. 改完 sshd 登不上：走那九步安全顺序，重点是「先开新会话验证再关旧会话」。

## 边界

- 只做**定位路径与日志判读口径**，不代替现场登录解锁操作与配置变更审批
- **在只有 SSH 一个入口的服务器上修改认证配置属于高风险操作**，必须先建立云控制台 VNC 或其他入口
- 生产服务器认证配置变更必须走变更流程：`sshd -t` 验证 + 保留回滚路径 + 保留当前会话
- 重置密码、调整账号锁定、修改防爆破策略需**经授权并留记录**
- 遇到疑似暴力破解或攻击流量**转安全事件处理**，不要为了让自己登录而关闭防护
- 脚本**不发起任何 SSH 连接、不修改任何配置**，只归拢观测结果
- 不提供任何绕过认证的方法，也不建议为兼容老旧客户端长期放开弱算法
