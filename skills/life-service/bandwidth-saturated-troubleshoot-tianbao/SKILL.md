# 网络带宽跑满排查（bandwidth-saturated-troubleshoot）

带宽问题的第一个分岔口不是「谁在占」，而是**内网跑满还是出口打满**——这两者的成因、影响面和处置方式完全不同，混在一起查必然绕路。

这个技能做两件事：**先分清内网/出口** → **再按四步定位到具体进程**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出内网/出口的区分方法与判定 | ❌ 代替你做扩容决策或采购 |
| 给出定位到进程的命令与判读 | ❌ 代替你改 QoS 或限速策略 |
| 识别限速未生效的原因 | ❌ 承诺「限速后一定能达到效果」 |
| 给出利用率阈值与业务影响对照 | ❌ 代替网络管理员做链路调整 |
| 提示 QoS 配置常见错误 | ❌ 提供绕过安全或计费管控的做法 |

**出现以下情况，先停下来人工处理：**

- 出口带宽**持续跑满超过一个业务周期** → 这是**容量规划问题**，不是排查问题，应转扩容评估
- 监控显示带宽跑满但**各网卡流量都正常** → 可能是**计费/监管链路口径问题**，或链路拥塞在运营商侧
- 需要调整**生产环境的限速或 QoS 策略** → 必须走变更流程，限速配置错误会**让业务完全不可用**
- 发现**单进程异常占满带宽**且疑似异常程序 → 先隔离取证，不要直接 kill 掉证据
- 涉及**云厂商带宽计费与限速**（如云主机按流量计费）→ 限速阈值与超费规则**以云厂商产品说明为准**
- 需要**跨链路 QoS 改造** → 需网络专业人员评估，本技能只给核查口径

## 二、第一步：先分清内网跑满还是出口打满（最关键的分岔口）

| 维度 | 内网跑满 | 出口（互联网侧）打满 |
|---|---|---|
| **现象** | 同网段/同交换机内互访慢 | 跨网络访问慢（公网、云外访问） |
| **影响面** | 局部（同机房、同 VLAN） | 全局（所有对外服务） |
| **典型成因** | 交换机背板/上联口不足、东西向流量大、镜像流量、集群心跳 | 上传占满、下载被抢、爬虫、备份外传、CDN 回源 |
| **是否影响公网业务** | 通常不影响 | **一定影响** |
| **关键区别** | **和买的带宽大小无关** | 和出口带宽直接相关 |
| **处置方向** | 升级内网交换与上联、隔离东西向流量 | 限速、QoS、扩容、治理异常流量 |

**判定方法（三条命令）：**

```bash
# 1. 找出出口网卡与默认路由
ip route get 8.8.8.8 | head -1        # 输出里的 dev 就是出口网卡
ip -br a

# 2. 看出口网卡实时流量
nload eth0                             # 或 iftop，看上行与下行
# 关键：上行 RX/TX 到底是哪一侧跑满
#   注意方向：TX 通常是「本机发出」（对内网来说就是上传）
#   RX 通常是「本机收到」

# 3. 对比内网互访与外网访问
iperf3 -c <同网段另一台机器>           # 内网实测带宽
speedtest                              # 公网实测带宽（注意 speedtest 也占带宽）
```

> **重要提醒**：`speedtest` 本身会占满带宽，**不能在业务高峰用**，而且它测的是到某个测速节点的路径，不等于你的出口带宽。判断出口是否打满，应该看**出口网卡的持续流量**而不是跑测速。

**方向必须分清（最常见的误判）：**

| 方向 | 含义 | 跑满的典型后果 |
|---|---|---|
| **上行（出方向）满** | 本机向外发送 | **网站访问慢、响应延迟高**（请求发不出去、ACK 发不回来） |
| **下行（入方向）满** | 本机接收 | 上传下载慢，**但一般不影响网站响应** |

> 家用/中小路由器的「上行」常远小于「下行」（如 100M 下行、10M 上行）。
> **上行被打满时下行很空闲，这是最典型的「带宽明明没满却很慢」的原因。**

## 三、第二步：四步定位到具体进程

```
第 1 步  看总量：nload / iftop，确认哪一侧、哪张网卡跑满
第 2 步  找进程：nethogs / iftop 按进程排序，定位到具体程序与远端 IP
第 3 步  看连接数：ss 与连接状态统计，判断是长连接大流量还是小连接海量
第 4 步  看队列与丢包：sar -n DEV / ethtool，确认是否出现队列丢弃
```

### 3.1 工具选择

| 工具 | 用途 | 是否需安装 |
|---|---|---|
| `nload` | 快速看网卡总吞吐与方向 | 多数发行版自带 |
| `iftop` | 实时按 IP 排序看谁在通信 | 需装（`iftop`） |
| `nethogs` | **按进程**看流量，最直观 | 需装（`nethogs`） |
| `ss` | 连接数与连接状态统计 | 自带 |
| `sar -n DEV` | 网卡收发速率与队列丢弃 | 需 sysstat |
| `tcpdump` | 抓包确认具体流量内容 | 自带（慎用生产） |
| `iperf3` | 内网/链路实测带宽 | 需装（两端都要） |
| `tc`/`tc qdisc` | 查看与配置限速 | 需装（限速排查必用） |

### 3.2 命令速查

```bash
# ---- 第 1 步：看总量与方向 ----
nload eth0                              # 简单直观，显示上下行
nload -m                                 # 只显示，不画图
iftop -i eth0                            # 实时按连接排序
iftop -i eth0 -n -N                      # 不解析主机名/端口，更清爽
ifstat eth0                              # 另一种风格
sar -n DEV 1 10                          # 每秒采样，看收发速率与丢包
cat /proc/net/dev | awk 'NR<3 || /eth0/'  # 零依赖方式

# ---- 第 2 步：按进程定位 ----
nethogs                                  # 实时按进程
nethogs -t 10                            # 刷新间隔 10 秒
nethogs -c 2 -d 5                        # 每 5 秒刷新，连续 2 次
# 看不到时用 ss 反查
ss -tnp | grep <远端IP或端口>

# ---- 第 3 步：连接数与状态 ----
ss -s                                    # 汇总：总数/状态分布
ss -tan state established | wc -l        # ESTABLISHED 数
ss -tan state time-wait | wc -l          # TIME-WAIT 数
ss -tan | awk '{print $5}' | sort | uniq -c | sort -rn | head -20   # 按对端统计
ss -tn state established dst <对端IP>    # 与某对端的连接
cat /proc/sys/net/ipv4/ip_local_port_range
cat /proc/sys/net/core/somaxconn

# ---- 第 4 步：队列与丢包 ----
ethtool -S eth0 | grep -iE "drop|err|discard"   # 网卡丢包与错误
ethtool eth0                              # 看速率与双工
tc -s qdisc show dev eth0                 # 限速规则与丢弃统计
ip -s link show eth0

# ---- 限速核查 ----
tc qdisc show dev eth0
tc class show dev eth0
tc filter show dev eth0
iptables -L -n -v                         # 是否有 iptables 限速/计数规则
# 应用层限速（很多场景用的是这一层）
# Nginx: limit_rate / limit_rate_after
# Apache: mod_bw / mod_ratelimit
# 应用配置项: maxBytesPerSecond 之类

# ---- 实测带宽（低峰期做）----
iperf3 -c <同网段IP> -t 10                # 内网实测
iperf3 -c <对端IP> -t 10 -R               # 反向测速（模拟下载）
iperf3 -c <对端IP> -t 10 -u -b 100M       # UDP 测试丢包与抖动
```

## 四、限速误判的四类原因（限速配了没生效）

| # | 原因 | 现象 | 验证 | 处置 |
|---|---|---|---|---|
| 1 | **规则顺序** | 后加的规则匹配在前，新规则不生效 | `tc filter show dev eth0` 看优先级（handle/priority） | 调整优先级或删除冲突规则 |
| 2 | **只限了默认类** | 自定义 class 的流量没被限 | `tc class show` 与 `tc filter` 对比 | 补上其他 class 的限速 |
| 3 | **子接口/物理口不匹配** | 限速加在 eth0，实际走 bond0 或 vlan | `ip -br a` 确认实际出接口 | 限速加在实际接口上 |
| 4 | **单位搞错** | 限速没生效或限得过头 | `tc class show` 看 rate 单位（bit/kbit/mbit） | 确认 `bit` vs `mbit` 写对 |

**其他常见原因：**

| 原因 | 说明 |
|---|---|
| **应用层限速被绕过** | 应用有自己的多线程/多连接限速逻辑，tc 只限了单连接 |
| **容器网络绕过宿主机限速** | 容器走的是 veth/网桥，宿主机 eth0 上加的 tc 可能不生效 |
| **多网卡策略路由** | 限速加在默认路由的网卡上，但实际走了另一张卡 |
| **NAT 之后限速** | 限速加在 NAT 前/后位置不对，效果完全不同 |
| **企业网络设备接管** | 上级设备或云厂商的 QoS 覆盖了你的本地限速 |
| **突发缓存掩盖** | 限速生效了，但 socket 缓冲里的存量数据还在发，看瞬时速率像是没生效 |

**判断限速是否真的生效的方法（不要只看瞬时速率）：**

```bash
# 1. 看 qdisc 的丢弃统计在涨（说明确实在限）
tc -s qdisc show dev eth0 | grep -i drop

# 2. 长时间采样，看平均速率是否贴近限速值
sar -n DEV 1 60

# 3. 主动测试（低峰期）
iperf3 -c <对端> -t 30        # 看实际速率是否接近限速值
```

## 五、带宽利用率阈值与业务影响

| 利用率 | 等级 | TCP 表现 | 体验影响 | 处置 |
|---|---|---|---|---|
| < 40% | 充裕 | 正常 | 无感 | 无需处理 |
| 40–60% | 正常 | 正常 | 无感 | 无需处理 |
| 60–75% | 关注 | 开始出现排队 | 高峰偶发变慢 | 观察趋势 |
| 75–85% | 告警 | 排队明显，重传增加 | 用户可感知变慢 | 治理或限速 |
| 85–95% | 严重 | 吞吐饱和，延迟陡增 | 明显变慢甚至超时 | 限速 + 治理，评估扩容 |
| > 95% | 饱和 | 吞吐不再增长，延迟与丢包飙升 | 业务不可用 | 立即处置 |

**上行与下行要分别看：**

| 侧 | 上行跑满的表现 | 下行跑满的表现 |
|---|---|---|
| 用户感知 | **网站慢、接口超时** | 下载慢、上传文件卡 |
| 原因 | 出方向队列满、ACK 发不回来 | 入方向队列满 |
| 治理重点 | **上行限速、封异常上传** | 下行配额、CDN 加速 |

**必须记住：带宽利用率 60% 就开始出现排队延迟是正常的**，因为排队发生在最后一档。要判断「是否影响业务」，**看队列深度和丢包，不要只看利用率百分比**。

## 六、QoS 与限速的正确做法与常见错误

### 6.1 优先级（QoS）的正确思路

```
最高优先级  语音 / 视频会议 / 关键交易
     ↓
中优先级    数据库复制 / 核心接口
     ↓
普通优先级  常规业务请求
     ↓
最低优先级  文件下载 / 数据备份 / 日志上传 / 批量任务
```

**原则：低优先级流量必须在链路**拥塞时**被主动丢弃，而不是让所有流量一起排队。** 不做优先级的限速只是平摊，没有意义。

### 6.2 常见错误配置

| # | 错误 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 所有流量同一条 tc 限速 | 一起被限，语音和下载一样卡 | 按 class 分级限速 |
| 2 | 限速值贴近链路带宽 | 长期排队，延迟高 | 峰值限速设在带宽的 80–85% |
| 3 | 只对内网 IP 限速，外网不限 | 外网流量仍可打满 | 内网外网都要覆盖，或在出口统一限 |
| 4 | 限速在应用层做 | 多进程/多实例绕过 | 网络层限速为准，应用层补充 |
| 5 | 改完 tc 不清计数就下结论 | 存量突发仍在发 | `tc qdisc del` 后重加，或等缓存排空再测 |
| 6 | 限速加在容器宿主机 eth0 | 容器流量可能绕过 | 确认容器实际出接口（veth/网桥） |
| 7 | 忽略 TCP 重传占用的带宽 | 误判为「正常流量」 | 看 `ss -ti` 的 retrans 或 `netstat -s` |
| 8 | 限速后不做长时间采样 | 峰值降了但均值没降 | `sar -n DEV 1 60` 采样 |

### 6.3 限速配置示例（仅供参考，需评估后使用）

```bash
# 查看当前状态（排查时第一件事）
tc qdisc show dev eth0
tc class show dev eth0
tc filter show dev eth0

# 分级限速示例：80M 出口，语音优先
tc qdisc add dev eth0 root handle 1: htb default 30
tc class add dev eth0 parent 1: classid 1:10 htb rate 10mbit        # 语音
tc class add dev eth0 parent 1: classid 1:20 htb rate 30mbit        # 业务
tc class add dev eth0 parent 1: classid 1:30 htb rate 40mbit ceil 40mbit  # 默认
tc filter add dev eth0 protocol ip parent 1: prio 1 u32 \
  match ip dport <语音端口> 0xffff flowid 1:10

# ⚠️ 以上仅为语法示例。生产环境应用前必须：
# 1) 先 tc qdisc del dev eth0 root 清理旧规则（否则会冲突）
# 2) 用 iperf3 实测验证限速是否生效
# 3) 准备回滚命令（tc qdisc del dev eth0 root）
```

> **限速是可远程造成服务不可用的操作。** 生产环境必须：先记录现状 → 配置 → 验证 → 保留回滚路径，且**不得在业务高峰操作**。

## 七、四步定位决策树

```
问题：网络变慢 / 带宽跑满
  │
  ├─ 第 0 步：同网段互访慢吗？
  │    ├─ 是 → 内网问题：查交换机上联口速率、端口协商速率
  │    │        （和买的出口带宽无关，升级交换机不是升带宽）
  │    └─ 否 ↓
  │
  ├─ 第 1 步：出口网卡哪一侧跑满？
  │    ├─ 上行（出方向）→ 影响网站响应，优先治理上传/备份/爬虫
  │    ├─ 下行（入方向）→ 影响下载/上传文件，优先治理下载/分发
  │    └─ 两侧都满 → 大流量双向传输，查对端与中间链路
  │
  ├─ 第 2 步：哪个进程？（nethogs / iftop）
  │    ├─ 单进程异常占满 → 隔离取证，查是否异常程序
  │    ├─ 正常业务流量 → 属容量问题，评估扩容
  │    └─ 分散但总量大 → 海量小连接，查连接数与进程数
  │
  ├─ 第 3 步：连接特征？
  │    ├─ 少量连接 + 高流量 → 大文件传输、备份、镜像同步
  │    └─ 海量连接 → 连接池未复用、短连接、爬虫、CC 攻击
  │
  └─ 第 4 步：有队列丢弃吗？（tc -s qdisc / ethtool -S）
       ├─ 有丢弃 → 链路确实饱和，限速或扩容
       └─ 无丢弃但慢 → 不是带宽问题，查延迟、丢包、MTU、CPU
```

**最后一条特别重要：有丢弃才说明带宽真的不够。** 没有丢弃却慢，通常是延迟、丢包、MTU 或 CPU 的问题，继续限速只会更糟。

## 八、脚本用法

```bash
python scripts/bandwidth_triage.py --file obs.txt --uplink-mbps 100
```

| 参数 | 说明 |
|---|---|
| `--file` | 观测数据，每行 `指标\|数值`，见下表 |
| `--uplink-mbps` | 上行带宽（Mbps），用于算利用率 |
| `--downlink-mbps` | 下行带宽（Mbps） |
| `--local-mbps` | 内网交换上联带宽（Mbps），用于区分内网/出口 |
| `--json` / `--out` | JSON 输出 / 写入指定报告文件 |
| `--selftest` | 跑内置自检（≥ 8 条断言） |
