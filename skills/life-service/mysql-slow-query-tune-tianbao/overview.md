# SQL 慢查询优化与改写 · 能力概览

## 你会得到什么

**一套排优先级的口径**。慢 SQL 优化最容易犯的错是"看谁单次最慢"，正确做法是看**总耗时 = 平均耗时 × 执行次数**。先用慢日志 / `sys.statements_with_ranking_by_total_latency` / `SHOW PROCESSLIST` 三条互补路径拿到 TOP 清单，再用一个数字定严重程度：**扫描比 = Rows_examined / Rows_sent**。1-10 正常，1000 以上可疑，超过 10000 基本是全表扫或深分页。

**一张反模式打钩表**。深分页、列套函数、隐式类型转换、前导通配符、`SELECT *`、关联子查询、OR、大 IN 列表、`ORDER BY RAND()`、大表 COUNT、不可合并的派生表、一次几十万行的批量写——每类都给了可抄的改写 SQL，而不是"优化一下"。

**被顺序毁掉的判断**。`Lock_time` 高、偶发慢平时快、EXPLAIN 很好但还是慢，这三种情况都不是 SQL 的锅，先排查锁等待、事务未提交、Buffer Pool 波动与 IO 抖动。这一条能省掉大量无效改索引的时间。

**脚本**：`scripts/slow_sql_check.py` 有两种模式。给它慢日志文件加 `--slowlog`，它会解析出每条语句的 Query_time / Lock_time / Rows_sent / Rows_examined，自动算扫描比并按 严重/可疑/留意/正常 分级，`Lock_time` 异常时提示先查锁，最后按耗时倒序输出 TOP 10。给它 SQL 文本，它按 15 条规则扫写法问题（四级严重度 + 风险分），并给出每条的具体改法。

## 典型用法

1. 每周一次性能例会：跑 `--slowlog` 出 TOP 10，直接进优化看板。
2. 有具体 SQL 要看：`--sql` 快速过一遍有没有命中已知反模式。
3. Review 别人的新上线 SQL：加到 CI 或 MR 前的本地检查，重点抓深分页、`SELECT *`、隐式转换。
4. 优化后复查：原 SQL 与改写 SQL 各跑一次，对比风险分与 EXPLAIN，留存记录。

## 边界

- 静态分析不等于真实耗时，最终以 EXPLAIN ANALYZE 与慢日志 P95 为准
- MySQL 5.6 / 5.7 / 8.0 在 Hash Join、CTE 合并、临时表策略上差异明显
- 生产 DDL 与批量 DML 属高风险操作，必须走评审并在预发验证回滚
- 阈值（扫描比分级、分批 1000、IN 列表 500）是工程经验值，需按真实数据量校准
