# Code Review 规则库（判定口径 + 门禁）

## 1. PR 尺寸分级 → 评审方式

| 级别 | 判定（满足任一即入级） | 评审要求 | 处理建议 |
|---|---|---|---|
| **XS** | ≤ 5 文件 且 ≤ 30 行改动 | 1 人评审即可 | 直接合 |
| **S** | ≤ 15 文件 且 ≤ 150 行 | 1 人评审 | 直接合 |
| **M** | ≤ 30 文件 且 ≤ 500 行 | 1-2 人评审，至少 1 人是模块 owner | 可以合，但正文要写清验证方式 |
| **L** | ≤ 60 文件 或 ≤ 1500 行 | **2 人评审** + 必须附测试证据 | 强烈建议拆分（按重构/功能/格式拆） |
| **XL** | > 60 文件 或 > 1500 行 | **不建议合** | 拆 PR；format-only 提交单独一个 PR |

> 说明：**自动生成的文件、锁文件、格式化结果**必须单独成 PR。混进来会把 S 级 PR 变成 XL 级。

## 2. 必审项清单（按严重级别）

### A 级（发现就挡回，不许合）

| # | 检查项 | 常见表现 |
|---|---|---|
| A1 | 密钥/凭证入库 | diff 里出现 `AKIA`、`-----BEGIN RSA`、`password = xxx`、`token: " eyJ...` |
| A2 | 破坏性变更无迁移方案 | 删了接口字段、改了返回结构、改了枚举值，但没写兼容处理 |
| A3 | 数据库不可回滚的变更 | `DROP COLUMN`、改字段类型、删除数据，没有双写/双读过渡 |
| A4 | 并发与幂等缺失 | 支付/退款/库存扣减没有幂等键、没有锁、没考虑并发扣成负数 |
| A5 | SQL 注入 / XSS / SSRF | 字符串拼接 SQL、`innerHTML` 直接塞用户输入、请求地址由用户参数拼 |
| A6 | 循环里做 IO | 在 for 循环里查库、调远程接口、写文件 |
| A7 | 裸改生产配置 | 直接动 `application-prod.yml`、K8s ConfigMap，无灰度无回滚开关 |

### B 级（必须给出解释或补测试）

| # | 检查项 |
|---|---|
| B1 | 逻辑改动没有对应单测（纯配置/文档除外） |
| B2 | 异常被吞掉：`catch(e){}`、只打日志不抛、返回空对象 |
| B3 | 魔法值：金额单位、超时秒数、重试次数写死在代码里 |
| B4 | 引入新依赖：没有说明 License、体积、维护活跃度 |
| B5 | 日志：用 `System.out.println` / `console.log` 而不是日志框架；日志里打敏感信息 |
| B6 | 事务边界：跨服务调用写在事务里；事务方法被同类内部 this 调用导致不生效 |
| B7 | 分页缺失：查列表没有 `LIMIT` |

### C 级（建议修改）

注释与代码不符、命名与上下文不一致、重复代码块、遗留调试代码/注释掉的代码、TODO 没带工单号。

## 3. 按文件路径指派评审人

| 路径包含 | 必须由谁批 |
|---|---|
| `pay` / `refund` / `settle` / `account` | 交易组 owner |
| `auth` / `permission` / `token` / `crypto` | 安全/基础 owner |
| `db/migration` / `*.sql` / `schema` | DBA + 后端 owner |
| `Dockerfile` / `k8s/` / `terraform/` / `.github/workflows` | SRE |
| 公共 SDK / `common/` / `sdk/` | 架构组（影响面未知） |
| 第三方 License / 法务文本 | 法务（SR 级改动） |

CODEOWNERS 就是照这张表配的。

## 4. 评审时效（SLA）

| 环节 | 时限 |
|---|---|
| 首次响应（从提出到有人看） | ≤ 4 个工作小时 |
| 一般 PR 给出结论 | ≤ 1 个工作日 |
| L / XL 级 PR | ≤ 2 个工作日（超出应说明原因） |
| 作者回应评论 | ≤ 1 个工作日/轮 |
| 超过 3 天无人理的 PR | 自动提醒 + 抄送 owner 上一级 |

## 5. 评论的写法（强行规定）

每条评论必须带**级别前缀**，作者才知道能不能合：

| 前缀 | 含义 | 是否阻断 |
|---|---|---|
| `[blocking]` | 必须改 | 是 |
| `[suggestion]` | 建议改，作者可拒绝但要回复理由 | 否 |
| `[nit]` | 吹毛求疵（格式、命名偏好），作者可忽略 | 否 |
| `[question]` | 我没看懂，需要解释 | 是（要回答） |
| `[praise]` | 写得好的地方，点出来让别人学 | 否 |

禁止无前缀评论。禁止只写「这里不太对」不说哪里不对。

## 6. 批准前必须确认的 6 件事

- [ ] 我自己看懂了他在改什么，**能说出改动的风险点**
- [ ] A 级必审项全部过（尤其是 idempotent 与迁移回滚）
- [ ] 有对应的测试用例，或作者说明了为什么不需要
- [ ] CI 全绿，**没有用 rerun 掩盖偶发失败**
- [ ] 该 PR 的回滚方式明确（回滚提交 / 关开关 / 数据补偿脚本）
- [ ] 依赖发布顺序已确认（先发哪个服务、要不要先跑数据）

## 7. 不能因为以下原因打回

- 风格偏好没有写进 lint 规则（先补 lint，别用嘴评审）
- 「我以前是这么写的」——以规范和现状为准
- 要求作者顺手改无关文件
- 只有 nit 级评论却把 PR 挂了两天

## 8. 评审人自己要注意

- **不要只看 diff 的改动行**，上下文同样重要
- 看到 L 级 PR 就要求拆分，而不是硬着头皮全看
- 别人 approve 了不等于你也可以 approve——批准人是连带责任的
- 对自动生成/格式化提交，只 review 配置变更，不逐行看产物
