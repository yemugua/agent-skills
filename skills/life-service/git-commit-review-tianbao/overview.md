# Git 提交规范与 Code Review · 能力概览

## 你会得到什么

**提交信息这一半**：11 个 type 的语义边界（`feat` 和 `refactor` 怎么分、`优化`该归哪一类）、标题的硬指标（≤72 字符、结尾不加句号、动词开头）、四种必须写正文的场景、footer 白名单与常见拼错对照表。`BREAKING CHANGE` 必须全大写这件事看起来是小事，写错了语义化版本工具识别不到，会以 patch 版本发出去，属于典型的线上事故诱因。

**Code Review 这一半**：按文件数 + 改动行数把 PR 分成 XS/S/M/L/XL 五级，每级对应明确的评审人数要求；七条 A 级必审项（密钥入库、无迁移方案的破坏性变更、不可回滚的表结构变更、幂等缺失、注入类漏洞、循环内 IO、裸改生产配置）、七条 B 级必审项；按路径自动指派必审角色（支付/鉴权/迁移/K8s/公共 SDK）；以及强制的评论前缀规范 `[blocking]` `[suggestion]` `[nit]` `[question]`。

**脚本**：`scripts/commit_msg_check.py` 读取 `git log --format=%B` 的导出文本，逐条检查格式、type 白名单、正文必填、footer 拼写，同时按 `--files` / `--additions` 给 PR 分级并标出必审路径，输出可直接贴进 PR 评论的检查结论。

## 典型用法

1. 新人上手：先读 type 表，写三个样例提交跑一遍脚本，再开始正式提交。
2. 发版前：导出最近 30 条提交，找出没写正文、footer 拼错、标题超长的问题，趁还没生成 CHANGELOG 改掉。
3. 评审前：先用 `--files --additions` 定级，XL 直接打回拆分，不浪费评审时间。
4. 团队对齐：把 A 级必审项贴到 PR 模板里，让所有人按同一张表自检。

## 边界

- 只校验格式与尺寸，**不判断代码正确性**
- PR 能不能合由模块 owner 决定，脚本给的是分级建议
- 注入、越权、加密等安全问题需专岗复核，本技能只给检查点
- 数据库不可逆变更必须有备份与回滚预案，不以评审结论替代演练
- 各团队 type 白名单与语言习惯不同，规则需按团队现状调整
