# 小程序虚拟支付（xpay）接入避坑清单

## 一、通道区分（最容易踩的坑）
- **虚拟支付（xpay）≠ 微信支付商户号**。
  - 虚拟支付用于**虚拟商品**（会员、道具、内容、课程解锁等），在微信支付侧单独开通「虚拟支付」能力。
  - 普通微信支付商户号用于**实物/服务交易**的下单收款。
  - 二者通道独立、分别下单，**有商户号不代表能卖虚拟商品**。
- 微信小程序内的虚拟支付走 xpay 即可，**不受 Apple IAP 限制**（IAP 限制只针对独立上架 App Store 的 iOS App）。

## 二、常见报错 / 驳回与处理
| 现象 | 可能原因 | 处理 |
|------|----------|------|
| 下单报「无权限/未开通虚拟支付」 | 主体未开通 xpay 或小程序未认证 | 先认证小程序并在微信支付开通虚拟支付 |
| 下单报「offer_id 不存在」 | offer_id 填错或未创建应用 | 在虚拟支付后台核对应用 ID |
| 下单报「product_id 不存在」 | 商品未创建或未绑定 | 创建 product_id 并确认状态 |
| 价格异常/金额不符 | 价格单位不是「分」或传了浮点/元 | 价格一律传整数「分」（如 68 元=6800） |
| 用户付了钱但权益没发 | 发货回调（xpay_goods_deliver_notify）未配置或未生效 | 配置消息推送→服务端回调激活权益 |
| 同一笔订单重复发货 | 回调未幂等 | 以订单号去重，重复回调直接返回已处理 |
| 偶发掉单/权益缺失 | 回调丢失或超时 | 提供补发入口 + 定时对账补单 |
| iOS 审核被拒 | 独立 iOS App 内用了微信支付/xpay | 改走 Apple IAP |

## 三、最佳实践
1. 下单与回调链路**全链路联调**（沙箱/测试环境）通过再上线。
2. 回调处理**幂等**：用订单号 + 支付状态做去重，避免资损。
3. **掉单兜底**：定时任务扫描「已支付未发货」订单补发；并提供用户侧「补发/重新激活」入口。
4. 价格、商品信息、退款规则在购买页与用户协议**明示**。
5. 关注虚拟支付后台的账单与对账，防范刷量/套现。
