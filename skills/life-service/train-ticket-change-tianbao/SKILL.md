# 高铁票改签与退票核查（train-ticket-change）

「改签和退票哪个划算」这个问题，答案不在费率表里，而在**你手上的票是什么状态**。开车前、开车后、误点、联程票，处置逻辑完全不同。

这个技能做四件事：**看状态** → **选动作** → **算费用方向** → **处理连带**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 说明改签与退票的规则结构与判断逻辑 | ❌ 给出具体费率与时间窗数字 |
| 说明费用档位的结构逻辑 | ❌ 承诺一定能改签成功 |
| 说明开车前与开车后的差异 | ❌ 代用户操作购票渠道 |
| 说明误点与取消的处置顺序 | ❌ 判断某次列车是否一定停运 |
| 说明联程票的连带处理要点 | ❌ 编造条款号或规则条文 |

**改签时间窗、改签次数、改签费与退票费的具体数值，以承运方现行规定为准。** 本技能只讲**规则的结构与判断逻辑**，不写死任何具体数字，也不引用条款号。查询时请以承运方官方渠道公布的现行规则和购票页显示为准。

**遇到以下情况，直接联系承运方官方渠道：**

- 需要改签的班次已满、无余票
- 涉及卧铺、贵宾席等特殊席别的变更
- 联程票中部分行程无法衔接
- 列车停运或长时间晚点且需改后续行程
- 票已过站、票已作废等异常状态

## 二、完整工作流

```
第 1 步  确认票的状态：还没开车 / 已开车未到站 / 已过站 / 已作废
第 2 步  确认是不是联程票或分段票（后面还有没有要衔接的行程）
第 3 步  先读规则文件 rules/train_change_rules.md（时序决策表 + 费用结构 + 连带处理）
第 4 步  跑决策脚本，按状态给出动作方向与连带影响
    python scripts/train_change_check.py --status before --segments 2
第 5 步  在承运方官方渠道查看当前可改班次与实际费用
第 6 步  一次把要改的都改完，不要分多次操作增加出票成本
```

## 三、时序决策表（先看这张）

| 票的状态 | 可以考虑的动作 | 说明 |
|---|---|---|
| **开车前** | 改签或退票都还有选择 | 选择面最大，优先在此阶段处理 |
| **开车后未到站** | 通常仍可按承运方规则办理变更 | 具体能否办理与办理方式以承运方现行规定为准 |
| **已过站** | 通常已无法按普通改签流程办理 | 需要联系承运方官方渠道处理 |
| **列车停运** | 按承运方公告的处置方案办理 | 退票通常不收取费用 |
| **票据已作废** | 无法再办理 | 需查清作废原因 |

**核心口径**：**能早处理就早处理。** 开车前的选择面最大，越往后可选方案越少、连带影响越大。

**具体的时间窗与办理条件以承运方现行规定为准**，本表只描述状态与选择面的关系。

## 四、费用结构对比（讲逻辑，不讲数字）

**改签费的结构逻辑：**

- 通常**按新班次的车票价格与原票价的差额**处理
- 新车票价格**高于**原票价时，通常需补差价
- 新车票价格**低于**原票价时，差额部分的处理方式以承运方现行规定为准

**退票费的结构逻辑：**

- 通常按**距开车时间的长短分档**，越临近开车费率越高
- 分档的**具体档位与费率以承运方现行规定为准**
- 列车停运、误点无法乘车等情形通常有专门的处理方式

**改签与退票的关键差异**：

| 维度 | 改签 | 退票 |
|---|---|---|
| 结果 | 保留乘车资格，另出一张票 | 取消乘车，退回票款扣除相应费用 |
| 费用 | 按新旧票价差额 | 按距开车时间分档 |
| 适用 | 还想去，只是时间变了 | 不打算去了 |

**判断方向**：**行程还想去但时间要变，优先考虑改签；行程本身取消了，再考虑退票。** 先想清楚这一点，再看哪种更划算。

---

## 五、误点与取消的处置顺序

```
第 1 步  先看官方公告或通知，确认列车状态
第 2 步  确认自己能否换乘同一行程的其他班次
第 3 步  有衔接行程的，先处理衔接关系，不要只改自己这一段
第 4 步  按承运方公布的处置方案办理改签或退票
第 5 步  保留好公告截图与办理凭证
```

**保留凭证很重要**：涉及费用处理时，**公告截图、办理记录、车票凭证都要留好**，这是后续申诉与核对的依据。

**不要在信息不明确时反复操作**：先确认列车状态，再一次性把要改的都改完。**分多次改签可能产生多次出票与差额处理。**

## 六、联程票与分段票

**联程票或分段行程的连带影响**：

| 情况 | 需要注意 |
|---|---|
| 只改了第一段，后续衔接会断 | 后续行程很可能需要一起处理 |
| 只改了最后一段，前段可能白费 | 前段票款可能涉及退改 |
| 前后两段不在同一订单 | 处理起来更复杂，需要分别确认 |
| 中间段无法改 | 整条行程可能只能重订 |

**核心口径**：**有衔接行程时，改签不能只看自己这一段。** 改了时间就可能接不上后面的车，联程票的整体影响要先确认。

**处理要点**：

1. 先把所有要衔接的行程列出来
2. 确认每段能否改、能否退
3. 优先按整条行程的可行性来决策，而不是只保住其中一段
4. 改完后重新确认衔接时间是否合理

---

## 七、常见误区

| 误区 | 说明 |
|---|---|
| 「退票肯定比改签划算」 | 行程还想去就该优先改签，不是比价 |
| 「开车前和开车后一个价」 | 越临近开车选择越少、影响越大 |
| 「改签就是免费改」 | 通常涉及新旧票价差额的补缴 |
| 「误点了先自己想办法」 | 先看官方公告，处置要按公布方案走 |
| 「联程票改一张就行」 | 衔接断了后续行程可能一起作废 |
| 「网上看到的费率就是当前的」 | 规则会调整，以承运方官方渠道公布的现行规则为准 |

## 八、脚本用法

```bash
python scripts/train_change_check.py --status before --segments 2
python scripts/train_change_check.py --file trip.json --out 处置建议.md
python scripts/train_change_check.py --selftest
```

| 参数 | 说明 |
|---|---|
| `--status` | `before`（开车前）/ `after`（开车后未到站）/ `passed`（已过站）/ `cancelled`（列车停运） |
| `--segments` | 行程段数，1 表示单程，多于 1 涉及连带处理 |
| `--want` | `change`（想改期）/ `refund`（想退票） |
| `--file` | 从 JSON 读（自动兼容带 BOM 的文件） |
| `--out` | 结果落盘路径 |
| `--format` | `md`（默认）或 `json` |
| `--selftest` | 跑内置样例自检 |

脚本输出**状态与选择面说明、费用结构方向、连带影响提示、处置顺序**。

> 脚本只做状态判断与结构说明，**不给出任何费率与时间窗数字**，实际数值以承运方官方渠道公布为准。

## 十、最常见的坑

**坑一：先比价再决定改还是退。**
顺序反了。**先想清楚行程还想不要去**，还能去就改签，不去了才退票。

**坑二：拖着不开车前处理。**
开车前选择面最大，越往后可选方案越少。

**坑三：以为开车后和开车前一样。**
开车后能否办理与办理方式都受承运方规则限制，别用开车前的经验套。

**坑四：把网上看到的费率当现行标准。**
规则会调整，**以承运方官方渠道公布的现行规则为准**。

**坑五：误点了先自己折腾。**
先看官方公告，确认列车状态后按公布的处置方案办理。

**坑六：分多次改签。**
可能产生多次出票与差额处理，一次改完更省事。

**坑七：联程票只改自己这一段。**
衔接断了，后续行程可能一起受影响。

**坑八：没留凭证。**
公告截图与办理记录是后续核对与申诉的依据。

**坑九：把「改签」理解成免费改。**
通常涉及新旧票价差额的补缴，要先看新班次有没有票。

**坑十：已过站还按普通改签流程操作。**
这种情况通常无法按普通流程办理，要联系官方渠道。

## 十一、边界与免责

- 本技能**只讲规则的结构与判断逻辑**，**改签时间窗、次数、费率与退票费档位以承运方现行规定为准**
- 不引用具体条款号或规则条文，**实际数值请以承运方官方渠道公布为准**
- 不代用户在购票渠道执行任何操作
- 不判断某次列车是否一定停运或晚点，**以官方公告为准**
- 涉及特殊席别、异常票务状态、联程衔接失败的情况，联系承运方官方渠道处理
