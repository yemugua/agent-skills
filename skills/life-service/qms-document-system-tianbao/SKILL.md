# 质量管理体系文件搭建（qms-document-system）

体系认证查什么？**查文件、查记录、查一致性**。文件体系和实际做的是两套，是认证现场的高频硬伤。

这个技能做四件事：**搭架构** → **定编号** → **管受控** → **接审核**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 设计四层文件架构与编号规则 | ❌ 替代认证机构审核与标准原文 |
| 编写程序文件框架与受控流程 | ❌ 出具认证结论或符合性声明 |
| 设计记录表单与保存期限表 | ❌ 编造不存在的质量记录 |
| 梳理内审与管理评审输入 | ❌ 替代内审员现场审核 |

**涉及产品安全、法规强制性要求的，一律以现行标准原文和认证机构要求为准。** 不同行业（医疗器械、汽车、食品）有专用体系要求，本技能以通用质量管理体系为基线。

## 二、完整工作流

```
第 1 步  明确体系范围、产品/服务与适用标准
第 2 步  读规则文件 rules/document_control_rules.md
第 3 步  搭四层文件架构，输出体系文件清单
第 4 步  定编号规则，跑受控台账体检
    python scripts/doc_number_check.py --file 受控台账.csv --as-of 今天
第 5 步  按 templates/程序文件模板.md 编写程序文件
第 6 步  人工确认流程与部门职责匹配
```

## 三、四层文件架构

```
第一层  质量手册      为什么做：方针、目标、范围、过程相互作用（纲领性文件）
第二层  程序文件      谁来做：跨部门过程的职责、流程、接口（如采购、内审）
第三层  作业指导书    怎么做：岗位操作细节、技术规范、设备规程（WI）
第四层  记录表单      做了什么：过程输出的证据（QR，与上层文件一一对应）
```

| 层 | 回答的问题 | 典型编号 | 编制责任 |
|---|---|---|---|
| 手册 | 为什么做 | QM | 最高管理者/管理者代表 |
| 程序 | 谁来做 | QP | 过程归口部门 |
| 指导书 | 怎么做 | WI | 使用部门 |
| 记录 | 做了什么 | QR | 过程执行岗位 |

**层间对应原则：每一个程序文件都应指向若干记录表单；每一个记录表单都应能找到产生它的程序。** 对应关系断链是现场审核的常见不符合项。

## 四、编号规则设计

```
推荐结构：类型码 - 部门/过程码 - 序号 [- 版本]

例：
QM-2026              质量手册（版本 2026 换版）
QP-08-02             采购控制程序（过程 08，序号 02）
QR-08-02-01          采购供方调查表（采购程序第 1 号记录）
WI-06-03-A           装配作业指导书 A 版
```

**编号设计四原则：**

| 原则 | 说明 |
|---|---|
| 唯一性 | 一个编号只对应一份文件，废止不复用 |
| 可读性 | 看编号能判断类型和归属过程 |
| 可扩展 | 留足序号空间，新增过程不打乱既有体系 |
| 版本分离 | 编号不带版本号，换版只升版本不改编号 |

## 五、受控管理十项规定

1. 文件发布前须经**编制、审核、批准**三级签字，授权名单存档
2. 受控文件加盖**受控章**（编号、份数、持有人）
3. 发放履行**签收登记**，回收履行**注销登记**
4. 修订须填写**更改申请单**，说明原因、影响与验证要求
5. 换版后**旧版全部回收**，留存样本加盖"作废留存"标识
6. 作废文件不得出现在工作现场，电子版同步下线
7. 外来文件（法规、标准、客户图样）建立**外来文件清单**并跟踪有效性
8. 每年至少一次**文件适用性评审**（可结合管理评审）
9. 电子受控与纸质受控具有同等效力时，明确主控形式与备份机制
10. 文件档案保存期限满足法规与客户要求，一般不少于产品责任期

## 六、记录表单设计五要素

| 要素 | 要求 |
|---|---|
| 唯一性标识 | 表单编号+版本号 |
| 可追溯字段 | 日期、产品/批次、操作人、审核人 |
| 判定字段 | 合格/不合格、数据留痕，不留"基本符合" |
| 更改规范 | 划改签名注日期，禁用修正液 |
| 保存期限 | 在表单页脚或总表中明示 |

## 七、脚本用法（受控台账体检）

```bash
python scripts/doc_number_check.py --file "D:\体系\受控台账.csv" --as-of 2026-10-13
```

| 参数 | 说明 |
|---|---|
| `--file` | 必填。受控文件台账 CSV（UTF-8/GBK） |
| `--as-of` | 核查基准日，默认今天 |
| `--out` | 输出路径 |
| `--format` | `md`（默认）或 `json` |
| `--selftest` | 跑内置样例自检 |

台账建议列：`doc_no, title, layer, version, status, owner, issue_date, next_review, approver`
脚本检查七类问题：**编号格式违规、编号重复、版本断档、审批人缺失、超期未评审、作废仍有效、记录表单无对应程序**。

## 八、人工确认（这步不能省）

- [ ] 体系范围描述与营业执照、现场实际一致
- [ ] 过程归口部门与组织架构、岗位职责匹配
- [ ] 外来标准清单覆盖全部适用法规与产品标准
- [ ] 记录表单与实际使用的一致性（有没有没人填的表）
- [ ] 电子文件主控形式与备份机制是否成文

## 九、输出结构（固定三段）

1. **体系文件清单** —— 四层架构、编号、归口、状态一览
2. **受控台账体检** —— 逐项标合规/缺失/存疑
3. **整改与迎审建议** —— 先后顺序、责任部门、留存材料

## 十、最常见的坑

**坑一：文件与实际两张皮。**
程序书写一套、现场做一套。审核员访谈三个员工三个版本，直接开不符合项。

**坑二：编号打架。**
同一文件两个编号，或换版后编号跟着变，追溯链断掉。

**坑三：作废文件躺现场。**
旧版指导书还在车间抽屉里，操作工照旧版干，出了事说不清。

**坑四：记录后补。**
审核前一周集中补记录，笔迹、日期、逻辑全穿帮，性质从"不符合"变"诚信问题"。

**坑五：记录表单没人填。**
设计了几十张表，实际用的就五张。设计时先问执行岗位"填这个有没有用"。

**坑六：换版不改动配套记录。**
程序换版了，记录表单还是旧字段，前后对不上。
