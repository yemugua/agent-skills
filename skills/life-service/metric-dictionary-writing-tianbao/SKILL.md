# 指标字典编写与口径对齐（metric-dictionary-writing）

同一个「活跃用户」，市场部说 120 万、产品部说 95 万、财务说 100 万。
三个数都「有依据」，问题在于**没有任何一处文档写着依据是什么**。

指标字典要解决的就是这一件事：**让每个指标的口径有唯一出处，且能追溯。**

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出九项必备字段与每项最低填写标准 | ❌ 代替业务方确定指标的**业务含义**（如什么算「活跃」） |
| 提供命名规范模板与改名检查 | ❌ 保证改完名所有下游报表自动同步（需人工改造） |
| 给出口径变更三段式流程 | ❌ 直接决定废弃指标是否可下线（须业务方确认） |
| 检查同义词重复建设 | ❌ 代替数据血缘系统做影响面分析 |
| 校验公式与字段的自洽性 | ❌ 保证指标计算结果正确（需对数验证） |

**以下情况必须先做别的：**
- 指标的业务含义本身没人能说清 → 先开口径对齐会，别急着写文档
- 已有多个同名但口径不同的指标 → 先做**合并决策**（选主口径还是拆成两个指标）
- 指标涉及跨部门结算或对外披露 → 必须有财务与法务参与确认

## 二、完整工作流

```
第 1 步  读规则文件 rules/metric_dictionary_spec.md（九字段、命名规范、变更流程）
第 2 步  建目录：按业务域划分，不按报表划分
         例：交易域 / 用户域 / 内容域 / 履约域
第 3 步  对每个指标写满九项必备字段（模板见 templates/）
第 4 步  做同义词扫描，找出重复建设的指标
         同一个业务对象+动作有 2 个以上指标名 → 必须做合并决策
第 5 步  跑完备性校验
         python scripts/metric_dict_check.py --file metrics.csv
         → 输出 缺字段/命名不规范/公式不自洽/废弃但无下线记录 四类分级问题
第 6 步  定责任人：每个指标必须有一个业务 owner 和一个数据 owner
第 7 步  建立变更流程：新指标 / 口径变更 / 废弃 三条路径各有流程
```

## 三、九项必备字段（缺一项不得上线）

| # | 字段 | 最低填写标准 | 缺失后果 |
|---|---|---|---|
| 1 | **指标名** | 业务语言，中文无歧义；同名指标全公司唯一 | 沟通时反复确认「你说的是哪个」 |
| 2 | **业务定义** | 一句话说明「这个指标用来回答什么问题」 | 无法判断指标是否被误用 |
| 3 | **计算公式** | 精确到字段与运算；比率型必须写明分子分母 | 各方自己实现，数必然不同 |
| 4 | **统计维度** | 至少列出可拆分的维度（时间/渠道/端/人群） | 只有一个总计值，无法下钻 |
| 5 | **时间窗口** | 自然日还是滚动；时区；边界含不含 | 跨时区或跨天时对不上 |
| 6 | **数据来源** | 来源表名 + 关键字段 + 计算方式（SQL 或计算逻辑） | 无法验证、无法重建 |
| 7 | **负责人** | 业务 owner + 数据 owner，各一名 | 数不对时无人可问 |
| 8 | **更新频率** | 实时 / 小时 / T+1 / 周 / 月 + 具体产出时间 | 用户把半天的数当全天 |
| 9 | **口径变更记录** | 版本号 + 变更日期 + 变更内容 + 是否重算历史 | 跨断点数据被错误对比 |

> **第 9 项最常被省略，也最致命。** 没有变更记录，一年后没人说得清某个数字变化是业务变化还是口径变化。

## 四、命名规范七要素

```
命名结构：  业务域_业务对象_统计动作_口径修饰_时间周期
示例：      trade_order_paid_gmv_1d
            user_active_device_dau_1d
```

| 要素 | 说明 | 取值示例 |
|---|---|---|
| 业务域 | 指标归属的域 | trade / user / content / logistics |
| 业务对象 | 度量的实体 | order / user / goods / merchant |
| 统计动作 | 做了什么 | paid / active / refund / avg / cnt |
| 口径修饰 | 排除/包含的规则 | all / new / valid / excl_refund |
| 时间周期 | 窗口长度 | 1d / 7d / 30d / mtd / lifetime |

**四条命名硬规则：**

| 规则 | ❌ 错误 | ✅ 正确 |
|---|---|---|
| 不用「总数」这类空词 | `order_total` | `trade_order_paid_cnt_1d` |
| 比率型必须含比率标记 | `order_paid_rate` → 改为 `order_paid_ratio_1d` | 明确是 ratio 而非 count |
| 累计型必须标注 | `gmv` | `gmv_mtd`（月累计） |
| 不含时间维度别名 | `daily_active_user` | `user_active_device_dau_1d` |

**缩写表必须在字典里给出**：`dau`=日活、`mau`=月活、`gmv`=成交总额、`aov`=客单价、`arpu`=每用户平均收入。**没有缩写表的命名规范等于没有规范。**

## 五、同义词与重复建设

**识别信号：同一个「业务对象 + 统计动作」出现多个指标名。**

| 情形 | 判断 | 处置 |
|---|---|---|
| 同名同口径 | 完全重复 | 保留一个，其余标记为别名 |
| 同名不同口径 | **危险** | 必须合并决策，或改名区分后同时保留 |
| 不同名同口径 | 别名泛滥 | 选定一个主名，别名全部登记 |
| 不同名不同口径 | 正常 | 各自建条目，但需在描述里写清区别 |

**举例**：订单数有 `order_cnt`、`order_count`、`order_num`、`order_total` 四个字段存在于不同报表里——这是最典型的重复建设，必须收敛到一个主名。

**同名不同口径的处理流程：**
1. 列出各口径的具体差异（分子分母、过滤条件）
2. 判断业务上是否真的需要两个口径
3. 需要 → 改名区分（用口径修饰要素），并在字典中互相引用
4. 不需要 → 选定一个为准，其余标记废弃并走下线流程

## 六、口径变更三段式流程

```
① 登记变更
   新版本号 + 变更日期 + 变更内容 + 变更人 + 审批人
② 影响面评估
   列出所有引用了该指标的报表、看板、API、看板与下游任务
③ 历史数据处置（二选一，必须明确记录）
   A. 全量重算：以新口径回溯重算全部历史，标注重算区间
   B. 断点处理：不重算，标注断点日期，断点两侧不可直接比较
④ 双跑期（涉及对外披露或结算时必须有）
   新旧口径并行产出至少一个完整周期（建议含一个完整月结周期）
⑤ 通知与切换
   更新字典、通知所有引用方、切换下游、下线旧口径
```

**铁律：口径变更后不做任何标注 = 数据污染。** 断点两侧的历史对比会得出完全错误的结论（详见「指标字典编写与口径对齐 · 最常见的坑」第六条）。

**在字典里的写法：**

```
口径变更记录：
v1.0  2025-01-01  初始口径：支付订单数 / UV
v2.0  2026-03-15  排除测试订单（order_type != 'TEST'）；历史自 2025-01-01 起全量重算
v3.0  2026-09-01  分子改为支付成功且未退款；历史未重算，断点 2026-09-01，两侧不可比
```

## 七、废弃指标下线流程

**四个前置条件（缺一不得下线）：**

| # | 条件 | 判定 |
|---|---|---|
| 1 | 无活跃引用 | 近 90 天血缘中无任何报表/看板/API 引用 |
| 2 | 已通知使用方 | 至少提前 30 天通知并确认无人使用 |
| 3 | 有替代指标 | 明确指向哪个现行指标 |
| 4 | 历史数据保留 | 已产出的历史数据归档保留，不删除 |

**下线条目必须写明：**

```
状态：deprecated
废弃日期：____
废弃原因：____
替代指标：____（字典链接）
最后引用方：____（已确认不再使用）
历史数据：已归档至____，保留____
```

**禁止**：直接把指标从字典删掉。删除会让历史报表失去出处，且无法回答「这个数以前是怎么算的」。

## 八、脚本用法

```bash
# 校验指标字典条目
python scripts/metric_dict_check.py --file metrics.csv

# 指定模式，额外检查命名规范
python scripts/metric_dict_check.py --file metrics.csv --check-naming

# 检查同义词重复
python scripts/metric_dict_check.py --file metrics.csv --check-duplicates

# 检查废弃指标下线完整性
python scripts/metric_dict_check.py --file metrics.csv --check-deprecated
```

**CSV 格式：**

| 列名 | 含义 | 必填 |
|---|---|---|
| `metric_id` | 唯一 ID | ✅ |
| `metric_name` | 指标中文名 | ✅ |
| `business_def` | 业务定义 | ✅ |
| `formula` | 计算公式 | ✅ |
| `dimensions` | 统计维度 | ✅ |
| `time_window` | 时间窗口 | ✅ |
| `source` | 数据来源 | ✅ |
| `biz_owner` | 业务负责人 | ✅ |
| `data_owner` | 数据负责人 | ✅ |
| `freq` | 更新频率 | ✅ |
| `change_log` | 口径变更记录 | ✅ |
| `name_en` | 英文规范名 | 选 `--check-naming` 时必填 |
| `status` | `active` / `deprecated` | ✅ |
| `replacement` | 替代指标（废弃时必填） | 废弃时必填 |
| `notify_date` | 通知日期 | 废弃时必填 |

脚本输出四类分级问题：
- **错误（ERROR）**：必备字段缺失、公式无分子分母、废弃指标缺替代指标或通知日期、`metric_id` 重复
- **警示（WARN）**：命名不符规范、未标注缩写表、无变更记录、同义词重复
- **提示（INFO）**：建议补齐负责人或更新频率的更细说明
- **结论**：是否达到可发布标准

## 九、人工确认清单（这步不能省）

- [ ] 九项必备字段全部填了吗？公式精确到字段了吗？
- [ ] 业务定义说的是「回答什么问题」，而不只是「怎么算」吗？
- [ ] 比率型指标的分子分母都写了吗？
- [ ] 时间窗口含时区与边界规则吗？
- [ ] 至少列了一个可拆分维度吗？
- [ ] 业务 owner 和数据 owner 都指定了吗（不是只写一个部门）？
- [ ] 英文规范名符合七要素吗？缩写表里有这个缩写吗？
- [ ] 同义词扫过了吗？同名不同口径的都做合并决策了吗？
- [ ] 口径变更记录里能看出「是否重算历史」吗？
- [ ] 废弃指标满足四个前置条件了吗？
- [ ] 和财务/业务报表对过数吗？差异能解释到字段级吗？

## 十、最常见的坑

**坑一：只写公式，不写业务定义。**
公式写「COUNT(DISTINCT user_id)」，业务定义留空。三个月后有人问「这个活跃用户包含只打开未登录的匿名用户吗」，没人答得上来。**业务定义回答「这个指标用来回答什么问题」，公式只回答「怎么算」，两者不能互相替代。**

**坑二：比率型指标不写分母。**
「转化率 3.2%」——分子是支付订单还是支付 UV？分母是曝光、访问还是下单？分母不同结果差好几倍。**比率型指标的分子分母必须分别写清。**

**坑三：口径变更不留记录。**
2026 年把「活跃用户」从「登录过」改成「完成核心行为」，然后拿新定义去比旧定义，得出「活跃大涨 40%」。这 40% 全是口径变化。**口径变更必须登记版本号、日期、内容和是否重算历史。**

**坑四：口径变更后不评估影响面。**
改了订单数的过滤条件，忘了某张财务报表也在用这个指标，三个月的财务表数据全错，且没人发现。**变更前必须列出所有引用方。**

**坑五：废弃指标直接从字典删掉。**
删掉之后，半年后有人问「以前那张报表里的『日活』是怎么算的」，无解。**废弃必须留条目**，标记 deprecated 并指向替代指标，历史数据归档保留。

**坑六：口径变更不重算也不标断点。**
最危险的一种。断点两侧直接对比，得出「同比大涨」，实际是定义变了。**二选一必须做：要么全量重算，要么明确标注断点日期且两侧不可比。**

**坑七：指标命名无规范，各报表各起各的名。**
`order_cnt`、`order_count`、`order_num`、`order_total` 四个字段并存，谁也不认谁。**收敛到一个主名，其余登记为别名**，并给出缩写表。

**坑八：只写部门不写人。**
负责人写「增长部」——出事时不知道找谁，且人员流动后无人接手。**必须写到具体的角色或个人，并设置备份。**

**坑九：把指标字典当技术文档写。**
字典是给业务方看的，每条都写满 SQL 实现，业务方读不下去也不看。**业务定义用业务语言，计算逻辑放附录或链接到数据文档。**

**坑十：更新频率不写具体时间。**
写「T+1」，用户不知道几点能看；凌晨 3 点查看到昨天的数，以为今天已经出了。**要写清「每日 08:00 前产出」。**

**坑十一：指标定义了但没有使用场景。**
定义了一堆没人用的指标，维护成本高，最终整个字典腐化。**新指标必须写明「谁在什么场景下用它」，写不出来就不该建。**

## 十一、边界与免责

- 本技能给出的是**字段结构、命名规范与流程要求**，指标的**业务含义必须由业务方确定**，本技能不代替业务决策
- 字典建设涉及跨部门协调，实际推进节奏取决于组织协作方式
- 涉及对外披露、财务结算、法务口径的指标，必须经相应部门正式确认，**以现行规定和主管部门要求为准**
- 历史数据重算的成本与必要性需评估，涉及不可逆的数据订正时应谨慎操作并保留原始数据
- 指标平台的技术实现（血缘采集、自动同步、影响面分析）超出本技能范围
