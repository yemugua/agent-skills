# 留存分析口径定义与核查（retention-analysis-definition）

留存率是**唯一一个「不同人算出不同数」的指标**。
同样一批用户，有人算 25%、有人算 40%，两边都没错——只是口径不同。

这个技能做三件事：**定口径** → **算准数** → **读曲线**。

---

## 硬边界（先看这条）

| 能做 | 不能做 |
|---|---|
| 给出 N 日留存的完整定义与回访窗口 | ❌ 代替业务方定义「什么算一次有效回访」 |
| 校验留存矩阵的边界一致性与加权换算 | ❌ 保证留存率高低就能判断产品好坏（需对标同类产品） |
| 说明按注册日与按活跃日分组的差异 | ❌ 把留存下降直接归因为产品改动（需排除同期因素） |
| 解读留存曲线形态（平坦/陡降/台阶） | ❌ 预测未来留存或给出留存提升方案 |
| 检查跨端/跨天/去重口径陷阱 | ❌ 替代 A/B 实验验证改动效果 |

**以下情况必须先做别的：**
- 还没定义「活跃」（打开/登录/完成核心行为）→ 先定活跃事件，再谈留存
- 业务本身低频（用户一周才来一次）→ 次日留存天然极低，应改用 7 日或 14 日口径
- 同一用户跨多端 → 必须先确定用户 ID 归并规则，否则留存被系统性低估

## 二、完整工作流

```
第 1 步  读规则文件 rules/retention_definition.md（N 日定义、两种分组、曲线判读）
第 2 步  定四件事（缺一件就不能出数）：
         ① 起点事件（注册/首次下单/首次活跃）
         ② 留存事件（打开 App / 登录 / 完成核心行为）
         ③ 回访窗口（第 N 天那一天，还是前 N 天内任一次）
         ④ 分组基准（按注册日 cohort，还是按活跃日 cohort）
第 3 步  算留存矩阵并校验
         python scripts/retention_audit.py --file retention.csv \
             --unit user --base signup --active "app open" \
             --window "day N only" --on-day 1 --on-day 7 --on-day 30
第 4 步  做交叉校验：加权留存率（按当日 cohort 规模加权）应与逐日留存一致
         对不上 → 说明分母口径不一致，回去查
第 5 步  读曲线形态：陡降 / 台阶 / 平坦 / 二次上扬，各对应不同结论
第 6 步  按维度横向对比（渠道、机型、新老、地区），找留存差异最大的细分
```

## 三、N 日留存的四种定义（必须显式声明用哪一种）

设 `C(t)` = 第 t 天开始时仍在队列内的用户数，`R(t, N)` = 留存人数。

| 定义 | 公式 | 名称 | 特点 |
|---|---|---|---|
| **当日留存** | `R(t,N) / C(t)`，其中 t 为第 N 天 | N 日留存（On-day） | **最常用**，是「第 N 天当天来过」 |
| **区间留存** | 第 0~N 天内**至少来过一次**的用户 / `C(t)` | N 日内留存（Unbounded/Range） | 数值更高，不能与当日留存混称 |
| **加权留存** | Σ(逐日留存 × 当日 cohort 规模) / Σ(当日 cohort 规模) | 加权 N 日留存 | 用于跨队列横向比较 |
| **滚动留存** | 第 t 到 t+N 天内累计来过 | 滚动留存 | 反映「一段时间内来过」，与队列无关 |

> **最常见的对不上来源**：运营报的是「7 日内留存」（区间留存），数据报的是「第 7 日留存」（当日留存）。同一批用户，前者可能是后者的 2 倍。**报告里必须写「7 日留存（当日）」还是「7 日内留存（区间）」。**

## 四、次日 / 7 日 / 30 日留存的区别与适用场景

| 口径 | 反映什么 | 适用场景 | 风险 |
|---|---|---|---|
| **次日留存（D1）** | 首次体验后的即时回访意愿 | 新手引导、首次体验优化、注册转化链路 | 对低频业务天然偏低；受「第二天才想起用」影响大 |
| **3 日留存** | 短期的习惯形成期 | 需要短期养成的工具类 | 与 D1 高度相关，边际信息少 |
| **7 日留存（D7）** | 一周内的习惯是否建立 | **社交、内容、消费类产品的核心指标** | 受周末效应影响，需看完整自然周 |
| **14 日留存** | 两周习惯 | 订阅制、工具类 | 数据成熟慢 |
| **30 日留存（D30）** | 长期价值与 LTV 基础 | **付费模型、融资材料、LTV 测算** | 早期队列数据未成熟，需标注 |

**选择原则：**
- **要快**（高频迭代）→ D1 / D7
- **要准**（评估长期价值）→ D30，且必须等队列满 30 天
- 业务天然低频（社交、内容）→ 直接从 D7 起看，D1 参考价值低

## 五、按注册日 vs 按活跃日分组（结论会不同）

| 分组基准 | 定义 | 回答什么问题 | 适合场景 |
|---|---|---|---|
| **按注册日（Signup cohort）** | 按首次注册/首次活跃的日期分组 | 「这批新用户后来还回来吗」 | 评估拉新质量、渠道对比、新手引导效果 |
| **按活跃日（Active cohort）** | 按当天活跃用户分组，看其在之后各天的回访 | 「现有用户里哪些留下来了」 | 评估存量健康度、活动效果、整体留存趋势 |

**差异最大的场景：**

| 场景 | 按注册日 | 按活跃日 | 谁更适合 |
|---|---|---|---|
| 评估新渠道拉来的用户质量 | ✅ 新用户 D7 明显低于老渠道 | ❌ 看不出来 | 按注册日 |
| 评估一次运营活动效果 | ❌ 活动只影响存量 | ✅ 活动日活跃用户后续留存变化明显 | 按活跃日 |
| 评估新手引导改动 | ✅ 直接看新用户 | ❌ 混入老用户，效应被稀释 | 按注册日 |
| 看公司整体留存趋势 | ❌ 受拉新波动影响大 | ✅ 更稳定 | 按活跃日 |

> **结论**：两套都要有。**只报一套，另一套的问题就永远看不见。**

## 六、加权留存率与流失率换算

```
加权 N 日留存  = Σ(各日 cohort 留存率 × 该日 cohort 规模) ÷ Σ(该日 cohort 规模)
加权 N 日流失  = 1 − 加权 N 日留存
当日流失率      = 1 − 当日 N 日留存率
区间流失率      = 1 − N 日内留存率（区间定义下）
```

**注意两条曲线的分母不同：**
- **加权留存**用**当日 cohort 规模**加权（每个新用户批次权重相同）
- **按活跃日的加权留存**用**当日活跃用户数**加权

两者数值会不同，**不能混用同一个「平均留存率」**。报告里必须说明用哪种权重。

## 七、留存曲线形态判读（平坦意味着什么）

| 形态 | 特征 | 含义 | 该做什么 |
|---|---|---|---|
| **断崖式**（D1 就很低） | D1 < 20%，之后平缓 | 首次体验有问题，或流量不精准 | 优先查新手引导与渠道质量 |
| **陡降后平坦** | 前 3 天快速下降，之后稳定 | 常见的健康形态，触底了 | 看触底后的平台值，这是真实留存水平 |
| **持续陡降无平台** | 到 D30 仍在下降 | 产品未形成使用习惯 | 检查核心价值是否成立 |
| **台阶状** | 明显断层（如 D7 与 D14 之间突降） | 存在周期性使用场景（周末/发薪日） | 排查是否有周期因素，不要误判为流失 |
| **二次上扬** | 先降后升 | 回访型产品（社交、消息） | 正常，注意勿把低谷当真实流失 |
| **平坦且高** | D7 后稳定在高位 | 核心价值已成立 | 以提升绝对值为目标 |
| **平坦且低** | D7 后稳定在低位（如 5%） | 触底了，但触底位置低 | **「已经触底」不等于「触底位置可以接受」** |

**最容易被误读的一点：「留存曲线平坦了」经常被当成好消息。**

**平坦只说明「不再继续流失」，不说明「留得够多」。** 一个 D7 稳定在 3% 的产品，曲线同样平坦。正确读法是**同时看形态和绝对值**：

| D7 绝对值（参考量级） | 判读 |
|---|---|
| ≥ 25% | 多数消费/社交类产品可接受水平 |
| 15%–25% | 正常区间，取决于获客成本 |
| 8%–15% | 偏低，需评估 LTV 是否覆盖获客成本 |
| < 8% | 触底位置过低，产品价值主张可能不成立 |

> 上表是**通用参照量级，不是行业标准**。不同品类差异极大，必须同时对标同类产品的公开数据或自身历史值。工具类 10% 未必差，社交类 10% 很可能有问题。

## 八、口径陷阱（留存数字对不上的六个原因）

| # | 陷阱 | 表现 | 处置 |
|---|---|---|---|
| 1 | **当日留存 vs 区间留存混用** | 同一批数据两个数相差近一倍 | 每次写「N 日留存」必须标注是当日还是区间 |
| 2 | **回访窗口未定义** | 「7 日留存」是否包含第 7 天当天？含不含第 6 天？ | 显式写「第 N 天当天」或「第 0~N 天内任一次」 |
| 3 | **跨端未归并** | 用户 App 登录了但没打开微信小程序，被算流失 | 统一用户 ID 归并；未登录单列口径 |
| 4 | **活跃事件选得太宽松** | 「打开 App」就算活跃，卸载重装也算 | 明确核心行为；必要时用「完成核心动作」 |
| 5 | **队列未满期** | 昨天的队列算「30 日留存」，实际只跑了两天 | 队列未满 30 天的行必须留空，不能填 0 |
| 6 | **加权方式不一致** | 用 cohort 规模加权 vs 用日活加权，混用 | 固定一种加权方式并注明 |

**队列未满期是最隐蔽的坑**：把「昨天注册的队列」的 30 日留存填成 0，整条曲线会出现断崖，看起来像大量流失，实际是数据还没跑出来。**正确做法是留空或标注「未成熟」。**

## 九、脚本用法

```bash
# 校验留存矩阵并计算加权留存
python scripts/retention_audit.py --file retention.csv \
    --unit user --base signup --active "app open" \
    --window "day N only" --on-day 1 --on-day 7 --on-day 30

# 检查队列成熟度（queue_age 为队列已存在天数）
python scripts/retention_audit.py --file retention.csv --check-maturity

# 检查权重一致性
python scripts/retention_audit.py --file retention.csv --check-weight
```

**CSV 格式（`cohort_date` 与 `dN` 列必填，`dN` 表示第 N 日留存率）：**

| 列名 | 含义 |
|---|---|
| `cohort_date` | 队列日期（注册日或活跃日） |
| `size` | 该队列用户数 |
| `d1`,`d7`,`d30` … | 对应 N 日的留存率，取值 0–1；**写 `40%` 也可以，但必须带百分号** |
| `queue_age` | 队列已存在天数（用于成熟度检查） |

> 百分号是必需的：`40%` 会被解析为 0.40，而裸写的 `1.4` 会被判为**错误**（留存率不可能超过 100%），而不是被自动缩放。这样「去重失效导致分子大于分母」这类问题才会暴露出来，而不是被悄悄改小。**留空 = 队列未成熟，正确做法；填 0 = 假异常，脚本会警告。**

脚本输出：逐队列留存率、加权留存率（按 `size` 加权）、流失率换算、边界一致性校验（各 N 日留存应随 N 增大而不增）、队列成熟度检查、口径字段完整性诊断。

**单调性校验**：在**同一回访窗口定义**下，第 N 日留存率应随 N 单调不增。若 D7 > D1，说明口径混用或数据错误，脚本会报错。

## 十、人工确认清单（这步不能省）

- [ ] 起点事件定义了吗（注册/首次下单/首次活跃）？
- [ ] 留存事件定义了吗？「活跃」是打开 App 还是完成核心行为？
- [ ] 回访窗口是「第 N 天当天」还是「第 0~N 天内任一次」？
- [ ] 分组基准是注册日还是活跃日？
- [ ] 跨端用户归并了吗？未登录用户怎么处理？
- [ ] 队列未满期的行留空了吗？还是被填成了 0？
- [ ] 加权方式是按 cohort 规模还是按日活？报告里写了吗？
- [ ] 同时给了注册日和活跃日两套吗？
- [ ] 留存曲线的**绝对值**评估过了吗（而不只看形态）？
- [ ] 对标的是同类产品还是自己的历史值？
- [ ] 留存下降有没有排除同期因素（版本发布、渠道变化、活动）？

## 十一、最常见的坑

**坑一：把「7 日留存」和「7 日内留存」当成同一个数。**
运营报的 40% 是区间留存（第 0~7 天来过就行），数据报的 22% 是当日留存（只算第 7 天）。两个都对，但混用会吵到天昏地暗。**每次写留存率必须带「当日」或「区间」限定词。**

**坑二：队列没满期就出数，把空值填成 0。**
昨天的队列算「30 日留存」，实际只跑了两天，填成 0 之后曲线尾部断崖，图上看像大量流失。**未满期的队列必须留空或标注「未成熟」，这是留存图最常见的假异常。**

**坑三：把「曲线平坦了」当成好消息。**
平坦只说明不再继续流失，不说明留得够多。D7 稳定在 3% 的产品曲线同样平坦。**必须同时看形态和绝对值，并和同类产品或自身历史对标。**

**坑四：只报注册日 cohort，看不到存量问题。**
只按注册日分组时，一次只影响存量用户的运营活动完全看不出来——因为新用户队列的留存没变。**两套分组都要有，只报一套就等于蒙住一只眼。**

**坑五：回访窗口不写，跨人沟通全靠猜。**
「7 日留存」到底含不含第 7 天？含不含第 6 天上午的访问？口径不写进指标字典，三个月后没人说得清。**回访窗口必须写进字典并在每次引用时带上。**

**坑六：跨端没归并，留存被系统性低估。**
用户在小程序用过了，但因为没有统一 ID，系统认为是两个用户，一个「流失」了。**未登录用户是重灾区**——只有设备 ID 时跨端无法归并，这个限制必须写明。

**坑七：留存下降直接归因为产品改动。**
D7 掉了 3pp，可能是上周换了渠道、拉来更多低质量用户，与产品改动无关。**留存是同期指标，不是不受其他因素影响的**。要证明是改动导致的，必须有对照组。

**坑八：加权留存率算法不统一，团队各算各的。**
有人按 cohort 规模加权，有人按日活加权，两人都叫「平均留存率」，数值差好几个点。**加权方式必须固定并注明。**

**坑九：只看 D1 做所有判断。**
D1 从 45% 掉到 42%，就宣布留存下滑开始恶化。但 D1 本来就受「新用户第二天才想起用」影响，波动大。**短期看 D1，长期看 D7/D30**，且 D7 要看完整自然周（避开周末效应）。

**坑十：拿不同定义的两个留存率做除法。**
「留存率提升了 20%」——如果基期是区间留存、本期是当日留存，这个 20% 纯属口径变化。**跨期对比前必须先确认口径完全一致，包括「活跃事件定义」是否改过。**

## 十二、边界与免责

- 留存是**同期指标**，会受到拉新渠道、季节、活动、版本发布的共同影响，单期变化不宜直接归因于产品改动
- 早期队列（如两年前的 D30）反映的是旧版本产品，跨期对比时须确认产品是否发生实质变化
- 本技能给出的 D7 绝对值参照量级为**通用经验值，非行业标准**；不同品类差异极大，必须以同类产品对标或自身历史为准
- 涉及用户标识合并与跨端口径，须遵守本单位数据合规要求，**以现行规定和主管部门要求为准**
- 留存事件（什么算「活跃」）的最终定义须与业务方确认，本技能给出的是口径结构与校验方法
